# 設計分岐点カタログ

対応要件：要件定義書全体。本書の目的は、要件定義書の記述だけでは実装方式が一意に定まらない箇所（＝複数の妥当な設計が考えられる分岐点）を洗い出し、採用方針を明記することで、実装フェーズでの手戻りリスクを減らすこと。

## 1. 分類の考え方

| カテゴリ | 定義 | このカテゴリへの対応 |
|---|---|---|
| A：技術検証待ち | 外部ライブラリ（主にalphaTab）の実際の仕様次第で実装方式が変わる分岐点。要件所有者の判断では決められない | 暫定方針＋フォールバックを明記し、Phase 0/1の技術検証結果で確定させる |
| B：工学判断で確定 | 要件文面からは複数実装が可能だったが、ユーザー体験や実装コストへの影響が小さく、設計者（Claude Code）の判断で確定してよいもの | 本セッションで確定し、各設計書に反映済み |
| C：ヒアリングで確定 | ユーザー体験・ビジネス方針に関わり、要件所有者本人の判断が必要だったもの | 本セッションのヒアリングで確定し、各設計書に反映済み |

新たな分岐点が見つかった場合は、本書に追記したうえで該当設計書を更新し、[[12_traceability.md]]から参照する運用とする。

## 5. 運用ルール

- 実装中に新たな分岐点（要件文面から複数実装が可能な箇所）に気づいた場合は、まず本書に追記し、カテゴリA〜Cのいずれかに分類する。
- カテゴリAの項目は、検証結果が出た時点で「解決済み」に更新し、確定した実装方式を該当設計書に反映する。
- [[12_traceability.md]]の完了基準チェックリストは、本書のカテゴリA項目が0件になった時点で「検証待ち事項なし」と言えるが、Phase 0/1の技術検証はスコープ上必須であるため、基本設計フェーズ自体の完了条件には含めない。
- **2026-09-02追記**：カテゴリAの項目は一律に同じ重みで扱わない。実機検証すればいずれかの選択肢に収束しフォールバックも用意済みの項目（A4・A6・A8・A9・A10等）と、検証結果次第でアーキテクチャ方針自体の見直しに発展しうる項目（A11・A12）とは性質が異なるため、後者に該当する項目は本書の記載上も「重み付けが異なる」ことを明記し、対応するPhaseの詳細設計に着手する前に優先的に検証・再検討する運用とする。
- **2026-09-06追記（B-1の教訓）**：ディレクトリ構造図・ファイルツリー表記は、1行につき1つのパスのみを記載する（性質の異なる複数のパスをカンマ区切り等で1行に併記しない）。1行に複数パスを詰め込むと、それぞれの実際の格納階層（親ディレクトリ）が一意に読み取れなくなる（本書B29、[[../review/design_review_2026-09-04.md]]B-1）。
