### 1.1 実装アーキテクチャ

```mermaid
flowchart LR
    SRC["各サービス層(編集/再生/ファイルI/O)"] -->|report(level, code, context)| NOTIFIER["NotificationCenter(Webコア内シングルトン)"]
    NOTIFIER -->|Info/Warning| TOAST["トーストキュー(ステータスバー付近)"]
    NOTIFIER -->|Error| HIGHLIGHT["譜面上ハイライト制御"]
    NOTIFIER -->|Critical| MODAL["確認モーダル"]
    NOTIFIER --> LOGGER["ログ基盤(2節)"]
```

- すべてのレベルのメッセージはまずログ基盤に記録される（後から確認できるようにする、要件5.4）。
- **画面に出すかはコードごとに決める（2026-09 追記、本人決定）**：記録（`report`）は 1 つ作って、ログに書く側と画面に出す側へ別々に渡す。**ログにはすべての記録を書く。** 画面に出すかどうかはコードごとの設定で、**指定が無ければ上表のレベルの表示形式で出す**。出さないと決めたコードの記録は、利用者へのメッセージではなく、端末内に残すデバッグログ（要件5.4「ログ・デバッグ情報」）として扱う。上表の4段階の表示形式（要件4.5「エラー・警告メッセージ」）は、画面に出す記録に当てはめる。出さない設定はレベルを問わず選べる。その代わり、どのコードが出さない設定かと、その理由を旧詳細設計 `00_reference.md` §5（`2759936` 時点）の表に印を付けて書き、一目で分かるようにする。最初の例は起動時の音源の先読みの失敗（`PLAY-003`）で、再生時に読み込み直すため、まだ再生していないうちに利用者へ知らせない（読み込み直しも失敗したら`PLAY-001`を画面に出す）。
- `NotificationCenter`はWebコアに属し、プラットフォーム非依存（[[01_architecture.md]]のレイヤー規則に従う）。表示コンポーネントのみがプラットフォームのUIフレームワーク（React）に依存する。
- トーストは複数同時発生時にキューイングし、重要度順（Warning優先）に表示する。
- **テスト可能性（本セッションで明記）**：`NotificationCenter`をElectron・DOM等に依存しない純粋ロジックとして実装することで、単体テストから`report()`を直接呼び出し、レベル別の振り分け結果（4段階のどこにルーティングされるか）とログ記録内容を検証できる。表示コンポーネント（トースト／ハイライト／モーダルの見た目）はロジックと分離しているため、`NotificationCenter`が発行するイベントを受けての描画のみを独立してテストできる。どのコードも単体テストの見本の入力（1.2節）を持ち、Criticalレベルはそれに加えて、発生条件（チェックサム不一致等）を結合テストでのフォールトインジェクションによって再現する。フリーズの確認（3節の表の「自動再読み込み」の行、メインプロセスが出すOSのネイティブダイアログ）は`NotificationCenter`の外にあるので、結合テストで確かめる（2026-10-09 追記）。詳細は[[11_test_strategy.md#4]]。
- **2026-09-02追記**：詳細設計（旧詳細設計 `error-logging-foundation.md`（`2759936` 時点））では、呼び出し側の誤用（同じコードに異なるレベルを渡してしまう等）を防ぐため、`report(level, code, context)`ではなく`report(code, context)`とし、レベルはエラーコードレジストリがコードから一意に導出する実装に精緻化した。基本設計レベルの図の意図（レベル別ルーティング）自体は変わらない。
- **2026-09-08追記（実装時、[[13_design_decision_points.md#3]]B32）**：Electronのmain/renderer分割上、`NotificationCenter`はrenderer（Webコア）内シングルトン、`Logger`（永続ログ・`FileSystemAdapter`注入）はmainプロセスに置き、両者を非破壊追加の`log:append` IPCで結線した。上図の「ログ基盤」への矢印は、実装ではrenderer→main IPC越しになる。詳細は旧詳細設計 `error-logging-foundation.md` §2.4（`2759936` 時点）。**main側の`Logger`が持つのは、①ファイルへの書き出しと⑦クラッシュ後の記録の2つだけで、ログの組み立て（レベル・書式）はWebコア側に置く**（2026-09 追記。[[01_architecture.md#4.1]]の①⑦の実装として読む。main側に8点目のシェル側責務を足したのではない）。現行の実装（旧詳細設計 `error-logging-foundation.md` §2.4（`2759936` 時点））は`toLogEntry`をmainに置いており（mainの`registerLogHandlers`が受け取ったイベントを`toLogEntry(event)`で`LogEntry`へ組み立ててから書く）、この原則と食い違う。`bd->dd`で是正する。

### 1.2 エラーコード体系

`{ドメイン}-{連番}`形式（例：`EDIT-001`＝重複配置、`FILE-002`＝チェックサム不一致による整合性エラー）とし、ログにはコードを必ず含め、発生源に曲や小節があるときは文脈情報（曲ID、小節番号等）も必ず含める（曲に関係しない通知、例：`SYS-001`には曲IDが無い。2026-09 改訂）。ドメイン一覧：`EDIT`（編集）、`PLAY`（再生）、`FILE`（ファイルI/O）、`EXPORT`（書き出し）、`SYS`（システム全般）、`RENDER`（譜面描画）、`TAG`（タグ管理）、`SONG`（曲一覧・曲数上限）。**2026-09-10 追記**：`RENDER`／`TAG`／`SONG` は実装時（パッケージ3・8）に追加されたドメインだが本一覧に反映されていなかったため補完した。コードの現行一覧は旧詳細設計 `00_reference.md` §5（`2759936` 時点）（統合表）が正で、本節はドメイン体系の説明に留める。各エラーコードは、それを発生させる最小限の入力を単体テストのフィクスチャとして持てるように、発生条件を一意に特定できる粒度で採番する（[[11_test_strategy.md#4]]）。実際に本パッケージ時点で登録されたコードの一覧は旧詳細設計 `error-logging-foundation.md` §4（`2759936` 時点）を参照。

## 2. ログ基盤（要件5.4、9章「容量上限10MBのローテーションログ」）

| 項目 | 設計 |
|---|---|
| 保存先 | [[06_file_io_persistence.md#3]]の`logs/`フォルダ |
| ローテーション方式 | 日次ファイル（`app-YYYYMMDD.log`）。フォルダ合計サイズが10MBを超えたら古いファイルから削除 |
| 記録内容 | タイムスタンプ、レベル、エラーコード、メッセージ、文脈情報（曲ID等）、スタックトレース（Error/Critical時） |
| クラッシュログ | レンダラークラッシュ検知時に別ファイル（`crash-YYYYMMDD-HHMMSS.log`）へ直前のログバッファ＋クラッシュ理由を書き出す。**【設計分岐点B8で決定】** このファイルも`logs/`フォルダ内に置き、通常ログと**同一の10MB容量上限を共有する**（クラッシュログ専用の別枠クォータは設けない）。ローテーション判定はフォルダ合計サイズで行うため、古いファイルから削除される際は日付の古いものから対象になり、通常ログ・クラッシュログの種別は問わない（[[13_design_decision_points.md#3]]B8） |
| 参照方法 | 設定ダイアログの「アプリ情報」からログフォルダをエクスプローラーで開けるようにする |

**設計分岐点B8の補足**：クラッシュ調査の重要性を踏まえ専用クォータを設ける案も検討したが、個人利用アプリでクラッシュ頻度が低い前提のもとでは実装の複雑化（2つの容量監視ロジック、優先削除順の設計）に見合わないと判断し、単純な単一クォータ方式に確定した。将来クラッシュが頻発するようであれば、クラッシュログのみ別途アーカイブする運用でカバーする。

## 3. クラッシュ検知・自動復旧の詳細（[[06_file_io_persistence.md#9]]と連動）

1. Electronメインプロセスが`webContents.on('render-process-gone', ...)`を監視。
2. 検知したら該当ウィンドウを`loadURL`で再読み込み。画面の部品の描画で例外が起きたときに出す画面（1節の`SYS-004`）の「画面を開き直す」ボタンも、この`loadURL`の再読み込みでウィンドウを開き直す（2026-10-14 本人決定）。
3. レンダラー起動時、直前のクラッシュフラグ（メインプロセスがセッション内で保持）を確認し、フラグがあれば直前の自動保存内容から状態復元＋Warningレベルで「直前のクラッシュから復旧しました」を表示。
4. クラッシュ理由はログに記録し、繰り返しクラッシュする場合（同一操作で3回等）はCriticalダイアログで詳細ログの場所を案内する。案内はログの場所を文で示すだけで、ログフォルダを開く手段は設定ダイアログの「アプリ情報」のままとする（2節の参照方法、[[13_design_decision_points.md#4]]C14、2026-10-09 追記）。

**フリーズ（応答なし）の検知（2026-09-10 追加、[[../detailed_design/00_reference.md#8.1]] G57）**：当時の要件5.4は「Webコアのレンダリング部分が**クラッシュ・フリーズ**した場合は自動検知して再読み込みし、直前の自動保存内容から復元する」と2つの条件を挙げているが、上記1〜4は`render-process-gone`（プロセスの消滅＝クラッシュ）しか監視しておらず、**フリーズ（プロセスは生きているが応答しない）の検知が落ちていた**。次を追加する。

| 項目 | 設計 |
|---|---|
| 検知 | メインプロセスが`webContents.on('unresponsive', ...)`を監視する。復帰した場合は`responsive`イベントで解除する |
| 扱いの違い | クラッシュ（プロセス消滅）は復帰の見込みが無いため**即座に再読み込み**するが、フリーズは重い描画・大曲のシリアライズ等で**一時的に応答しないだけの場合がある**（要件5.2の大曲対応、[[09_nonfunctional.md#2]]）。したがって即座には再読み込みせず、**フリーズ中はその場では何も出さない**（画面側は応答していないので表示できない。ウィンドウにはOSの「応答なし」が出る）。重い処理で一瞬止まるたびにダイアログを出さないためでもある |
| 自動再読み込み | `unresponsive`から**5秒**たっても`responsive`が来なければ、メインプロセスがOSのネイティブダイアログ（Critical、「待つ」「再読み込み」）で確認し、「再読み込み」が選ばれたときだけ再読み込みする。「待つ」を選んでさらに5秒応答が無ければ、もう一度出す。**自動保存されていない編集が失われうるため、無確認では再読み込みしない**（クラッシュ時はプロセスが既に失われているため確認の余地が無い、という違い）。2026-09 改訂（本人決定：フリーズ中は出さず、5秒後の2段目で選ばせる） |
| 復帰の通知 | 応答が戻ったら、画面側（Webコア）がWarningレベルの通知（`SYS-003`）で「一時的に応答が停止していました」と知らせる |
| 復元 | 再読み込み後の復元手順はクラッシュ時（上記2〜3）と同じ経路を使う |

**上位との関係（2026-09 追記、2026-09 改訂）**：当時の要件5.4「クラッシュ対応」は「Webコアのレンダリング部分（PC版：Electronのレンダラープロセス、iPhone版：WebView）がクラッシュ・フリーズした場合は自動検知して再読み込みし、直前の自動保存内容から復元する」と、**クラッシュとフリーズの両方について「自動検知して再読み込みし」と書いている。** クラッシュ側（上記1から4まで）はそのとおり無確認で再読み込みしており、要件どおり。**フリーズ側だけは、上の表のとおり確認を挟んでいて要件と異なる。** 理由は表に書いたとおり「自動保存されていない編集が失われうる」ためで、意図的に外していた。**2026-09、要件5.4をこの扱いに合わせて改めた。** 現行の要件5.4「クラッシュ対応」は「フリーズ（応答なし）した場合は自動検知して知らせ、確認のうえで再読み込みし、同じく直前の自動保存内容から復元する」で、クラッシュ側・フリーズ側とも要件どおりである。

**2026-09 確定（[[13_design_decision_points.md#3]] B43）**：この「フリーズ側だけ確認を挟む」という扱いを、**下位を正として確定した**。クラッシュはレンダラーが既に死んでおり、未保存の編集はその時点で失われているので、確認を出しても復元される中身は変わらない。フリーズはレンダラーが生きている可能性があり、検知そのものが誤判定しうるので、無確認で再読み込みすると生きていた未保存の編集を自分から壊す。当時の要件5.4からの意図的な逸脱として分岐点カタログに B43 を起こした。**2026-09、要件定義書をこの扱いに合わせて書き換えた**（要件5.4「クラッシュ対応」）。

エラーコード`SYS-003`（Warning：一時的に応答が停止していました。応答が戻ったあとに出す）を本節で新規に登録する。**2026-09-02追記**：「同一操作」の判定にはコマンド層（タブ譜編集コアパッケージ）の直前操作情報が必要なため、詳細設計（旧詳細設計 `error-logging-foundation.md` §2.3（`2759936` 時点））では暫定的に「同一アプリセッション内で3回」に簡略化し、コマンド層完成後に精緻化する方針とした。

## 4. テーマトークン化（要件4.5「配色はテーマトークン化」）

ダークモード非対応（現時点）だが、将来対応を妨げないため、色は直値ではなくトークン（[[14_visual_design_system.md#3]]の表にあるすべてのトークンを、`--color-` ＋表の名前のCSS変数にする。例：`--color-bg`, `--color-danger`, `--color-warning`。2026-09 改訂）で定義する。エラーハイライト色・トースト背景色もこのトークン体系に含める。命名規則と「直値禁止」ルールは本設計で確定し、**具体的な色トークンの値は[[14_visual_design_system.md#3]]で確定済み**（Warning＝`--color-warning`系、Error/Critical＝`--color-danger`系トークンを使用。Infoレベルは専用色を持たずsurfaceトークン＋アイコンで表現する）。

## 5. Criticalダイアログの文言方針

- 見出しで何が起きたか（例：「データの整合性エラーを検知しました」）、本文で原因の要約と選択肢（例：「このファイルの中身が、保存したときの記録と一致しません。保存の途中で書き込みが止まったか、ほかのアプリで書き換えられた可能性があります。ひとつ前に保存した内容（自動保存を含む）を復元しますか？」。2026-09 改訂：例が選択肢だけで原因の要約を欠いていて、そのまま写した文言にも欠けが写ったため、両方の入った例にした）、ボタンは肯定/否定を明確な文言にする（「復元する」「キャンセル」等、「OK」のみの曖昧な表現は避ける）。
