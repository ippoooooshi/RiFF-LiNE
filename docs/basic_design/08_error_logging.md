# エラー・ログ基盤設計書

対応要件：要件定義書4.5節（エラー・警告メッセージ）、5.4節（信頼性）、9章「エラー・警告基盤」「ログ基盤」作業パッケージ

## 1. 4段階メッセージ方式（要件4.5）

| レベル | 表示形式 | 発生源の例 | 操作継続 |
|---|---|---|---|
| Info | 自動消滅する軽量トースト（3秒程度） | 自動保存完了、エクスポート完了、Undo/Redo履歴のメモリ予算超過によるエビクション発生（セッション中初回のみ、`EDIT-008`） | 可 |
| Warning | やや目立つトースト＋アイコン | 上限接近（曲数900/1000＝90%到達）、ゴミ箱復元期限接近、クラッシュからの復旧成功通知、メモ文字数が上限（100字）に達し保存時に切詰め（`EDIT-004`）、ペースト時に貼り付け先の弦数不足で一部の音を破棄（`EDIT-009`） | 可 |
| Error | その場でブロック＋該当箇所を赤くハイライト（モーダルなし） | 重複配置、フレット範囲外、iCloud同期エラー、小節数上限(2048)超過、パート数上限(8)超過、タグ数上限(50)超過、曲数上限(1000)到達による新規曲作成の拒否（`SONG-002`） | 該当操作のみ不可、他操作は可 |
| Critical | 確認必須のモーダルダイアログ | データ破損検知（チェックサム不一致）、小節削除に伴うメモ/マーカー消失確認、繰り返しクラッシュの検知 | 応答するまでブロック |

### 1.1 実装アーキテクチャ

```mermaid
flowchart LR
    SRC["各サービス層(編集/再生/ファイルI/O)"] -->|report(level, code, context)| NOTIFIER["NotificationCenter(Webコア内シングルトン)"]
    NOTIFIER -->|Info/Warning| TOAST["トーストキュー(ステータスバー付近)"]
    NOTIFIER -->|Error| HIGHLIGHT["譜面上ハイライト制御"]
    NOTIFIER -->|Critical| MODAL["確認モーダル"]
    NOTIFIER --> LOGGER["ログ基盤(2節)"]
```

- すべてのレベルのメッセージはまずログ基盤に記録される（後から確認できるようにする、要件5.4）。
- `NotificationCenter`はWebコアに属し、プラットフォーム非依存（[[01_architecture.md]]のレイヤー規則に従う）。表示コンポーネントのみがプラットフォームのUIフレームワーク（React）に依存する。
- トーストは複数同時発生時にキューイングし、重要度順（Warning優先）に表示する。
- **テスト可能性（本セッションで明記）**：`NotificationCenter`をElectron・DOM等に依存しない純粋ロジックとして実装することで、単体テストから`report()`を直接呼び出し、レベル別の振り分け結果（4段階のどこにルーティングされるか）とログ記録内容を検証できる。表示コンポーネント（トースト／ハイライト／モーダルの見た目）はロジックと分離しているため、`NotificationCenter`が発行するイベントを受けての描画のみを独立してテストできる。Criticalレベルの発生条件（チェックサム不一致等）は結合テストでのフォールトインジェクションによって再現する。詳細は[[11_test_strategy.md#4]]。
- **2026-09-02追記**：詳細設計（[[../detailed_design/error-logging-foundation.md]]）では、呼び出し側の誤用（同じコードに異なるレベルを渡してしまう等）を防ぐため、`report(level, code, context)`ではなく`report(code, context)`とし、レベルはエラーコードレジストリがコードから一意に導出する実装に精緻化した。基本設計レベルの図の意図（レベル別ルーティング）自体は変わらない。
- **2026-09-08追記（実装時、[[13_design_decision_points.md#3]]B32）**：Electronのmain/renderer分割上、`NotificationCenter`はrenderer（Webコア）内シングルトン、`Logger`（永続ログ・`FileSystemAdapter`注入）はmainプロセスに置き、両者を非破壊追加の`log:append` IPCで結線した。上図の「ログ基盤」への矢印は、実装ではrenderer→main IPC越しになる。詳細は[[../detailed_design/error-logging-foundation.md#2.4]]。
- **2026-09-02追記（セルフレビューでの是正、[[13_design_decision_points.md#3]]B20）**：小節数上限(2048)・パート数上限(8)・タグ数上限(50)は、いずれも「上限に達したら操作自体を拒否する」ハードキャップであるにもかかわらず、当初本表でWarningレベル（操作継続可）として例示されていた。Warning本来の定義（操作は継続でき、追加を許可した上で警告するだけ）と実際の挙動（追加不可）が矛盾していたため、これら3件をErrorレベル（該当操作のみ拒否、他操作は可）に再分類し、上表を修正した。曲数上限90%到達（`SONG-001`）は追加自体を拒否しない予告的な警告のためWarningのまま据え置く。詳細設計側の該当箇所（[[../detailed_design/editing-core.md#7]]の`EDIT-003`、[[../detailed_design/part-tuning-management.md#4.4]]の`EDIT-005`、[[../detailed_design/screens-navigation.md#3.5]]の`TAG-001`）もあわせて修正した。あわせて、Critical例に誤って含まれていた「クラッシュ復旧通知」を、実際の実装（`SYS-001`=Warning：復旧成功、`SYS-002`=Critical：繰り返しクラッシュ）に合わせて訂正した。
- **2026-09-06追記（レビュー是正、[[../review/design_review_2026-09-04.md]]A-1）**：C11・C12（2026-09-03確定）に伴い新規登録された`EDIT-008`（Undo/Redo履歴エビクション通知）・`SONG-002`（曲数上限到達による新規作成拒否）が、[[00_reference.md#5]]のエラーコード統合表や[[09_nonfunctional.md#5]]には反映済みだった一方、本表の例示リストにのみ反映漏れが残っていた（本ファイルの直近更新が2026-09-02時点で、C11・C12確定（2026-09-03）より前だったため）。上表のInfo行・Error行にそれぞれ追加して解消した。

### 1.2 エラーコード体系

`{ドメイン}-{連番}`形式（例：`EDIT-001`＝重複配置、`FILE-003`＝チェックサム不一致）とし、ログにはコード＋文脈情報（曲ID、小節番号等）を必ず含める。ドメイン一覧：`EDIT`（編集）、`PLAY`（再生）、`FILE`（ファイルI/O）、`EXPORT`（書き出し）、`SYS`（システム全般）。各エラーコードは、それを発生させる最小限の入力を単体テストのフィクスチャとして持てるように、発生条件を一意に特定できる粒度で採番する（[[11_test_strategy.md#4]]）。実際に本パッケージ時点で登録されたコードの一覧は[[../detailed_design/error-logging-foundation.md#4]]を参照。

## 2. ログ基盤（要件5.4、9章「容量上限10MBのローテーションログ」）

| 項目 | 設計 |
|---|---|
| 保存先 | [[06_file_io_persistence.md#3]]の`logs/`フォルダ |
| ローテーション方式 | 日次ファイル（`app-YYYYMMDD.log`）。フォルダ合計サイズが10MBを超えたら古いファイルから削除 |
| 記録内容 | タイムスタンプ、レベル、エラーコード、メッセージ、文脈情報（曲ID等）、スタックトレース（Error/Critical時） |
| クラッシュログ | レンダラークラッシュ検知時に別ファイル（`crash-YYYYMMDD-HHMMSS.log`）へ直前のログバッファ＋クラッシュ理由を書き出す。**【設計分岐点B8で決定】** このファイルも`logs/`フォルダ内に置き、通常ログと**同一の10MB容量上限を共有する**（クラッシュログ専用の別枠クォータは設けない）。ローテーション判定はフォルダ合計サイズで行うため、古いファイルから削除される際は日付の古いものから対象になり、通常ログ・クラッシュログの種別は問わない（[[13_design_decision_points.md#3]]B8） |
| 参照方法 | 設定ダイアログの「アプリ情報」からログフォルダをエクスプローラーで開けるようにする |

**設計分岐点B8の補足**：クラッシュ調査の重要性を踏まえ専用クォータを設ける案も検討したが、個人利用アプリでクラッシュ頻度が低い前提のもとでは実装の複雑化（2つの容量監視ロジック、優先削除順の設計）に見合わないと判断し、単純な単一クォータ方式に確定した。将来クラッシュが頻発するようであれば、クラッシュログのみ別途アーカイブする運用でカバーする。

## 3. クラッシュ検知・自動復旧の詳細（[[06_file_io_persistence.md#9]]と連動）

1. Electronメインプロセスが`webContents.on('render-process-gone', ...)`を監視。
2. 検知したら該当ウィンドウを`loadURL`で再読み込み。
3. レンダラー起動時、直前のクラッシュフラグ（メインプロセスがセッション内で保持）を確認し、フラグがあれば直前の自動保存内容から状態復元＋Warningレベルで「直前のクラッシュから復旧しました」を表示。
4. クラッシュ理由はログに記録し、繰り返しクラッシュする場合（同一操作で3回等）はCriticalダイアログで詳細ログの場所を案内する。**2026-09-02追記**：「同一操作」の判定にはコマンド層（タブ譜編集コアパッケージ）の直前操作情報が必要なため、詳細設計（[[../detailed_design/error-logging-foundation.md#2.3]]）では暫定的に「同一アプリセッション内で3回」に簡略化し、コマンド層完成後に精緻化する方針とした。

## 4. テーマトークン化（要件4.5「配色はテーマトークン化」）

ダークモード非対応（現時点）だが、将来対応を妨げないため、色は直値ではなくトークン（`--color-bg-base`, `--color-error`, `--color-warning`等のCSS変数）で定義する。エラーハイライト色・トースト背景色もこのトークン体系に含める。命名規則と「直値禁止」ルールは本設計で確定し、**具体的な色トークンの値は[[14_visual_design_system.md#3]]で確定済み**（Warning＝`--warning`系、Error/Critical＝`--danger`系トークンを使用。Infoレベルは専用色を持たずsurfaceトークン＋アイコンで表現する）。

## 5. Criticalダイアログの文言方針

- 見出しで何が起きたか（例：「データの整合性エラーを検知しました」）、本文で原因の要約と選択肢（例：「直前の自動保存内容から復元しますか？」）、ボタンは肯定/否定を明確な文言にする（「復元する」「キャンセル」等、「OK」のみの曖昧な表現は避ける）。
