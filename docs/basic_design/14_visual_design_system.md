# ビジュアルデザインシステム

対応要件：要件定義書4.5節「配色はテーマトークン化」「設計原則（横断的）」、[[00_overview.md#6]]で「詳細設計・実装時に確定する」としていたビジュアルデザイン（配色具体値・フォント等）を、本セッションでの方向性確認（サンプルUIによる位相合わせ）を経て基本設計段階で確定するもの。[[03_screens_ui_pc.md]]が定義する画面構造・レイアウト・操作パターンに対し、本書は「どう見えるか」（配色・タイポグラフィ・余白・角丸・アイコン・コンポーネントの見た目）を定義する。

## 1. 経緯・位置づけ

[[00_overview.md#6]]は当初「UI設計（03章）はワイヤーフレームレベルに留め、ピクセル単位のビジュアルデザインは実装時に確定する」としていたが、本人から「UIデザイン・アーキテクチャにこだわりたい」との要望があり、実装に依存しないHTMLサンプルで配色・密度・コンポーネント形状の方向性をすり合わせたうえで、基本設計段階のうちに確定させることにした。本書はそのすり合わせ結果を正式な設計として記録するものであり、[[13_design_decision_points.md#4]]のカテゴリC（ヒアリングで確定した分岐点）にC5として追加登録する。

**ステータス**：色トークンの具体値・タイポグラフィ・コンポーネント形状は「方針確定」とする。ただし実際のalphaTabレンダリング結果（譜面部分の配色はalphaTab側の描画に依存する）を見ながら、Phase 0〜1で微調整の余地を残す（[[13_design_decision_points.md#2]]A2のレンダリング方式確認と合わせて調整）。

## 2. デザイン原則

ヒアリングで確認した好み（無骨すぎて使いづらいのも、AIっぽい見た目やポップすぎるのも避けたい／上品さと実用性のバランス）を、以下の具体的な設計原則に翻訳する。

| 原則 | 具体的な運用ルール |
|---|---|
| 装飾より機能を優先する | グラデーション・大きな柔らかい影・過剰に丸い角を避ける。要素の区切りは基本的に1pxの罫線（ボーダー）で表現し、影は「浮いていることを示す必要がある場合」（ドロップダウン、非ドッキング時のフローティングパネル、ツールチップ）に限定して使う |
| ニュートラル基調＋効果的な差し色 | 画面の大部分はグレースケール階調で構成し、アクセントカラーは主要ボタン・アクティブなナビゲーション/タブ・フォーカスリングなど「意味のある箇所」だけに使う。ステータス色（成功/警告/エラー）も彩度を抑え、多用しない |
| 数値・技術的情報は等幅フォントで示す | 小節番号／拍子／テンポ／ズーム％／曲数などの数値は等幅フォントで表示し、実務ツールらしい質感を出す（4節） |
| 密度は中間バランス | 詰め込みすぎず、間延びもさせない。1行の高さ・余白は実用的なクリック/視認のしやすさを優先する（5節） |
| パネルは急に縮退させない | サイドパネル（パートリスト等）は、ウィンドウが本当に窮屈にならない限りラベル付きの状態を維持する（7節で詳細） |

## 3. カラートークン

ライトモードのみが要件（要件5.4「ダークモードは不要」）だが、テーマトークン化の要件（要件4.5、[[08_error_logging.md#4]]）に基づき、ダーク値もあわせて定義しておく（将来の追加を容易にするための先行定義であり、v1で使用するのはライト値のみ）。命名規則は[[08_error_logging.md#4]]の「直値禁止・CSS変数で定義」方針に従い、`--color-*`のようなトークン名で実装する（下表の名称は意味の対応を示す仮称）。

|---|---|---|---|

**Part.colorとの関係**：[[02_data_model.md#3.2]]の`Part.color`（パート識別色、8色程度の既定パレットから自動割当・手動変更可）は、本節のアクセントカラーとは**独立した別の色システム**である。アクセントカラーはアプリのUIクロム（操作可能要素であることを示す色）、Part.colorはデータ（パートという概念）を識別するための色であり、混同しないよう実装時も別のトークン体系（`--part-color-1`〜`--part-color-8`等）として管理する。Part.colorの既定パレットは、本書のアクセントカラーと隣接しすぎない（パートの色をアクセント＝操作可能要素と誤認しない）よう、ヒュー（色相）を意図的にずらして選定する。

## 4. タイポグラフィ

**フォントスタック（PC版はWindows前提のため、Windows標準フォントを優先する）**：

```
UI基本: "Segoe UI", "Yu Gothic UI", "Meiryo UI", "Hiragino Kaku Gothic ProN", sans-serif
数値・技術情報用（等幅）: "Cascadia Mono", "Consolas", ui-monospace, monospace
```

macOS/iPhone版（Phase 3）着手時は上記スタックの先頭にSF系フォントを追加する形でよく、原則を変える必要はない。

**等幅フォントを使う箇所**（2節の原則に基づく明確なルール）：

- ステータスバーの小節位置／拍子／テンポ／カポ表示（[[03_screens_ui_pc.md#5]]）
- ズーム％表示
- 曲数・上限表示（例：「42/1000」）
- 小節メモ一覧・ゴミ箱の日時表示
- ミキサーのdB/パン数値表示

**サイズ・ウェイトの目安**（実装時はOSのUIスケーリングに追従するため相対単位で定義する）：

| 用途 | 目安サイズ | ウェイト |
|---|---|---|
| ダイアログ見出し | 15〜16px相当 | 650 |
| 本文・標準UI文字 | 13〜13.5px相当 | 400〜450 |
| ラベル・見出し小 | 11.5〜12px相当 | 600 |
| 補助文字・タイムスタンプ | 11px相当 | 500 |

## 5. スペーシング・密度

「中間バランス」（詰め込みすぎず間延びもさせない）に基づき、4pxを基準グリッドとする。

| トークン | 値 | 主な用途 |
|---|---|---|
| space-1 | 4px | アイコンと文字の間隔等、最小間隔 |
| space-2 | 8px | ボタン内パディング、タイトな要素間 |
| space-3 | 12px | パネル内の標準パディング |
| space-4 | 16px | パネル間・カード間の標準ギャップ |
| space-5 | 20〜24px | ウィンドウ余白（コンテンツ領域の外周） |

ツールバー・メニューバーの高さはそれぞれ目安28〜32px／44〜48pxとし、[[03_screens_ui_pc.md#5]]のレイアウトに合わせる。

## 6. 角丸・境界・影のルール

| トークン | 値 | 用途 |
|---|---|---|
| radius-sm | 4px | ボタン、バッジ、入力欄、アイコンボタン |
| radius-md | 6px | ドロップダウン、ポップオーバー |
| radius-lg | 8px | パネル、カード、ダイアログ |

- **影は最小限に使う**：ドッキングされているパネル・カード・テーブルは境界線のみで表現し、影を付けない。影を使うのは「画面上に浮いている」ことを示す必要がある要素（フローティング状態のミキサーパネル、ドロップダウンメニュー、ツールチップ、ダイアログ本体）に限定する。
- **角丸は統一的にやや控えめにする**：市販の「AIが生成したような」UIに見られがちな過剰な丸みは避け、実務ツール（Ableton／Figma等）に近い、直線基調の中に最小限の丸みを持たせる程度に留める。

## 7. ウィンドウ構成の視覚的な取り扱い

[[03_screens_ui_pc.md#5]]が定義する「メニューバー＋ツールバー＋パートリスト＋譜面表示領域＋入力ツールバー＋ステータスバー」という構造に対し、以下の視覚ルールを適用する。

### 7.1 メニューバー

OS標準（Windowsのアプリケーションメニュー相当）のテキストメニューとする。特別な装飾は行わず、視認性を最優先する（本人ヒアリングにより「見た目より視認性重視でよい」と確認済み）。

### 7.2 ツールバー

アイコンボタンを機能グループ単位でまとめ、グループ間を1pxの縦区切り線（ディバイダー）で分ける「アイコンクラスタ」方式とする（例：`[Undo][Redo] | [再生][停止][ループ][メトロノーム] | [ミキサー][パート][チューニング][フレットボード][メモ一覧]`、[[03_screens_ui_pc.md#5]]のツールバー構成に対応）。ズームコントロールは「−／％表示／＋」の3要素をひとつの縁取りされたグループとして表示する。このアイコン密度・グループ分けの考え方は、事前に作成したサンプルUIで確認済みの構成をそのまま踏襲する。

**アイコン素材の調達方針（新規確定）**：ツールバー・メニュー・パネル等で使うUIアイコンは自作せず、オープンソースの線画（ストローク）ベースのアイコンセット（Lucide等、MITライセンス相当のもの）を採用する。線の太さ・角の丸みが本書2節・6節の基調（境界線ベース、過剰な丸み回避）と一致するものを選定基準とする。採用ライブラリは実装時に1つに確定し、要件4.5の横断原則（第三者ライブラリ・アセットのライセンス確認）に従って[[10_extensibility_future.md#8]]のクレジット／ライセンス画面にエントリを追加する。

### 7.3 ステータスバー

常時表示とし、数値情報（小節位置・拍子・テンポ・カポ・ズーム％）は4節の等幅フォントルールに従う。[[08_error_logging.md#1]]のInfo/Warningトーストの表示領域も兼ねる。

## 8. レスポンシブ・堅牢性の原則

要件5.6「ウィンドウサイズ：最小800×600、最大はモニタサイズに応じて拡大可能」を踏まえ、以下を確定する。

### 8.1 パートリストパネル（左パネル）は自動で縮退させない

サンプルUIでの検証を踏まえ、**パートリストパネル（[[03_screens_ui_pc.md#5]]）は、ウィンドウ幅に応じて自動的にアイコンのみの表示へ縮退させる実装は行わない**方針に確定する。理由：

- 実アプリの対応ウィンドウ幅は800px〜であり、この範囲内でパートリストをラベル付きのまま表示する余地は十分にある。
- パート名（曲ごとに自由入力される情報）はアイコンだけでは判別できないため、自動縮退は誤操作（別パートの選択・編集）のリスクを増やす。
- 画面領域を広げたいユーザー自身の意思は、パネル境界のドラッグによる**手動リサイズ**（最小幅は目安120px程度、パート識別色スウォッチ＋ミュート/ソロアイコンが判読できる下限）で吸収する。これは自動の閾値縮退ではなく、ユーザーが明示的に選択する操作である点が異なる。

同じ考え方を、将来Phase 3（iPhone版）以降で類似のリスト型UIを設計する際にも踏襲する。

### 8.2 ツールバー・メニューバーは折り返し／横スクロールで吸収し、崩れさせない

ツールバーの合計幅がウィンドウ幅を超える場合は、要素が重なったりウィンドウ外にはみ出したりしないよう、次のいずれかで吸収する（サンプルUIで検証済みの手法）。

- ツールバー：折り返し（2段化）を許容し、行の高さは固定せず可変にする。
- メニューバー：折り返さず、必要であれば横スクロール（スクロールバー非表示）で吸収する。
- いずれの場合も、ページ（ウィンドウ）全体が横スクロールする状態は避ける（要素ごとの内側スクロール／折り返しで完結させる）。

### 8.3 表・一覧は内側スクロールで対応する

曲一覧のグリッド／小節メモ一覧などの表形式コンテンツは、列や項目が窮屈になっても要素を圧縮しすぎず、必要であれば一覧領域の内側で横スクロールを許容する（ウィンドウ全体の崩れを防ぐことを優先する）。

## 9. コンポーネントの見た目ルール（抜粋）

| コンポーネント | ルール |
|---|---|
| ボタン | プライマリ＝塗り（accent）、セカンダリ＝枠線のみ、ゴースト＝枠なし透明。角丸はradius-sm |
| バッジ／タグ | ステータス色の淡色背景＋濃色文字（3.3節参照）。角丸はradius-sm、小さいドットアイコンを添えてよい |
| タブ／セグメントコントロール | 選択中はsurface背景＋薄い影1段のみ、非選択はsurface-2上に文字のみ |
| トグルスイッチ | OFF＝surface-3、ON＝accent。つまみは白円、影は最小限 |
| スライダー | トラックはsurface-3、塗り部分はaccent、ハンドルは白円＋accent枠 |
| ツールチップ | 濃色背景＋白文字、角丸radius-sm、影あり（フローティング要素のため8節の例外に該当） |
| アイコン | ストロークベースの線画アイコンで統一（塗りつぶし絵文字的な表現は使わない）。ツールバー内は15〜16px相当、太さは統一する。素材の調達方針は7.2節参照 |
| アバター類（将来ユーザー要素が必要になった場合） | グラデーションは使わず、単色背景＋イニシャル等のフラットな表現を基本とする |

## 10. アプリアイコン・ブランディング（新規確定）

Windowsのタスクバー／ウィンドウ／`.tabapp`ファイル関連付け（要件5.6「ファイル関連付け」）に使用するアプリアイコンについて、ヒアリングの結果、基本設計段階では以下の**方向性のみ**を確定する。具体的な図案の詳細デザイン（複数ラフ案の作成・選定）はPhase 1後半、他画面のビジュアルが固まった段階で別途行う。

| 観点 | 方針 |
|---|---|
| モチーフ | 波形／耳コピ作業を連想させる抽象的なモチーフ（具体的な音波形・耳のシルエット等の図案化はPhase 1後半に複数案を作成して選定する）。タブ譜の弦・数字を模した具象的なモチーフは採らない |
| 配色 | 3.2節のUIアクセントカラー（インディゴ系）と統一し、アプリ本体のUIと一貫した印象にする |
| スタイル | 6節「角丸・境界・影のルール」の基調（過剰な丸み・グラデーションを避ける）を踏襲したフラットな表現とする |
| 用途・解像度 | Windowsタスクバー／ウィンドウアイコン、`.tabapp`ファイル関連付けアイコンの用途ごとに、必要な解像度のICO/PNGを実装時に書き出す。用途追加（将来のiPhone版アプリアイコン等）にも同じモチーフ・配色を踏襲する |
| 検討時期 | 具体的な図案検討はPhase 1後半（実装時）に行う。本節で確定するのは「実装時に何をどう検討するか」の方向性のみ |

この決定は[[13_design_decision_points.md#4]]C7として登録する。

## 11. 今後の運用

- 実際のalphaTabレンダリング結果（譜面部分の配色）は本書のスコープ外であり、alphaTabのデフォルトテーマ設定や[[13_design_decision_points.md#2]]A2の調査結果と合わせてPhase 0〜1で確定する。
- 本書のトークン値は「方針確定」であり、実装時にOSのアクセシビリティ設定（コントラスト比等）を確認しながら微調整してよい。ただし命名・役割分担（何のためのトークンか）は変更せず、値のみを調整する運用とする。
- 新しい分岐点（例：将来のダークモード対応時の具体的なコントラスト調整）が見つかった場合は[[13_design_decision_points.md]]に追記する。
- アプリアイコンの具体的な図案検討（10節）、UIアイコンライブラリの最終選定（7.2節）も、確定した時点で本書を更新する。
