# 非機能設計書

対応要件：要件定義書5.1節（可用性・オフライン）、5.2節（パフォーマンス）、5.3節（キャパシティ）、5.5節（互換性）、8章リスク#3・#5

## 1. パフォーマンス目標と実現方式

| 目標値（要件5.2） | 実現方式 |
|---|---|
| 起動3秒以内 | ①曲一覧は`index.json`のみ読み込み表示（全曲パース不要、[[06_file_io_persistence.md#10]]）。②alphaTab/AlphaSynthの初期化は起動シーケンスに入れず、曲を開いた編集ウィンドウで非同期に行うので、曲一覧表示をブロックしない（2026-09-26 本人決定、[[05_playback_audio.md#9]]） |
| ノート入力反応100ms以内（**画面反映・発音の両方**） | 画面反映とシンセ反映を分離（[[05_playback_audio.md#3.2]]）。コマンド実行はメモリ内Scoreモデルへの同期的な小さい差分更新のみで、I/Oを伴わない（自動保存は非同期デバウンス）。**要件5.2の「タップから音／画面反映まで100ms以内」は両方に掛かるため、上限は片方ずつ100msとし、内訳（画面に何ms・音に何ms）は定めない**。画面反映は体感速度に直結するため先に実行し、シンセ側は同じ入力イベントの処理内でAlphaSynthへノートオンを発行して、入力から発音までを100msの内側に収める。SoundFontは曲を開いた時点で常駐している（3節）ため、この経路にロード待ちは入らない。この目標に対する再描画戦略の妥当性は[[13_design_decision_points.md#2]]A8として検証待ち |
| 描画30fps以上 | **2026-09-10 是正**：当初は「alphaTabのCanvas/SVGレンダリングの仮想化（画面外小節を描画しない）に依存」としていたが、**B30（2026-09-07、パッケージ1実装時）で `core.enableLazyLoading: false`（描画チャンクを即時に全反映）を全体確定しており、画面外描画の抑制は現在**働いていない**。したがって 30fps の実現は (1) フォーカスビューで表示範囲を数小節に絞ること（`ScoreRenderHost.applyViewMode` の `startBar`／`barCount`、旧詳細設計 `view-modes.md` §3.1（`2759936` 時点））にのみ依存し、(2) 全体スクロールビュー・スコア表示の大曲時とズーム操作中の fps は[[13_design_decision_points.md#2]]A9 のフォールバック（簡易描画レイヤー、または専用ワーカースクリプト同梱による非同期描画への復帰）が前提となる。負荷テスト（2節）で未達なら A9 のフォールバックを実装する。B30 の背景は旧詳細設計 `web-core-foundation.md` §6（`2759936` 時点） |
| 再生開始200ms以内 | [[05_playback_audio.md#9]]参照 |
| 自動保存デバウンス | [[06_file_io_persistence.md#5]]数秒間隔でまとめて保存 |
| 100小節超での維持 | 2節「大曲対応設計」参照 |

## 2. 大曲（最大2048小節）対応設計（要件5.3、リスク#5）

| 課題 | 対策 |
|---|---|
| 全小節を一度にDOM/Canvasへ描画するとfps低下 | フォーカスビューでは編集対象周辺のみをレンダリング対象にする（**2026-09-10 是正**：当初併記していた「alphaTabのレイアウト仮想化」は B30 の `enableLazyLoading: false` により現在無効。1節参照）。全体スクロールビューの描画方式は当初「サムネイル的な簡易描画（詳細記譜を省略した縮小表示）を検討する」という`⚠要検証`のままだったが、**2026-09-02、[[13_design_decision_points.md#2]]A9として正式に検証待ち事項へ編入し、詳細設計（旧詳細設計 `view-modes.md` §3.1（`2759936` 時点））で暫定方針（alphaTabネイティブ描画をそのまま採用し、簡易描画レイヤーは実装しない。fps未達時のみフォールバックとして追加実装）を確定した** |
| Undo履歴のメモリ増大 | 各コマンドは原則として差分（パッチ）のみ保持し、Scoreモデル全体のスナップショットを都度複製しない。ただし`RemovePartCommand`（[[04_editing_core.md#8.2]]の唯一の例外）は復元のためパート全体を保持する例外があり、これが「セッション内無制限」というUndo/Redo保持要件と組み合わさるとメモリを圧迫しうる問題が2026-09-03のレビューで指摘された（[[../review/design_review_2026-09-03.md]]B-2）。是正として、`CommandHistory`インスタンス（＝編集ウィンドウ）あたり80MBのメモリ予算・直近200件の下限保証・最古エントリからのエビクションという方式へ改訂した（[[13_design_decision_points.md#4]]C11、[[04_editing_core.md#8.2]]） |
| 自動保存のシリアライズコスト | 曲全体を毎回シリアライズするのではなく、変更のあったBar/Part単位の差分シリアライズを検討する（⚠要検証：実装時にJSONシリアライズの実測コストを確認し、全体シリアライズで許容範囲なら簡潔さを優先して差分化は見送る。[[13_design_decision_points.md#2]]A6） |
| 曲一覧のサムネイル生成コスト | 冒頭数小節のみをレンダリング対象とし、曲全体をレンダリングしない（[[06_file_io_persistence.md#10]]） |

**負荷テスト計画**：Phase 1後半（要件9章のPhase 1作業パッケージ表に明記の通り）に、2048小節・全奏法記号を含む開発用サンプルデータ（9章「開発用サンプルデータ」パッケージ）を、想定利用の4パートと上限の8パートの2つ用意する。上記目標値と3節のメモリ目標値は4パートのデータで満たすことを実測で確かめ、8パートのデータでは落ちずに動くことを確かめて測った値を記録する（8パートでは目標値を超えても不合格にしない。要件4.2の想定利用3から4パートと要件5.3の上限8は別の観点の数字であるため、2026-09-28 本人決定）。詳細は[[11_test_strategy.md]]。この負荷テストで[[13_design_decision_points.md#2]]のA6・A8・A9をまとめて検証する。

## 3. メモリ使用量目標との対応（要件5.5、リスク#3）

| 目標 | 対応方針 |
|---|---|
| アイドル時150MB以内 | **1ウィンドウあたり**の目標値（アイドル時は、曲を開いていない曲一覧ウィンドウ1枚の状態を指す）。曲を開いていない状態（曲一覧のみ）ではalphaTab/AlphaSynthの重量級リソース（SoundFontデータ等）を遅延ロードし、メモリに載せない。**本節の3つの目標値はいずれも1ウィンドウあたりの目安値であり、複数ウィンドウを同時に開いた場合はウィンドウ数に比例して増加する**（要件5.5）。印刷とPDFの生成のあいだだけ作る見えない`BrowserWindow`（[[01_architecture.md#6]]）は、編集ウィンドウの目標値に含めず別に数え、その目標値はPhase 0から1の実測の後に決める（2026-09-27 本人決定。印刷用の譜面を編集ウィンドウのメモリに載せないために分けたため） |
| 通常編集時400MB以内 | **1編集ウィンドウ（＝1曲）あたり**の目標値。1曲分のScoreモデル＋レンダリングキャッシュ＋SoundFontを常駐させる想定。Electronのレンダラープロセスを曲ごとに分離する（複数ウィンドウ＝複数レンダラープロセス）ため、同時に開く曲数に比例してメモリは増える点をユーザー（本人）に注記する。**2026-09-03追記**：この「1ウィンドウあたり」という粒度がPC版メモリ使用量の目標として本節に明記されていなかった点をレビューで指摘され（[[../review/design_review_2026-09-03.md]]A-5）、明記した（[[13_design_decision_points.md#4]]) |
| 大曲(2048小節)編集時600MB以内 | **1編集ウィンドウあたり**の目標値。2節の描画の対策（フォーカスビューは編集対象の周辺だけを描き、全体スクロールビューはalphaTabのネイティブ描画で、fps未達のときだけ簡易描画を足す）と差分Undo方針を前提とする。`CommandHistory`のUndo/Redo履歴自体は上記の80MB予算により編集ウィンドウあたりの上限が明確化されているため、本目標値との突き合わせもしやすくなった。Phase 0〜1で実測し、超過時は「開いていない小節のBeat/Note詳細データを遅延デシリアライズする」等の追加対策を検討する（⚠要検証） |

## 4. 互換性（要件5.5）

| 項目 | 方針 |
|---|---|
| 対応Windowsバージョン | **規則＝リリース時点の最新から1〜2世代前まで**（要件5.5）。**2026年時点でこれを当てはめると Windows 10 以降**（要件5.5が例として挙げているのと同じ値）。Electronのサポート範囲と食い違う場合は**狭いほうを採る**（下記4.2節） |
| 対応iOSバージョン（Phase 3） | **規則＝リリース時点の最新から1〜2世代前まで**（要件5.5）。**2026年時点でこれを当てはめると iOS 17 以降**（要件5.5の例と同じ値）。Expo SDKのサポート範囲と食い違う場合は**狭いほうを採る**（下記4.2節）。着手時に当てはめ直す |
| 高解像度ディスプレイ | Electron標準挙動に依存し特別対応なし（要件どおり） |
| データスキーマ変更 | [[02_data_model.md#4.2]]のマイグレーション方針に準拠 |
| ローカライズ（**2026-09-10追加**、[[../detailed_design/00_reference.md#8.1]] G59） | **日本語のみ対応**（要件5.5）。i18n層（メッセージカタログ・言語切替）は設けず、UI文言・エラーメッセージ（[[08_error_logging.md#1.2]]のメッセージテンプレート）は日本語を直接記述してよい。将来多言語化する場合の受け皿は、**文言がテンプレートとして1箇所に集約されていること**（エラーメッセージは`ErrorCodeRegistry`のテンプレート、画面文言は各画面コンポーネント）であり、これ以上の先行投資はしない。数値・日付の書式もOSロケールに追従させず日本語表記で固定する |
| アクセシビリティ（**2026-09-10追加**） | VoiceOver等のスクリーンリーダー対応は**不要**（要件5.5、個人利用のため）。ただし[[14_visual_design_system.md#11]]のとおり、配色のコントラスト比は実装時に確認して微調整してよい（読みやすさの確保はスクリーンリーダー対応とは別の話であり、要件の「不要」判定と矛盾しない） |

## 4.1 オフライン動作（要件5.1）

要件5.1は「通信なしで完全動作すること」を**必須**としている。v1 のアプリは**ネットワークI/Oを行う実装を持たない**ことでこれを満たす。根拠は次の3点で、いずれも他章で確定済みの設計である。

| 通信が発生しうる箇所 | v1 での扱い | 出どころ |
|---|---|---|
| 譜面エンジン・音源の読み込み | alphaTab本体とSoundFontはアプリにローカル同梱し、外部CDNからは読み込まない | [[01_architecture.md#3]]「SoundFontはローカル同梱（要件5.1：外部CDN禁止）」 |
| 曲データの保存・読み込み | アプリは常にローカルファイルI/Oのみを行い、クラウドAPIには触れない。iCloud Drive／Google Drive を選んでいる場合の同期はOS側の同期クライアントの責務で、同期が止まっていてもアプリの読み書きは成立する | [[06_file_io_persistence.md#1]] |
| 自動更新チェック | `UpdateCheckAdapter` は現状ダミー実装で、実際のHTTP問い合わせを行わない。将来実装した場合も、問い合わせの失敗を無視して起動・編集・再生を続けられること（更新チェックを必須経路に置かないこと）を条件とする | [[10_extensibility_future.md#1]] |

**検証**：Phase 1 の受け入れ確認で、ネットワークアダプタを無効にした状態から起動し、曲の新規作成・編集・保存・再生・エクスポート・印刷プレビューまでを一通り通せることを確かめる（[[11_test_strategy.md#6.1]]）。

## 4.2 対応OSバージョンの決め方（要件5.5、2026-09 追記）

4節の表の「対応Windowsバージョン」「対応iOSバージョン」は、**固定値ではなく規則として持つ。** 要件5.5は「対応Windowsバージョン | 最新の1〜2世代前まで（例：Windows 10以降）」、「対応iOSバージョン | 最新の1〜2世代前まで（例：iOS 17以降）」と書いており、**規則は「最新の1〜2世代前まで」のほう、`Windows 10以降`・`iOS 17以降` は例**である。本書は当初この例のほうを規則として書いていたため、時間が経つと必ずずれる状態になっていた。次の形に改める。

| | 内容 |
|---|---|
| 規則 | リリース時点でOSベンダーが出している最新バージョンから、**1〜2世代前まで**を対象とする（要件5.5） |
| いまの当てはめ | **2026年時点では Windows 10 以降 / iOS 17 以降**。これは規則を当てはめた結果の値であって、規則そのものではない |
| 当てはめ直す時期 | 各Phaseの着手時と、リリースを切るとき。そのつどこの行の値を更新する |
| 実行環境のサポート範囲との関係 | Electron（PC版）・Expo SDK（iPhone版）がサポートするOSの範囲と、上の規則が食い違うことがある。**そのときは狭いほうを採る。** 実行環境が切ったOSでは動かせず、規則が切ったOSは対象外と決めているため、どちらか一方でも外れたら対象外になる |

**この表の値を書き換えるときは、規則の行ではなく「いまの当てはめ」の行だけを書き換える。**

## 5. スケーラビリティ上限のまとめ（要件5.3、再掲）

上限値そのものは[[02_data_model.md#4.3]]に一元化し、本書では「上限に近づいた際のUX」を扱う。**2026-09-02修正**：曲数とタグ数で閾値の性質が異なるため、以下の通り区別する（画面群・ナビゲーション完了後のセルフレビューで発見・是正、[[13_design_decision_points.md#3]]B20参照）。

- **曲数**：上限1000の90%（900件）に到達した時点でWarningレベル（`SONG-001`、[[08_error_logging.md#1]]）を表示し、上限到達前にユーザーが気づけるようにする（曲の新規作成自体は1000件に達するまで継続可能な予告的警告）。**2026-09-03追記**：1000件到達時点の挙動が未定義だったレビュー指摘（[[../review/design_review_2026-09-03.md]]A-3）を受け、他のハードキャップと同様にErrorレベル（`SONG-002`）で新規作成を拒否することを確定した（[[13_design_decision_points.md#4]]C12、旧詳細設計 `screens-navigation.md` §3.5（`2759936` 時点））。
- **タグ数**：50件という上限自体が新規作成をブロックするハードキャップであるため、90%地点での予告Warningは設けず、上限到達時にErrorレベル（`TAG-001`）で作成を拒否する（旧詳細設計 `screens-navigation.md` §3.5（`2759936` 時点））。
