# 非機能設計書

対応要件：要件定義書5.2節（パフォーマンス）、5.3節（キャパシティ）、5.5節（互換性）、8章リスク#3・#5

## 1. パフォーマンス目標と実現方式

| 目標値（要件5.2） | 実現方式 |
|---|---|
| 起動3秒以内 | ①曲一覧は`index.json`のみ読み込み表示（全曲パース不要、[[06_file_io_persistence.md#7]]）。②alphaTab/AlphaSynthの初期化は起動シーケンスの後段・非同期で行い、曲一覧表示をブロックしない（[[05_playback_audio.md#9]]） |
| ノート入力反応100ms以内 | 画面反映とシンセ反映を分離（[[05_playback_audio.md#3.2]]）。コマンド実行はメモリ内Scoreモデルへの同期的な小さい差分更新のみで、I/Oを伴わない（自動保存は非同期デバウンス）。この目標に対する再描画戦略の妥当性は[[13_design_decision_points.md#2]]A8として検証待ち |
| 描画30fps以上 | alphaTabのCanvas/SVGレンダリングの仮想化（画面外小節を描画しない）に依存。フォーカスビューでは表示範囲を数小節に絞ることで描画負荷を本質的に下げる（要件4.1のフォーカスビューはUXだけでなく性能対策も兼ねる）。全体スクロールビュー・スコア表示の描画方式は[[13_design_decision_points.md#2]]A9、詳細は[[../detailed_design/view-modes.md#3.1]]参照 |
| 再生開始200ms以内 | [[05_playback_audio.md#9]]参照 |
| 自動保存デバウンス | [[06_file_io_persistence.md#2]]数秒間隔でまとめて保存 |
| 100小節超での維持 | 2節「大曲対応設計」参照 |

## 2. 大曲（最大2048小節）対応設計（要件5.3、リスク#5）

| 課題 | 対策 |
|---|---|
| 全小節を一度にDOM/Canvasへ描画するとfps低下 | alphaTabのレイアウト仮想化に加え、フォーカスビューでは編集対象周辺のみをレンダリング対象にする。全体スクロールビューの描画方式は当初「サムネイル的な簡易描画（詳細記譜を省略した縮小表示）を検討する」という`⚠要検証`のままだったが、**2026-09-02、[[13_design_decision_points.md#2]]A9として正式に検証待ち事項へ編入し、詳細設計（[[../detailed_design/view-modes.md#3.1]]）で暫定方針（alphaTabネイティブ描画をそのまま採用し、簡易描画レイヤーは実装しない。fps未達時のみフォールバックとして追加実装）を確定した** |
| Undo履歴のメモリ増大 | 各コマンドは原則として差分（パッチ）のみ保持し、Scoreモデル全体のスナップショットを都度複製しない。ただし`RemovePartCommand`等の一部コマンドは復元のためパート全体を保持する例外があり、これが「セッション内無制限」というUndo/Redo保持要件と組み合わさるとメモリを圧迫しうる問題が2026-09-03のレビューで指摘された（[[../review/design_review_2026-09-03.md]]B-2）。是正として、`CommandHistory`インスタンス（＝編集ウィンドウ）あたり80MBのメモリ予算・直近200件の下限保証・最古エントリからのエビクションという方式へ改訂した（[[13_design_decision_points.md#4]]C11、[[04_editing_core.md#8.2]]） |
| 自動保存のシリアライズコスト | 曲全体を毎回シリアライズするのではなく、変更のあったBar/Part単位の差分シリアライズを検討する（⚠要検証：実装時にJSONシリアライズの実測コストを確認し、全体シリアライズで許容範囲なら簡潔さを優先して差分化は見送る。[[13_design_decision_points.md#2]]A6） |
| 曲一覧のサムネイル生成コスト | 冒頭数小節のみをレンダリング対象とし、曲全体をレンダリングしない（[[06_file_io_persistence.md#7]]） |

**負荷テスト計画**：Phase 1後半（要件9章のPhase 1作業パッケージ表に明記の通り）に、2048小節・8パート・全奏法記号を含む開発用サンプルデータ（9章「開発用サンプルデータ」パッケージ）を用いて上記目標値を実測する。詳細は[[11_test_strategy.md]]。この負荷テストで[[13_design_decision_points.md#2]]のA6・A8・A9をまとめて検証する。

## 3. メモリ使用量目標との対応（要件5.5、リスク#3）

| 目標 | 対応方針 |
|---|---|
| アイドル時150MB以内 | 曲を開いていない状態（曲一覧のみ）ではalphaTab/AlphaSynthの重量級リソース（SoundFontデータ等）を遅延ロードし、メモリに載せない |
| 通常編集時400MB以内 | **1編集ウィンドウ（＝1曲）あたり**の目標値。1曲分のScoreモデル＋レンダリングキャッシュ＋SoundFontを常駐させる想定。Electronのレンダラープロセスを曲ごとに分離する（複数ウィンドウ＝複数レンダラープロセス）ため、同時に開く曲数に比例してメモリは増える点をユーザー（本人）に注記する。**2026-09-03追記**：この「1ウィンドウあたり」という粒度がPC版メモリ使用量の目標として本節に明記されていなかった点をレビューで指摘され（[[../review/design_review_2026-09-03.md]]A-5）、明記した（[[13_design_decision_points.md#4]]) |
| 大曲(2048小節)編集時600MB以内 | **1編集ウィンドウあたり**の目標値。2節の仮想化・差分Undo方針を前提とする。`CommandHistory`のUndo/Redo履歴自体は上記の80MB予算により編集ウィンドウあたりの上限が明確化されているため、本目標値との突き合わせもしやすくなった。Phase 0〜1で実測し、超過時は「開いていない小節のBeat/Note詳細データを遅延デシリアライズする」等の追加対策を検討する（⚠要検証） |

## 5. スケーラビリティ上限のまとめ（要件5.3、再掲）

上限値そのものは[[02_data_model.md#4.3]]に一元化し、本書では「上限に近づいた際のUX」を扱う。**2026-09-02修正**：曲数とタグ数で閾値の性質が異なるため、以下の通り区別する（画面群・ナビゲーション完了後のセルフレビューで発見・是正、[[13_design_decision_points.md#3]]B20参照）。

- **曲数**：上限1000の90%（900件）に到達した時点でWarningレベル（`SONG-001`、[[08_error_logging.md#1]]）を表示し、上限到達前にユーザーが気づけるようにする（曲の新規作成自体は1000件に達するまで継続可能な予告的警告）。**2026-09-03追記**：1000件到達時点の挙動が未定義だったレビュー指摘（[[../review/design_review_2026-09-03.md]]A-3）を受け、他のハードキャップと同様にErrorレベル（`SONG-002`）で新規作成を拒否することを確定した（[[13_design_decision_points.md#4]]C12、[[../detailed_design/screens-navigation.md#3.5]]）。
- **タグ数**：50件という上限自体が新規作成をブロックするハードキャップであるため、90%地点での予告Warningは設けず、上限到達時にErrorレベル（`TAG-001`）で作成を拒否する（[[../detailed_design/screens-navigation.md#3.5]]）。
