## 2. 背景（なぜこのパッケージが必要になったか）

パッケージ1〜8 はいずれも自動ゲート（typecheck / lint / test / build）とパッケージ単位のセルフレビューを通してマージされた。にもかかわらず、パッケージ8 完成後に実UIを起動して確認したところ、以下が判明した。

| 観測された状態 | 直接の原因 | 構造的な原因 |
|---|---|---|
| 15 画面のカードアクション・パネル・再生ボタン・ショートカットが無反応 | ハンドラが `() => undefined` のまま実サービスへ結線されていない | 「シェル段階だから非ブロッキング」という重大度の割引（[quality.rule.md](../../.claude/rules/quality.rule.md) Q3／Q8） |
| 15 画面が[[../basic_design/14_visual_design_system.md]]未到達、二重メニューバー等の構造破綻 | B36 のシェル方針で最小 inline style に留めた分が未回収（G25） | 同上 |
| 編集ウィンドウが白画面（`66e60a7` で是正済み） | `ScoreRenderHost.initialize()` より前に `ViewModeController` が `applyViewMode` を呼び throw | renderer bootstrap が構造的に無試験だった |
| 設計に同型の欠落が 3 件（`SetTempoCommand`＝G2、拍子変更＝BL-1、リピート＝BL-2） | 要件4.1 の記譜要素に対する順方向レビューしか行っていなかった | 最初の欠落（G2）を直したとき、**同じクラスを機械的に防ぐ手段を足さなかった**（Q5） |
| 設計書間のリンクが 75 本切れていた | 参照元からの相対パスではなくファイル名のみで書いていた | 人手の監査でしか検出できず、書いた本人には気づけない（Q1／F2） |
| 詳細設計書が責務レベルの散文に留まる（G1） | as-built のシグネチャが[[00_reference.md#3]]にしか存在しない | 「設計どおりに実装できているか」を検証する土台が無いまま 5 パッケージ積み上がった（Q7） |
| DoD 基準5（実UI手動シナリオ）が全パッケージで未実施 | 実UIがパッケージ8まで存在しなかった | 同種の繰り越しが 7 パッケージ連続したが、実施順序を見直さなかった（Q4） |

したがって本パッケージは「数件のバグ修正」ではなく、**設計から順にやり直して製品水準へ到達させる**位置づけとする（本人決定 2026-09-09：「このアプリの前提は製品」）。品質の基準そのものは [quality.rule.md](../../.claude/rules/quality.rule.md) を最上位とする。

## 3. サブ機能の構成とゴール

各サブ機能は着手前にゴール（識別子・達成状態・検証手段・範囲外・再発防止）を確定してから開始する（運用は [goal.md](../../.claude/commands/goal.md)）。本節が各ゴールの**正**であり、[phase1-productization.md](../../.claude/docs/phase1-productization.md)（`.claude` 側）はセッション運用の索引としてここを参照する。

```
D1 設計監査の是正・G1解消        ─┐
D2 画面/ビジュアル設計の製品水準化 ─┴─▶ 設計ゲート（sdlc-design-review PASS）
I1 機能の全結線                  ─┐
I2 見た目の14章到達               ─┴─▶ 実装ゲート（sdlc-impl-review PASS）
F  実アプリ P1〜P7 通し確認        ───▶ パッケージ完了（§8）
```

実装は機能（I1）→ 見た目（I2）の順。設計（D1・D2）は UI/UX まで含む。

## 4. D1：設計是正

作業指示書は[[../review/design_audit_2026-09-10.md]] §8。本節には**設計そのものの変更**（他書へ反映すべき新規の設計内容）だけを置き、リンク修正・節番号統一のような衛生作業は指示書側のチェックリストで追跡する。

### 4.1 記譜要素に対する編集経路の補完（BL-1／BL-2）

要件4.1 が挙げる記譜要素のうち、**曲途中の拍子変更**と**繰り返し記号**は、[[../basic_design/01_architecture.md#3]] AD-2（Score への変更はすべてコマンド経由）に反してコマンドが存在しなかった。`SetTempoCommand` 欠落（G2）と同型の見落としが計 3 回起きている。

追加するコマンドの仕様は[[editing-core.md#6.4]]に定義し、as-built を[[00_reference.md#3.4]]へ登録する。設計判断は[[../basic_design/13_design_decision_points.md#3]] B38（拍子変更）・B39（リピート）として記録する。

### 4.2 記譜要素 ↔ コマンド ↔ テスト の双方向対応表

BL-1／BL-2 は「設計にあるものが実装されたか」（順方向）のレビューでは検出できず、「要件にあるものが設計に存在するか」（逆方向）を見て初めて分かった。同型の見落としを 3 回起こしているため、**逆方向の検算を成果物として固定する**。

対応表は[[../basic_design/12_traceability.md]]の実装フェーズ対応版として維持する（MJ-A4 の是正と同時に行う）。要件4.1 の記譜要素・データモデルの変更可能フィールドは、それぞれ「対応するコマンド」または「明示的に編集不可である旨」と、対応するテスト ID を持たなければならない。空欄を残さないことが検証条件になる。

### 4.3 G1 の埋め戻し方針

[[00_reference.md#3]] の as-built を**正**とし、各詳細設計書へメソッドシグネチャ（引数・返り値・例外時の挙動）・型定義・状態遷移を書き戻す。乖離が見つかった場合は as-built に合わせる（DoD 基準2）。対象と参照節は[[../review/design_audit_2026-09-10.md]] §5 の表に従う。

埋め戻し後、同じ事実が 2 箇所（詳細設計書と `00_reference.md` §3）に並ぶことになるため、**詳細設計書本体を正、`00_reference.md` §3 は横断索引**と位置づけを明示する（Q2 単一の真実源）。

## 8. Definition of Done（完了判定）

[[../basic_design/15_development_process.md#7]] の DoD 6 基準に加え、本パッケージは**Phase 1 完了の定義そのもの**を兼ねるため、以下すべてを満たした時点で完了とする。

| # | 判定条件 | 検証 |
|---|---|---|
| 1 | 自動ゲートが緑 | `pnpm typecheck` / `lint` / `test` / `build` / `format` |
| 2 | 品質ゲートが緑 | `pnpm check:quality`（`check:docs` = 0、`check:stubs` = 0） |
| 3 | G-D1〜G-D2 達成、設計ゲート通過 | `sdlc-design-review` PASS、`/audit-consistency` 再実行で新規 Blocking・Major 0 |
| 4 | G-I1〜G-I2 達成、実装ゲート通過 | `sdlc-impl-review` PASS、`/audit-fidelity` の未結線リストが空 |
| 5 | G-F 達成 | [[screens-navigation.md#9]] §9.0.1 の P1〜P7 が全行 PASS（本人が実アプリで実施） |
| 6 | 未解消ギャップに無責任な繰り越しが無い | [[00_reference.md#8.1]] の各未解消行に、解消を担う作業単位と判定条件が書かれている |
| 7 | 是正ごとに再発防止が入っている | 本書 §3 各ゴールの「再発防止」欄がすべて実施済み、または実施できない理由が書かれている |
