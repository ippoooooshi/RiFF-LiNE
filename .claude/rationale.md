# なぜこのゲートが在るか

> v22 までの `failures.md`（65KB・F1〜F70）を、**1 ゲート 1 行**に畳んだもの。
> 元の記録は repo 外に退避してある。ここは「外すとどうなるか」を思い出すための表で、
> 読み物ではない。**ゲートを外す判断をする前に、その行だけ読むこと。**

## 中心の考え方

| | |
|---|---|
| 観測できる事実 | ゲートが毎回 `git` と実行結果から自分で取る。state を読まない |
| 観測できない意思 | `state.mjs` 経由でしか書けない。書いた事実が `journal.jsonl` に残る |
| 到達点 | 「物理的にごまかせない」は作れない。**ごまかしても得がない／明示的な操作が要る／抜けたら痕跡が残る** の3つ |

## 決定: 破壊的コマンドは「綴りの列挙」で止めない（2026-09-14）

`settings.json` に `Bash(rm -rf /*)` のような前置き一致を並べる方式をやめ、
`hooks/gate.mjs` が**削除先のパスを解決して**判定する方式に置き換えた。

### 列挙をやめた理由

`Bash(rm -rf /*)` は「`rm -rf /` で始まる」という前置き一致なので、`rm -fr /` は当たらない。
当たらないと `Bash(rm *)`（ask）に落ちて、**人が「はい」を押せる状態**になる。

| コマンド | 破壊力 | 旧方式での扱い |
|---|---|---|
| `rm -rf /` | 最大 | deny（ブロック） |
| `rm -fr /` | 同じ | ask（押せる） |
| `rm --recursive --force /` | 同じ | ask（押せる） |

**同じ破壊力のものが、書き方だけで扱いが変わっていた。** 守っているように見えるのが害で、
リストを読んだ人は「危険コマンドは塞いである」と受け取る。狭めれば外れやすくなり、
広げて `Bash(rm -rf *)` にすると `rm -rf node_modules` が死ぬ。**列挙という方式が用途に合っていない。**

### 置き換えた方式

`gate.mjs` の `destructiveVerdict()` が、削除系コマンドの引数を絶対パスに解決して比べる。

| 行き先 | 判定 | なぜ |
|---|---|---|
| プロジェクトの中 | 通す | git が戻せる |
| OS の一時ディレクトリ | 通す | 作業の後片付けを止めない |
| その外 | 確認（ask） | 意図した操作かもしれないが、黙って通す場所ではない |
| ルート・ドライブ直下・ホームそのもの | 拒否 | 正当な用途が無い |

書き方に依存しないので `rm -fr /` も `rm --recursive /` も同じ扱いになる。
副作用として、設定ファイルに破壊的コマンドの文字列が並ばなくなり、
**配布 zip がウイルス対策ソフトに誤検出される問題も消えた**（それが動機ではないが、同時に解決した）。

## 未決: OS 破壊系の拒否リスト（2026-09-14）

`settings.json` の `deny` にある、ディスク初期化・レジストリ削除・電源操作・低水準消去・
ルート配下の再帰削除を止める行。**残すか外すかが未決。** 判断する人のために材料を置く。

### きっかけ

配布 zip がウイルス対策ソフトに検出された。**この行が機械学習判定を引いたのではないか**と
推測して一度削除したが、**実際にどのファイルが検出されたかを確認しないまま消していた**ので戻した。
`.json` はスクリプトとして走査されないことが多く、より疑わしいのは `.mjs` のほう
（`smoke.mjs` は攻撃コマンドに見える文字列をテストの入力データとして持っている）。
**検出名とファイル名を確認してから決めること。**

### 外す側の論拠

- `rm` は `Bash(rm *)` が `ask` に在るので、書き方に関わらず全部そこで止まる
- パターン列挙で防げるのは「書き方を変えない実行」だけ。`node -e` から fs の削除 API を呼べば素通りする
- ディスク初期化・レジストリ削除・電源操作は、この種のアプリ開発で Claude が通る経路が無い

### 残す側の論拠

- **`deny` と `ask` は強さが違う。** `ask` は人が「はい」を押せば通るが、`deny` は押せない。
  疲れているときの 1 クリックを防ぐ価値はゼロではない
- 不完全な防御は、無価値な防御ではない。多層で薄く重ねるのは普通の考え方
- **外す理由が「検査ツールに嫌われたから」なのが筋として悪い。**
  機能ではなく外部の都合で安全側の設定を削るのは、後から見て理由が読めない変更になる

### 決め方

1. ウイルス対策ソフトの履歴で**検出名とファイル名**を見る
2. `.json` でなければ、この行は無関係。**触らない**
3. `.json` だったときに初めて、上の論拠を比べて決める。決めたらこの節を「決定」に書き換える

**このリストは「AI に文書で伝える」では代替できない。** 書いて守られるなら、
そもそもこの `.claude` 一式が要らない。文書は判断の記録であって、強制の手段ではない。

## 踏んだ罠 2: 検査治具が環境に依存していた（2026-09-14）

Windows 実機で smoke が 3 件赤になった。**3 件とも治具（`smoke.mjs`）側の前提ズレ**で、
製品コードの不具合ではなかった。開発側（Linux）では緑だったので気付けなかった。

| 症状 | 原因 | 直し方 |
|---|---|---|
| private が internal にならない | 偽プロジェクトが一時ディレクトリに在り、`typescript` を解決できず正規表現へ落ちていた。フォールバックはクラス名で修飾せず private も見ない | 解決先に**道具自身の置き場所**を足した。あわせて**抽出モード自体を検査対象に**した（フォールバックだと以降の検査が空振りの緑になるため） |
| `import しても CLI を実行しない` が赤 | 治具が Windows の絶対パスを `import()` に渡していた。ESM ローダは `file://` を要求する | `pathToFileURL` を通す |
| 一時ディレクトリの削除で確認が出る | Windows で `/tmp` は OS の一時ディレクトリではない。`C:\tmp` に解決されていた | POSIX 表記の `/tmp` を一時ディレクトリとして扱う（`..` を畳んでから判定） |

**教訓が 2 つ。**
1 つめは、**検査が空振りで緑になる経路を塞ぐこと。** 抽出がフォールバックに落ちると
「private を internal にする」検査は常に緑になるが、production でも効いていない。
だからモードそのものを検査する。
2 つめは、**開発環境だけで緑にしても意味がない。** `PORTING.md` が
「検査は必ず実際に使う OS でも一度走らせること」と書いているのは、まさにこれ。

## 踏んだ罠 3: 2 つの検査が違う粒度を見ていた（2026-09-14）

テストの ID は 2 通りの書き方で付いていた。どちらも採番簿どおりで正しい。

- (a) テストごと … `it('…', () => { // UT-PLAY-SVC-07 §4.6.2「…」`
- (b) ファイル冒頭に 1 行 … `// UT-EDIT-HIST: CommandHistory（元に戻す／やり直し）`

網羅台帳の抽出は (a) しか見ていなかった。(b) だけのファイルは全テストが ID なしになり、
`idPrefix` の絞り込みに掛からず、**どの段にも入らないまま消えた**。
実測でテストファイル 86 本のうち 33 本・`it(` 239 個が分母の外にいた。

気付けなかった理由は、もう片方の検査 `check-tests.mjs` が
「ファイルが予約プレフィックスの ID を**最低 1 つ**持つこと」しか見ないことにある。
(b) のファイルはその条件を満たすので 0 件で通る。
**2 つの検査が違う粒度を見ていたので、どちらも緑だった。**
`dd->it` と `impl->ut` の「未判定 0」は、239 件を最初から数えていない状態で出ていた。

一般化すると次のようになる。

- **同じものを見ている 2 つの検査は、見ている粒度を突き合わせること。**
  片方が「ファイル単位」、もう片方が「テスト単位」だと、間の抜けは両方とも緑で通る。
- **絞り込みは、落とした分を必ず数えること。** `filter` は「入れる」仕掛けに見えるが、
  実体は「落とす」仕掛けでもある。落ちた件数がどこにも出ない絞り込みは、静かな分母の穴になる。
  v23 では `orphan-tests` を足して「抽出はされたが、どの段にも属さなかったテスト」を赤にした。
- **推測で埋めない。** 冒頭の族が 2 つあるファイルは、どちらのものか決められない。
  片方へ寄せると寄せた段の件数だけが静かに増えるので、寄せずに穴として出す。
  同じ理由で、族を継いだテストに番号（`UT-EDIT-HIST-01`）は**振らない**。
  採番簿に無い ID を台帳に載せると、そこから先の照合が全部嘘になる。

## 踏んだ罠 4: 「指摘 0 件」に達した直後が一番危ない（2026-09-14）

検証キー方式（読んだ箇所のキーを書かせて照合する）で全段が「指摘 0 件」に到達した。
その直後に全行を人が読み合わせたところ、**25 件出た**。
キーは書く側が選ぶので、見落としているものは原理的にキーにならない。
自己申告の検査は、精度が上がったのではなく、申告の作り方が上手くなっただけのことがある。

だから v23 は「読んだか」を聞かない。**機械が全行を列挙し、間引きは理由つきの判定として残す。**
`0 件` を見たときに最初にすべきなのは、喜ぶことではなく**分母を数え直すこと**。

## 踏んだ罠 5: 検査が「数合わせ」を正解として教えていた（2026-09-15）

台帳の分解は、機械が「この行は最低 N 件に分かれるはず」と下限を出し、
AI がその件数以上の要求を書く、という形だった。機械が見ていたのは 3 つだけ:

- 件数が下限以上か / 完全一致の重複が無いか / 書いた文が原文の語を使っているか

**中身が原文のどこから来たのかを、誰も見ていなかった。**

実機の要件定義書で実際に回して確かめた結果:

| やったこと | 結果 |
|---|---|
| 正直に分解する（下限より少ない件数） | **5 件中 5 件が弾かれた** |
| 数合わせをする（言い換えで件数を埋める） | **5 件中 5 件が通った** |

日付の行（`- **作成日**：2026-08-27（初版）／同日 改訂`）にも下限 2 が出る。要求は 0 件なのに
0 件とは言えないので、架空の要求 2 件を書かされ、それが「判定済 2」として台帳に載った。

**弾かれた側は書き直す。書き直す方向は必ず「通る方」。**
サボりを検出するために作った仕掛けが、サボりの作法を教えていた。

### 直し方 — 件数ではなく、原文の覆いで見る

要求ごとに**原文のどこから読み取ったか**を逐語で書かせる（`from`）。

- 出どころは原文の**部分文字列でなければならない**（捏造できない）
- 出どころ同士は**重なれない**（言い換えを並べると取り合いで落ちる。**ここが水増しの本体**）
- **どこにも割り当てられなかった区間は列挙して返す**（飛ばしたことが見える）
- 要求でない部分は `{"skip": …, "why": …}` で外す（理由は原文の語を含むこと）
- 行全体が要求でないなら、行全体を 1 つの skip にする＝**要求ゼロ**。件数の下限は免除し、
  **その単位数を `pending` と `stats` に常に表示する**

下限（`minReq`）は「区切り記号の数 + 1」なので、**区切りで切れば必ず満たせる**。
意味が「要求の数の下限」から「**原文のうち説明すべき断片の数の下限**」へ変わり、
要求として書くか理由つきで外すかは選べるが、**黙って無視することはできない**。

同じ直し方を上の階層では既にやっていた（`--coverage`＝分割が文書の全行を覆っているか）。
**行に対してやっていたことを、行の中身に対してもやる**というだけで、新しい理屈は入っていない。

### 正直に書いておく限界

**水増しが不可能になったわけではない。** 原文を漏れなく覆う形で細かく切れば、
日付の行からでも 3 件の「要求」を作れる（実際に通ることを確認した）。
変わったのは 2 点:

1. **書ける件数が原文の長さで決まる**（AI の裁量では増やせない）
2. **台帳に出どころが残るので、中身が薄いことが読めば分かる**
   （要求「作成日を記録すること」／出どころ「`- **作成日**：`」）

完全に塞げてはいない。**見えるところまでしか行っていない**ことを承知で使うこと。

## 実地で確かめたこと（2026-09-15）

要件定義書 §4.1（53〜84 行・28 単位）を、新しい形式で**全件分解した**。
この節は本人が手で数えて「28 行に 61 件の要求」と出した唯一の基準点。

| | 件数 |
|---|---|
| 本人の手数え | 61 |
| 旧版の下限（機械が出す数字） | 81 |
| **新形式で実際に書けた要求** | **74**（＋ skip 4） |

28 単位すべてが通った。**通らなかったのは初回の 1 件だけ**で、原因は道具側の偽陽性
（カタカナ複合語の部分一致が漏れていた）。直してから 28/28。

74 と 61 の差は、奏法記号の 1 行
（`チョーキング／スライド／…／タッピング・スラップ・ポップ`）を 12 件に分けたぶん。
**12 件は実際に 12 の奏法**で、手数えのときに畳んでいたと思われる。
新形式では 1 件ずつ原文の別々の断片に紐付いているので、**どれがどこから来たか後から辿れる**。

分かったこと 3 つ:

- **下限（76）と、正直に書けた数（74 要求 + 4 skip = 78）はほぼ一致した。**
  外すべき断片を外せるようになった時点で、下限は無理のない数字になる。
- **表の見出しセル（`| フレット入力 |`）は、右のセルの要求の出どころに含めれば足りる。**
  1 行ごとに skip を書く必要は無い。
- **skip が必要だったのは 4 件だけ**（変更日の注記・旧仕様の記録・章参照・確定先の注記）。
  要求でない断片は、思ったより少ない。

## 踏んだ罠 6: 検査する仕組みが在るのに、呼ぶ側が無かった（2026-09-15）

`.claude/workflows/coverage.js`（台帳を回す本体）と `audit.js`（レビューの本体）は、
Claude Code の Workflow ツールでしか走らないため直接は検査できない。
そのために `scripts/lib/workflow-sim.mjs`（偽のエージェントでワークフローを走らせる）が
置いてあり、冒頭にこう書いてある。

> 使い方（selftest から）:
>   const { runWorkflow } = await import('./lib/workflow-sim.mjs')

**その selftest は v23 で smoke に置き換えられ、smoke からは一度も呼んでいなかった。**
つまり v23 のあいだ、台帳とレビューを回す本体は**まったく検査されていなかった**。
2026-09-15 に分解の書式を変えたときも、シミュレータは古い書式のまま壊れていて、
誰も気付かなかった。

`check-legacy.mjs` は「消したファイルが残っていないか」を見る。
ここで起きたのはその逆——**残すべきものは残っているのに、呼ぶ側だけが消えていた**。
ファイルの有無では検出できない。

一般化:

- **置き換え（selftest → smoke）では、消える側が持っていた呼び出しを数え直すこと。**
  ファイルを移すことと、呼び出しを移すことは別の作業。
- **「検査する仕組みが在る」は「検査されている」ではない。**
  在ることの確認（ファイルの存在）と、効いていることの確認（壊すと赤になる）は別物。
  v23 の逆対照はまさにそのために在るのに、ワークフローだけ対象外になっていた。
- 対策として smoke からシミュレータを呼び、**偽のエージェントが本物と同じ書式で
  書き戻すこと自体も検査対象にした**。書式が食い違うと「分解が書き戻される」が赤になる。

## 踏んだ罠 7: 「入れたもののハッシュ」では当て漏れを検出できない（2026-09-15）

差分配布を手で組み立てていて、**変更したファイルを 1 つ入れ忘れた**（`hooks/gate.mjs`）。
しかも配布時に「**前回ぶんも含めた一式**」と宣言したので、受け取った側は全部入っていると
信じて当てた。結果、新しい `smoke.mjs` が古い `gate.mjs` を検査して 2 件落ち、
「足した機能が自分のテストで落ちている」という誤った像を作った。

配布物にはハッシュを付けていた。**入れたファイルのハッシュを。**

```
c4457830b01830fd  split.mjs
dc724c4d947ee80d  ledger.mjs
…                             ← gate.mjs はここに載っていない
```

**入れ忘れたファイルは、照合リストにも載らない。** 9 個並べて「全部一致」を確認しても、
10 個目が抜けていることは原理的に分からない。**照合の相手が間違っていた。**

一般化:

- **「作ったものの一覧」で完全性は確かめられない。** 欠けているものは一覧にも欠けている。
  確かめられるのは「**在るべきもの全部の一覧**」と突き合わせたときだけ。
  これは台帳の「分母を先に固定する」とまったく同じ話で、配布にも同じ理屈が要った。
- **自分が組み立てたものを、自分の宣言で保証しない。**
  「一式です」は検証されない主張で、`claims.mjs` が本文の主張に要求しているのと
  同じ水準の裏取りが、配布物そのものには無かった。

対策:

1. `.claude/MANIFEST.sha256` に**道具一式 52 ファイル全部**のハッシュを置く
   （`project.json` と `rules/{typescript,electron,ui,layer}.md` は
   project.json 自身が「持っていくときは書き換える」と宣言しているので対象外。
   `baseline.json` は機械が書く記録なので対象外）
2. `check-version.mjs` が自分の `.claude` を照合し、**違うファイルを名前で出す**
3. **`smoke.mjs` の 1 番目の検査にする。** ここが赤のときは以降すべて
   「新しい検査 × 古い実装」なので、結果を信用してはいけない
4. 配布は差分をやめ、**一式で渡す**。当て漏れが構造的に起きない形にする

### 誤検知は誤検知として直す

初版は機械が書く `baseline.json` を「旧版の残骸かもしれません」と報告していた。
**当たっていない警告は、警告そのものを無視する癖をつける。**
新しい検査を足したら、まず「当たらないところで鳴らないこと」を確かめる。

## 踏んだ罠 8: 出力ゼロで落ちる検査は、赤 1 件より質が悪い（2026-09-15）

実機（Windows・リポジトリは OneDrive 配下）で `smoke.mjs` が
**出力ゼロ・プロセスごと終了**した。`node --check` は通り、他のスクリプトは動き、
`check-version.mjs` は単体で正常終了する。`process.on('exit')` も発火しない。

`smoke.mjs` は**結果を最後にまとめて出す**作りだった。途中で落ちると 0 バイト。
**どの検査で落ちたのかすら分からない。** 赤 1 件より切り分けが難しい。

### まず直したのは「見えないこと」のほう

原因の推測より先に、落ちたことが見える形にした。

1. **開始行を先に出す。** 0 バイトという状態を作らない
2. 主要な区切りに印を置き、**正常経路を通らずに終わったら直前の印を出す**
   （`process.on('exit')` は同期処理しか走れないので、出すのは数行だけ）

```
smoke 開始（node v24.13.0 / win32）

**smoke が結果を出す前に終了しました（exit 127）。**
  最後に通過したところ: 偽プロジェクトの作成（setup）
  ここまでに済んだ検査: 2 件（うち赤 1 件）
```

### 原因の推測を、確認前に記録しない

最初、`cpSync('.claude', temp, { recursive: true })`（検査のために本物の `.claude` を
丸ごと複製していた箇所）を原因と**断定して**この節に書いた。**外れていた。**
その処理を消しても同じ症状が出た。

確認していないものを「原因」として記録すると、次にここを読む者が誤った前提から始める。
**推測は推測として書くか、確認できるまで書かない。**

なお `cpSync` の削除自体は正しい変更として残してある。確かめたかったのは
「除外リストに載っているファイルを `extra` に数えないか」だけで、そのために
本物を複製する必要は無かった（最小の偽 `.claude` を 3 ファイル作れば足りる）。
**検査は確かめたいものだけを作る。** 手近な本物を使うと、検査が環境差を踏む面積が広がる。

### 限界

`process.on('exit')` はネイティブレベルの強制終了では発火しない。
そこまで行くと開始行だけが手がかりになる。
**Windows では標準出力をファイルへ向けると非同期になり、強制終了時に失われる**ので、
切り分けのときは端末にそのまま出すこと。

## 決定: 「そもそも要求か」は別の Claude に問う（2026-09-15）

### きっかけ

新形式で 10 単位を試しに分解したところ、30 件の「要求」のうち **8〜9 件が
ラベル・目的・枠組み**だった。たとえば:

| 出どころ | 書かれた「要求」 |
|---|---|
| `（PC版）` | 「（PC版）を対象とした利用シーンである」 |
| `…効率化するため` | 「耳コピ作業の効率化を目的とする」 |
| `ことを重視する` | 「…を重視する価値として位置づける」 |

**これらは形の検査を全部通る。** 出どころは逐語、区間は重ならず、取り残しも無く、
要求の文と出どころは語を共有している。機械が見ているのは**紐付けが嘘でないか**だけで、
**中身が要求かどうかは見ていない。** 意味を読まないと判定できないので、原理的に見えない。

### 原因は値段設定だった

`skip` は理由 15 文字、要求は本文 8 文字。**正直な道のほうが高い。**
安いほうに流れるのは当然で、これは作った側（＝こちら）の設計ミスである。

### なぜ Claude を足すことが循環にならないか

信用しない対象を、同じものに検査させている——ように見えるが、成り立つ理由は 1 つだけある。

**分解する側が水増しするのは、下限があるから。** 説明すべき断片が 5 つあるなら 5 件書かないと通らない。
**承認する側に下限は無い。** 1 件について 1 つ答えるだけで、何件通そうが何件落とそうが仕事は終わる。
掛かっている圧力が違うので、**間違え方が違う。** 重ならない誤りを二重に通すことだけが根拠である。

**承認する側に件数の目標を与えた時点で、この根拠は消える。**
`agents/approver.md` に「落とすこと自体を目的にしない。件数の目標は無い」と書いてあるのはそのため。

### 構造の無い敵対レビューにしない

自由に批評させると悪化することは、このリポジトリに記録が残っている
（構造なしの相互批判で F1 0.495→0.457、構造ありの反論つきで 77%→87%）。なので:

- 答えは **3 つに固定**（`要求` / `要求でない` / `判断できない`）
- 「要求」と答えるときは **`expect`**（その要求が満たされたとき下位に現れるはずの一文）を必須にする。
  **感想ではなく作文を課す。** 「（PC版）を対象とした利用シーンである」を満たす設計書の一文は書けない
- 「要求でない」と答えるときは **7 種のどれか**を名指しさせる
- 「判断できない」には **何を確かめれば決着するか**を書かせる

### 落ちたものを消さない

承認が「要求でない」と言っても、断片は台帳に残る。「指摘」として記録され、
分解した側が**直す**か**反論する**かで決着する。

消さない理由は 1 つ。**承認する側が誤って「要求でない」と言ったとき黙って消すと、
網羅台帳が存在する理由そのもの——落ちが無いこと——が壊れる。**
落ちるより残るほうが安全な側に倒している。

反論にも `expect` を課す。**そうしないと反論が無料になり、指摘を全部撥ねて終わりにできる。**
反論で通した件数は `approval-report` に別枠で出る。

### 直すほうを安くする

**指摘に従って直した分は、承認を引き継ぐ**（同じ断片を対象外へ移した場合）。
引き継がないと、10 件のうち 1 件を直すたびに残り 9 件を承認し直すことになり、
**「指摘に従う」が一番高くつく。** そうなると承認を通す最短経路が「反論して押し切る」になる。
**そこだけは絶対に逆にしない。**

逆向き（「要求である」と言われて対象外から要求へ移した）は引き継がない。
承認する側は「その断片は要求だ」と言っただけで、**新しく書かれた要求文は見ていない。**

### 覗きは止めずに数える

承認は「下位に無ければ不備か」を**上位だけを見て**答える作業である。
下位を開くと「下位に書いてあるから要求だ」という逆立ちした判断になり、
**下位に無いものだけが「要求でない」に落ちる**——つまり漏れを漏れでなくする。
分解で下位を見せない理由とまったく同じで、ここが一番効く。

機械で完全には防げないので、**`expect` が下位の文書と逐語一致したら記録して数える。**
止めないのは、偶然の一致があり得るのと、**当たっていない検査で止めると警告そのものを
無視する癖がつく**（罠 7 で書いたのと同じ理由）から。件数が多ければ、その承認は当てにならない。

### 既定では完了を止めない

`requireApproval: true` を書いた段だけが止まる。理由は順番の問題で、
**承認がどのくらい当たるかを測る前に全段を止めると、当たっていない検査で作業が止まる。**
まず全件に回して当たり方を測り、それから止める側に倒す。

### 測るための仕掛け

「非要求は語尾で見分けられる（要求は `〜すること`、非要求は `〜である`）」という仮説がある。
本当なら、承認を全件に回さずに済む。

ただしこれは 10 件見ただけの印象で、確かめていない。なので:

- 語尾の型は `approval-report` で**あとから**集計する
- **承認する側には一切渡さない**（渡すと仮説が答えを作ってしまい、測定にならない）

`endingVsVerdict` に差が出なければ語尾は使えない。**その場合は全件に回し続ける。**

### 正直に書いておく限界

- 承認する側が下位を覗くことを、機械では止められていない。**数えるところまで。**
- 反論を押し通すことも止められていない。**別枠で数えるところまで。**
- 同じモデルが両方をやる以上、**同じ誤りを二重に通す可能性は残る。**
  圧力の違いに賭けているだけで、それが実際にどれだけ効くかは**まだ測っていない。**

## 踏んだ罠 9: 一覧系のコマンドだけ「0 件」を黙って返していた（2026-09-15）

承認を初めて回すときに `--file 04_editing`（基本設計の章名）を `req->bd` に渡した。
`req->bd` の上位は要件定義書 1 本なので 1 件も当たらない。返ってきたのは `count: 0` と空の配列だけで、
**「もう承認するものが無い」と読めた。**

`--file` / `--section` が当たるのは**上位側**の文書である。下位側の章名は当たらない。

情けないのは、**同じ型を既に 2 か所で塞いである**こと:

- `pending` は `単位 0` のとき「範囲の指定が実ファイルに当たっていないか、split / sync が未実行」と出す
- `gate.mjs` は `pend.units === 0` を Stop の理由にして「**0 件を「漏れなし」と読まないこと。**」と書く

**一覧系（`next` / `approve-next`）にだけ同じ検査が無かった。**
塞いだつもりの型が、別のコマンドに残っていた。罠 3（2 つの検査が違う粒度を見ていた）と同じ構図で、
「どこに入れたか」ではなく「**どの入口にも入っているか**」で見ないと抜ける。

直し方は `scopeWarning()` を 1 か所に置き、`next` と `approve-next` の両方から呼ぶ。
警告は payload にも標準エラーにも出す（payload の中だけだと本文に埋もれる）。
ワークフローは空振りを **`complete` にしない**——`status: 'partial'` にして `scopeWarning` を報告に載せる。
載せないと「承認 0 件 / complete」になり、**何も見ていないことが完了に見える。**

## 踏んだ罠 10: ツールを外した役に、コマンドを実行させていた（2026-09-15）

承認する側（`agents/approver.md`）から `Bash` を外した。下位の文書を開かせないためである。
ところがワークフローは、その役に `approve-show` で断片を取って `approve` で書き戻せと言っていた。

実機で回した結果、**判定は 20 件すべて出たのに、台帳には 1 件も入らなかった。**

```
Error: No such tool available: Bash. Bash is disabled for this session, in subagents as well as here.
```

しかも外し方が効いていなかった。Bash が無い状態で、承認する側は
**`Read` で `.claude/coverage/edges/req-bd.jsonl` を直接開いて**断片を特定していた。
`Read(.claude/coverage/**)` は deny に入っていない（Edit / Write だけ）。
つまり **Bash を外しても下位は開けたし、書き戻しだけが壊れた**——両方とも裏目である。

### 直し方 — 役を分ける

承認する側はファイルを触るツールを持たない。渡された断片だけを見て JSON で答える。
台帳の取得と書き戻しは**親（`workflows/approve.js`）が別のエージェントにやらせる。**
承認する側は**開きたくても開けない。**

`tools:` を空にするとサブエージェントは起動に失敗する（公式ドキュメントに明記）。
なので**ファイルを読めないツール 1 つ**（`TodoWrite`）だけを置いてある。
ここに `Read` / `Grep` / `Bash` を足すと前提が消えるので、smoke が `approver.md` の
`tools:` 行を読んで赤にする。

### ついでに直した「書けたことにする」型

書き戻しの成否を、実行したエージェントの自己申告で数えていた。
**次のラウンドの一覧に訊く形に変えた**——まだ未承認として出てくるなら書けていない。
自己申告を数えると、「書けた」と言っているが書けていない状態が失敗 0 件に見える。

### 自分の誤診も記録しておく

このとき、Workflow ツールの表示（`"args": "{\"edge\": …}"`）を見て
「args が JSON 文字列で渡っているから最初の取得で落ちる」と本人に伝えた。**これは誤りだった。**
実際には取得は成功しており（実在する entryId に対して判定が出ていた）、落ちていたのは書き戻しだけ。
表示の形を実行時の値だと決めつけた——**確かめていないことを断定した**という、
罠 8 で書いたのとまったく同じ型である。

（ただし「args が JSON 文字列だと 0 件 / complete で返る」こと自体は手元で再現できたので、
そちらは実在する穴として塞いだ。誤診と、誤診の過程で見つけた穴は別のもの。）

## 残っている既知の弱点

| | |
|---|---|
| `node -e` / `python -c` での書き込み | パターンでは塞ぎきれない。**言及があれば止める**ところまで。抜けても journal と git 差分に残る |
| `claims.mjs` の自然言語照合 | 英語の主張は素通りする。日本語も言い回しを網羅しきれない。`file:行「逐語」` の照合以外は**助言として扱う**こと |
| `--coverage` | 「全行が判定対象か対象外に振られている」を見るだけ。振り分けの妥当性は `--show-skipped` の目視 |
| 表のセル・リスト項目の文分割 | 段落と引用は「。」で割るが、表の 1 行・リストの 1 項目は割らない。1 セルに 3 文あっても 1 単位 |
| 環境依存の検査 | `typescript` が解決できない機材では抽出がフォールバックに落ちる。**赤で止まる**ようにはしたが、その機材では分母の質の検査が回らない |
| `--file` の範囲照合は上位段がコードのエッジだけ | `impl->ut` は `X.test.ts` ↔ `X.ts` の規約で照合できるが、上位が設計書のエッジ（`dd->impl` / `bd->dd`）は編集したファイルと設計書の対応がパスでは決まらない。**決められないものを決めたことにしない**方針で、そこは未照合のまま。噛み合いの検査（段のレベル）だけが効く |
| 分解の水増しは「不可能」ではない | 原文を細かく覆えば、要求でない行からも複数件を作れる。出どころが残るので**読めば分かる**が、機械は止めない。人の目か、後段のレビューで見る |
| 承認する側の「覗き」 | ファイル系のツールを外したので**このワークフロー経由では開けない**。ただし `tools:` を 1 行足せば開けるようになるので、smoke がその行を見ている |
| 承認の反論の押し通し | `expect` を課して有料にしたが、書けてしまえば通る。**別枠で数えるところまで** |
| 承認が同じモデルであること | 圧力（下限の有無）が違うので誤りは重ならない、という前提に賭けている。**実際にどれだけ効くかはまだ測っていない** |
| 逆対照で当てられない箇所 | `ts-api` の「関数内へ降りない」は構造で担保しているため、1 行の書き換えでは壊せない。テスト自体は旧実装で赤になることを手で確認済み |
