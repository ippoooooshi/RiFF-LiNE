# 実装

## 0. 実装も「詳細設計 → 実装」のブレイクダウンである

コードを書く前に、担当範囲の詳細設計が何を要求しているかを機械に固定させる。
設計書を読んで「だいたいこれを作ればいい」で始めると、要求の一部が落ちたまま
「実装できました」になる——落ちたことは書いた側からは見えない。

```bash
node .claude/scripts/ledger.mjs pending "<edge>" --file "<範囲>"   # 既定は dd->impl
```

未分解が残っていたら、**実装コードを開く前に**分解する（下位＝コードを見ずに、詳細設計の原文だけを見る）。

```bash
node .claude/scripts/ledger.mjs next "<edge>" --phase decompose --file "<範囲>"
```

要求には原文の逐語の出どころ（`from`）を添える。要求でない部分は理由つきで `skip` する。
同じ部分を 2 つの項目が指すことはできない。書式は `/trace` の `phase: "decompose"` 節を見ること。

未分解 0 になってから実装に入る。残ったままコードを編集したターンは Stop hook が終わらせない。

詳細設計書に書かれたとおりに実装する。設計を書き換えて辻褄を合わせない（PreToolUse が `docs/**` への書き込みを拒否する）。テストを書き換えて通さない（同じく `*.test.ts` を拒否する）。

## 先に読む

- 対象の `docs/detailed_design/<スラッグ>.md`（クラス構成・シグネチャ・シーケンス）
- `docs/detailed_design/00_reference.md` §3（他パッケージの現行シグネチャ）・§7（命名規約）・§8.1（既知ギャップ）
- 該当する `docs/basic_design/*`
- `.claude/rules/` の該当ファイル（触るファイルに応じて自動で適用される）

## 前提差分の確認

着手前に `git log --oneline -5` で `main` の更新を確認する。実行計画の前提（クラス名・シグネチャ）に影響するなら、**コードを書かずに停止して報告する**。

## 手順 — 未判定の要求を 1 件ずつ潰す

設計と違い、実装は**詳細設計の項目と関数がほぼ 1 対 1** で対応する。
まとめて書くと漏れるので、台帳の未判定を 1 件ずつ取り、その 1 件を実装してから次へ行く。

```bash
node .claude/scripts/ledger.mjs next "<edge>" 1 --phase judge --file "<範囲>"   # 未判定を 1 件取る
# → その 1 件が要求していることを実装する
node .claude/scripts/ledger.mjs judge "<edge>" "<reqId>" 一致 '<evidence JSON>'  # 実装した箇所を逐語引用
```

- evidence の `file` / `line` / `quote` は**実装したコードの実物**を指す。書き込む前に照合され、一致しなければ記録されない
- 実装できない・設計が矛盾している場合は `一致` にしない。`不一致` や `部分` で記録し、下の「設計と食い違ったとき」へ
- **1 件が `一致` になるまで次の件へ行かない。** まとめて実装してまとめて判定すると、この機構の意味が無くなる

全件が `一致`（または理由つきの `対象外`）になったら、まとめて仕上げる。

1. テストを追加する（実装後。L/XL サイズはサブ機能の区切りごと）。カバレッジは全メソッド C0/C1 100%、`11_test_strategy.md` §2 の対象ロジックは C2
2. `node .claude/scripts/verify.mjs` を実行し、すべて緑を確認する
3. リファクタリング。リファクタ後もすべて緑を確認する
4. 構造の増減があれば連動更新（`.claude/rules/docs.md`）
5. `node .claude/scripts/ledger.mjs pending "<edge>" --file "<範囲>"` で未判定 0 を確認する

**緑でない状態を「完了」と報告しない。** Stop hook が実際に検証を走らせるので、報告だけでは通らない。

## 設計と食い違ったとき

シグネチャどおりに実装できない、または設計が自己矛盾している場合：

- **論理矛盾で実装不可能** → 即停止。書きかけコードを `git stash` で退避し、「設計起因ブロック」として報告する
- **誤字・表記の不正確だが解釈が一意に定まる** → コードを保持したまま「軽微誤記」として報告し、設計書の修正を依頼する

実装過程でシグネチャから乖離した場合は、実装を設計に合わせるか設計の修正を依頼するかを**その場で**選ぶ。乖離を放置しない。

## バグ修正のとき

1. **再現するテストを先に書く**（この時点で赤になること）
2. 直す
3. テストが緑になることを確認する
4. **水平展開する** — 直したパターンをリポジトリ全体から検索し、全件に判定を付ける。
   ```bash
   node .claude/scripts/spread.mjs scan "<直した型の正規表現>"
   node .claude/scripts/spread.mjs next 1
   ```
   **`spread.mjs` を使うこと。** Stop hook が見るのはこれが書く記録だけで、`horizontal.mjs`（内部で呼ばれる検索本体）を直接叩いても記録は残らず、ターンは終われない。
   1 ファイルに絞った走査は拒否される——自分が直したファイルだけを数えても「他に同型は無い」とは言えないため
5. 未対応が残るなら G 番号を起こす（`/gap`。実在しない番号への繰越は拒否される）。防止手段を1つ足す（足せないなら `.claude/rationale.md` に理由を書く）

再現テストなしの「直しました」は受け付けない（この手順の必須項目。Stop hook はこれを機械判定しない——検証が緑かどうかだけを見る）。

## 出力（省略・N/A 代替不可）

1. 変更ファイル一覧
2. テスト件数の増減（UT / IT / 合計、実装前・後・増減）
3. テスト結果内訳（PASS / SKIP / FAIL）と SKIP 理由（件ごと）
4. 今回追加したテスト（名前と追加理由）
5. 水平展開の結果（検索パターン・ヒット件数・未対応件数）
6. `ledger.mjs pending` の出力（**自己申告ではなく台帳の実測**）
7. **確認していない事項**（あれば。無ければ「なし」）

報告に挙げたファイルは、`git diff --name-only` に実際に含まれているものだけを書く（Stop hook はこの突き合わせをまだ行わない。書いた側の責任）。

## 禁止

- `docs/**` の変更（要件・設計）
- `*.test.ts` の変更（新規追加は可、既存の書き換えは不可）
- `git commit` / `git push` / ブランチ操作（`git stash` は設計起因ブロックで退避するときのみ可。上の「設計と食い違ったとき」を参照）
- 不要コードのコメントアウト放置（物理削除する）
- 承認済みフェーズを超えた実装
