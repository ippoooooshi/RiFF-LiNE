# 機能追加要望

引数: `$ARGUMENTS`

開発中に最も頻度の高い要望の形。**そのまま要件に書き込まない。** 要件は V 字の最上位なので、曖昧さはそのまま設計・実装・テストの全段へ伝播し、実装まで降りてから「これどっちの意味？」になる。そこで直すと全段やり直しになる。

**「よく質問してから書く」は規約にすると必ず形骸化する。** だから未確定点が 1 つでも残っている限り書き込めないようにしてある。質問は機械が本文から作るので、何を聞くべきかを当てにいかない。

---

## 1. 下書きを開く

```bash
node .claude/scripts/req-add.mjs open "$ARGUMENTS"
```

機械が 4 種類だけを見る。どれも判定が割れないものに限ってある。

| 検出 | なぜ止めるか |
|---|---|
| 未閉鎖の列挙（「など」「等」「その他」） | 何が対象で何が対象外かが決まっていない |
| 未定義の程度（「適切に」「高速に」「必要に応じて」） | 満たしたかどうかを誰も確かめられない |
| 数値のない閾値（「上限」「以内」に数値が無い） | 実装も試験も値を決められない |
| 受入条件が無い（「〜できる」だけ） | テストが書けない |

## 2. 1 つずつ聞く

出た質問を**本人に聞く**。まとめて聞かない。1 つ答えが返ると次の輪郭が変わるので、順に聞く。質問の書き方は `.claude/rules/core.md` §2（ID を主語にしない／矛盾は逐語引用／選択肢には結果を書く）。

```bash
node .claude/scripts/req-add.mjs answer "<聞いたこと>" "<返ってきた答え>"
```

**記録した質問の数が、最初に出た未確定点の数を下回っていると commit できない。** 差分は推測で埋めた分だからで、要件の推測は下位の全段へ伝播する。

## 3. 既存要件との衝突を見る

新しい要件は単独では成立しても、既存と矛盾することがある。書き込む前に見る。

```bash
node .claude/scripts/spread.mjs scan "<新要件の主要な語>" --in "docs/**/*.md"
```

同じ話題を扱っている既存の要件・設計が出る。矛盾があれば**逐語で並べて本人に確認する**（推測で寄せない）。

## 4. 要件に書き込む

```bash
node .claude/scripts/req-add.mjs commit "<ID>" "<確定した要件文>" --section "<節番号>"
```

## 5. 降ろしきる

**ここからが本体。** 足しただけでは、その要求はどの台帳にも載っていない。

```bash
node .claude/scripts/split.mjs req            # 分母を作り直す
node .claude/scripts/ledger.mjs sync "req->bd"
node .claude/scripts/split.mjs drift          # 全段のズレが無くなったか
```

`drift` が赤のまま `docs/` を編集したターンは Stop hook が終わらせない。**増えた分が誰にも見えないまま完了になるのを防ぐため。**

そのあと、縦と横の両方へ降ろす。

```
req -> bd -> dd -> impl     縦（ブレイクダウン）
req -> accept               横（受入シナリオ）
bd  -> system / dd -> it / impl -> ut
```

各段は `/wp start` → `/wp design` → `/wp impl` の通常フローに乗せる。**横の段（テスト）を忘れない**——`edges` に定義されているので、`ledger stats` で未着手のまま残っていれば見える。

## 6. 担当する作業パッケージを決める

**要件が増えても、担当が決まらなければ宙に浮く。** 既存のどれかに入れるか、新しく起こすか。

```bash
node .claude/scripts/wp.mjs list                    # 既存の一覧と、着手できるもの
node .claude/scripts/wp.mjs add WP10 --name "<名前>" --done "<完了条件>" --after "<前提>"
```

新しく起こすなら、**完了条件はこの要件の受入条件から書ける**はずです（3 で絞り切っているので）。書けないなら絞り切れていません。

## 7. 影響を報告する

新機能は既存に触る。**触った範囲を件数で報告する。**

- 既存要件との矛盾: `/audit design` の結果
- 既存実装への影響: 変更したファイルと、その呼び出し元の件数
- 既存テストへの影響: 期待値が変わるテストの件数

影響が無いと**書く**のではなく、調べた範囲と件数を書く。「影響ありません」は根拠にならない。

---

## 使わない場面

- **不具合の修正** → 要件は変わらない。`/wp start` か、小さいなら adhoc 宣言（`node .claude/scripts/state.mjs adhoc "<理由>"`）。修正には水平展開が要る（`spread.mjs`）
- **既存要件の解釈が割れているだけ** → 要件を足すのではなく、矛盾を逐語引用して本人に確認する。新しい要件を足すと矛盾が 2 箇所から 3 箇所になる
- **後回しにしたい** → `/gap`。番号・担当作業単位・判定条件の 3 つが揃わないものは繰り越せない
