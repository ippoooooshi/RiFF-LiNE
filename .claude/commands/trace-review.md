# 上位 → 下位の全行読み合わせ（トレース検証）

> 権威: [`../rules/quality.rule.md`](../rules/quality.rule.md) Q1（主張は検証を伴う）・Q4（繰り越しには番号・責任・期限）・Q6（トレーサビリティは双方向で閉じる）。失敗の実例は [`../docs/quality.md`](../docs/quality.md) F1・F11・F12。

**上位ドキュメントを 1 行目から全行読み、各行に対応する下位ドキュメントの記述を探して「上位が生きたまま正しく下位へ降りているか」を判定する。** V 字の隣り合う 2 段のあいだで行う。

## 1. なぜこの形でなければならないか

過去に次の 2 つを試して、どちらも取りこぼした。

| 試した方法 | なぜ取りこぼすか |
|---|---|
| **章単位の対応表**（「要件4.1 → `04_editing_core.md`」） | 章が埋まっていれば通るので、**章の中の抜け**を 1 件も検出できない。要件4.1 の記譜要素に編集経路が無い状態（BL-1〜BL-6）を 6 回続けて見逃した |
| **項目単位の対応表＋検証キー**（下位の本文に literal で在るべき語を機械照合する） | **キーに選ばなかった中身が素通りする。** キーは書く側が選ぶため、「見落としているもの」は原理的にキーにならない。実際、この方法で「指摘 0 件」に到達した直後に全行読み合わせをやり直したところ、**25 件の不具合**が出た（うち過半はキー照合では原理的に出ないもの） |

したがって**照合の単位は「上位ドキュメントの行」であり、判定は意味で行う**。対応表・キー照合は、一度確かめた事実が後で壊れたことを知るための**回帰ネット**としてなら有用だが、検証そのものにはならない。

> 参考：検証キー方式の実装（`scripts/check-traceability.mjs` と `12_traceability.md` §7〜§11）は 2026-09-10 に破棄した。タグ `backup/traceability-tables-20260910` に退避してある。**同じものを作り直さないこと。**

## 2. 適用する段（隣り合う 2 段でのみ行う）

| 上位 | 下位 | 「対応する記述」とは |
|---|---|---|
| 要件定義書 | 基本設計 16 冊 | その要件を扱う節の本文（方式・数値・列挙・可否の確定） |
| 基本設計 | 詳細設計 10 冊 | クラス・シグネチャ・状態遷移まで降りた記述 |
| 詳細設計 | 実装 | 名指しされたクラス／関数／定数の**中身**（決めた値がその値になっているか） |
| 実装 | テスト | その振る舞いを名指しして検証しているテスト |

**2 段飛ばして見ない。** 要件を実装と直接突き合わせると、間の設計が抜けていること自体を見逃す。

## 3. 手順

1. **上位ドキュメントを 1 行目から順に読む。** 原文の順序で、飛ばさない。見出し・表の行・箇条書き・太字段落・注記・打ち消し線・変更履歴への参照、すべてが対象。**打ち消し線は「撤回された旧要件」であり、下位が旧要件のままでないかを見る材料**になる。
2. その行に対応する下位の記述を探す。無ければ「無い」が結論（それが不具合）。
3. **下位の本文を実際に開いて読み、上位の本文と意味で突き合わせる。** 目次・対応表・「〜に反映済み」という記述を根拠にしない（それ自体が検証対象）。
4. 判定する（§4）。
5. 不具合は**その場で 1 件ずつ起票**する（§5）。まとめて直そうとしない。
6. 全行読み終えてから、**上位に近い文書から順に**是正する（§6）。

長い作業なので、中断するときは「どの行まで読んだか」を残す。再開時に頭から読み直さない。

## 4. 判定

| 判定 | 意味 |
|---|---|
| `一致` | 上位が決めていること（方式・数値・列挙・可否）がすべて下位に在る。**下位が別の言葉で表現していてもよい**（意味が一致していれば一致） |
| `部分` | 一部だけ降りている。**上位の何が下位のどこにも無いか**を具体的に書く |
| `不一致` | 下位が上位と**違うこと**を決めている。両者の記述を引用して対比する |
| `陳腐化` | 上位が後から変更された（変更履歴・打ち消し線）のに下位が古いまま |
| `申し送り先が不在` | 下位 A が「これは下位 B で扱う」と書いているのに、B にその記述が無い |
| `対応先が誤り` | 対応表等が指す節に、その内容が実際には無い（別の節に在るならどこか） |
| `対象外` | 上位側が「不要」「スコープ外」「他 Phase 送り」と決めている。**理由を書く**（判定を省略した扱いにしない） |

## 5. 起票

- **1 件 1 行、その場で。** [`docs/detailed_design/00_reference.md`](../../docs/detailed_design/00_reference.md) §8.1 へ G 番号で追記する（Q4：番号・解消を担う作業単位・判定条件を必ず書く）。
- 起票には**上位の該当箇所と下位の該当箇所を両方**書く。「〜が無い」と書くときは、**無いことを確かめた方法**（grep した語と結果）も書く（Q1）。
- 「0 件だった」と書く前に必ず検索する。読んだ記憶で断定しない。

## 6. 是正の順序

**上位に近い文書から順繰りに直す。** 上流を直さずに下流を直すと、下流が「間違った上流」に合わせて固まる。

1. 上位側の記述に誤り・内部矛盾があるなら、まずそれをどう解釈したかを**決めて記録する**（分岐点カタログ [`13_design_decision_points.md`](../../docs/basic_design/13_design_decision_points.md) と [`12_traceability.md`](../../docs/basic_design/12_traceability.md)）。上位を黙って解釈して下位だけ直さない。
2. 下位に追記・確定する。
3. 連動更新を同じターンで行う（[`../rules/docs.rule.md`](../rules/docs.rule.md)「文書同時改訂の原則」）。エラーコードを足したなら統合表、クラスを足したなら登録簿、決定を足したなら分岐点カタログと進捗ログ。
4. 是正しきれず下流（詳細設計・実装・テスト）へ渡る分は、G 行の状態を「**上位は解消済み・下流は未**」と書き分け、担当する作業単位と判定条件を残す。

## 7. 探すべき不具合の型（過去に実際に出たもの）

読みながらこの 8 つを疑う。2026-09-10 の要件 → 基本設計の全行読み合わせで出た 25 件は、すべてこのいずれかだった。

| 型 | 兆候 | 実例 |
|---|---|---|
| **上位内の矛盾を下位が黙って解決している** | 上位の 2 箇所が違うことを言っており、下位は一方だけを採っている。どちらを採ったかの記録が無い | 要件4.1 のカポが「表示は運指のまま」と「表示・再生ピッチに反映」の両方を書いていた（G46） |
| **申し送り先に実体が無い** | 「〜は◯章で扱う」と書いてあるが、◯章にその語が 1 件も無い | 02章「実音変換は 05章で実装」→ 05章に「カポ」が 0 件（G43）、03章「複製は 06章のファイルコピー」→ 06章に記述なし（G53） |
| **まったく降りていない** | 上位が決めているのに、下位のどの文書にもその語が無い | 五線譜を併記しない／日本語のみ／コスト方針／アンインストール時の残置／脆弱性対応（G45・G59・G60・G63・G64） |
| **半分だけ降りている** | 上位が「A と B の両方」と書いているのに、下位に A しか無い | テンポ入力の「数値直接入力＋タップテンポ」の数値側（G44）、メトロノームの「入力時のクリック音＋カウントイン」の入力側（G48）、クラッシュ対応の「クラッシュ・フリーズ」のフリーズ側（G57） |
| **変更経路が無い** | 下位がフィールド・データ構造としては持っているが、それを変える手段が無い | パートの音色変更（G49）、弦本数の単独変更（G50）、および BL-1〜BL-6 |
| **決めるべき中身が未定義** | 名前・置き場所は書いてあるが、何をどうするかが書いていない | フレットボード図が何を表示するか（G55）、連符の入力方法（G42）、同梱プリセットの一覧（G47） |
| **技術前提が検証待ちに登録されていない** | 下位が「〜できる」と前提して設計しているが、それが可能かを誰も確かめていない | パンの実行時制御可否（G51 → A13） |
| **総覧の抜け** | 「〜のまとめ」「前提・非対象」を名乗る節に、その話題の決定が 1 つ載っていない | データ保護のまとめに暗号化の扱いが無い（G58）、非対象にスコープ外機能が無い（G40） |

## 8. やってはいけないこと

- 対応表・キー照合の結果をもって「検証した」と言う（§1）
- 目次・「〜に反映済み」という記述を根拠に一致と判定する（それ自体が検証対象。Q1）
- 見つけた不具合をまとめて起票する（1 件ずつ。粒度が粗いと解消判定ができない）
- 上流を直さずに下流だけ直す（§6）
- 「対象外」と書いて理由を書かない（判定の放棄になる）
- 全行読まずに「主要な項目を確認した」と報告する（章単位の対応表が失敗した理由がこれ）
