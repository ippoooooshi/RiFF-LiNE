# 移行の検証

`.claude` を新しいものに入れ替えた直後に 1 回だけ実行する。**掃除と、パースが実物と合っているかの突き合わせ**をやる。

**削除は必ず一覧を見せて承認を得てから行う。** 勝手に消さない。

---

## 1. 検査スクリプト自身の健全性

```bash
node .claude/scripts/smoke.mjs
```

**1 件でも落ちたら、ここで止めて報告する。** 以降の検査結果は信用できない。落ちたケース名と、そのケースが何の誤検知を防いでいるものかを報告すること。

## 2. 旧構成の残骸

```bash
node .claude/scripts/check-legacy.mjs
```

- 検出されたファイルの**一覧を本人に見せて、削除してよいか確認する**
- 承認が取れたら削除する。承認前に消さない
- `.gitignore` の不足分は追記する（`.claude/state/` `.claude/coverage/` `.claude/settings.local.json`）
- `.claude.old` / `scripts.old` が残っていれば、それも一覧に含めて確認する

新旧が同居していると、同じ規則が 2 箇所にある状態になる。1 つ読んだ時点で「読んだ」感覚が成立してしまい、**どちらが正かを誰も確かめなくなる**——これが今回の入れ替えで実際に起きたこと。

## 3. 現在地が読めているか

```bash
node .claude/scripts/status.mjs --no-verify
```

**セッション開始時にフックが注入した現在地と、この実行結果を突き合わせること。**

出力の 1 行目に `status.mjs:1a2b3c7` のような**版のスタンプ**が入る。まずこれを比べる。

| 状況 | 意味 |
|---|---|
| スタンプが一致し、中身も一致 | 正常 |
| スタンプが一致するのに中身が違う | セッション開始後に状況が変わった（注入はスナップショット） |
| スタンプが違う | 注入は**別の版**の出力。`.claude` を入れ替えた直後によく起きる |
| 注入テキストにスタンプが無い | **その注入は現在の `status.mjs` の出力ではない。** フック経路の不具合か、別のものを読んでいる |

食い違ったら、フックを直接叩いて決着させる。

```bash
echo "{}" | node .claude/hooks/gate.mjs session-start
```

これが `status.mjs --no-verify` と同じ内容を返すなら、フック自体は正常。返さないなら、その出力を丸ごと報告してください。

表示された未解消ギャップの件数と番号を、`docs/detailed_design/00_reference.md` §8.1 を**自分で開いて数えて**突き合わせる。合っていれば「一致（実測 N 件 / 台帳 N 件）」と書く。合っていなければ `project.json` の `gapLedger` を実際の表の書式に合わせる。

網羅台帳の行が `未初期化` / `未着手` と出るのは正常（まだ回していないため）。**`✓ 完了` と出ていたら逆に疑うこと。**

## 4. 採番簿のパース

```bash
node .claude/scripts/check-tests.mjs
```

冒頭に「採番簿として読み取ったもの」が全件出る。`docs/basic_design/11_test_strategy.md` §3.1 の実物と**1 件ずつ**突き合わせる。

**件数が合っているだけでは不十分。** 前回、実物 23 種に対しスクリプトは 25 種と読んでいた——書式説明のプレースホルダを 2 件拾っていたためで、正解より多いぶん健全に見えた。**中身を見て、実在しないプレフィックスが混ざっていないかを確認する。**

指摘が出た場合は、それが本当の未登録なのか、パースの誤りなのかを切り分けて報告する。

## 5. 残りのチェッカ

```bash
node .claude/scripts/check-docs-links.mjs
node .claude/scripts/check-stubs.mjs
```

件数と、検出内容が妥当かを見る。**誤検知だと思うものは「なぜ誤検知か」を根拠つきで挙げる。** 挙げたものは `smoke.mjs` に回帰ケースとして足す候補になる。

`check-docs-links` は「エラー」と「助言」を分けて出す。助言（同一ディレクトリのファイル名参照など）は**終了コードに影響しない**ので、エラー件数だけを是正対象として見ればよい。全件見たいときは `--show-advisories`。

**エラーが大量に出た場合、それが本当に是正対象かを先に疑うこと。** 過去に、1754 件のうち全件がスクリプト側の 2 つの不具合による誤検知だったことがある。数十件を超えたら、まず数件を実ファイルで確認してから全体の是正に入る。

`check-stubs` は「意図的な繰り越し」（`quality-allow-stub`）も別枠で出す。それぞれ `00_reference.md` §8.1 に G 行があるかを確認する。

## 6. 基準線の記録（**実作業に入る前に必須**）

```bash
node .claude/scripts/baseline.mjs status
```

既存の負債が何件あるかを出す。**この時点で赤なのは正常**（まだ基準線が無いので、既存の負債が全部「新規」に見えている）。

内容を本人に見せて、**これを「既知の負債」として認めてよいか確認する。** 認められないもの（いますぐ直すべきもの）があれば、それを先に直してから記録する。

```bash
node .claude/scripts/baseline.mjs record
```

記録すると、ゲートは「基準線より増えていないか」だけを見るようになる。**これをやらないと、既存の負債で毎ターン Stop hook に止められて実作業に入れない。**

記録した負債は `status.mjs` がセッション冒頭に件数を出すので、隠れることはない。ただし**解消計画（G 番号・担当作業単位・判定条件）は別途必要**なので、`00_reference.md` §8.1 に無いものは `/gap` で起票する。

## 7. 網羅台帳の初期化（任意）

```bash
node .claude/scripts/split.mjs --coverage        # 分割が全行を覆っているか（覆えない行は分母から消える）
node .claude/scripts/split.mjs --all
node .claude/scripts/ledger.mjs sync
node .claude/scripts/ledger.mjs stats
node .claude/scripts/ledger.mjs scope "bd->dd"     # 章ごとの未処理件数
```

ここは判定を回さない。**切り出しが妥当かを見るだけ。** 「推定要求数 ÷ 判定対象」が 1 に近ければ切り出しが粗すぎる可能性がある。「列挙が未閉鎖」の件数は、要件が未確定である箇所の候補。
