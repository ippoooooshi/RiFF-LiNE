# ゴール設定（作業単位ごと）

> 権威: [`../rules/quality.rule.md`](../rules/quality.rule.md)（特に Q1 主張は検証を伴う／Q4 繰り越しには番号・責任・期限／Q8 重大度を完成度で割り引かない）。
> 現在進行中のパッケージのゴール台帳は [`../docs/phase1-productization.md`](../docs/phase1-productization.md)。

**着手前に必ずゴールを置く。** 「やってみて、できたところまで」を成果と呼ばない。ゴールが無い作業は、どこまでやれば終わりかを実行者が都度決めることになり、結果として一番早く終わる基準（＝一番低い基準）に収束する。これが WP1〜8 で起きたこと。

## 適用範囲

パッケージ、サブ機能（D1 / D2 / I1 / I2 / F のような区切り）、および**1 セッションで着手するバッチ**のいずれにも置く。粒度が小さくても省略しない。

## ゴールの必須要素（5 つ揃って初めてゴール）

| # | 要素 | 悪い例 | 良い例 |
|---|---|---|---|
| 1 | **識別子** | （無し） | `G-D1` / `G-D1-b3`（バッチ 3） |
| 2 | **達成状態**（何が「在る」状態か。作業の列挙ではない） | 「リンクを直す」 | 「docs 配下の相互参照が、実在ファイル・実在節のみを指している」 |
| 3 | **検証手段**（誰が見ても同じ判定になるもの。可能な限りコマンド） | 「レビューして問題なければ」 | `pnpm check:docs` が 0 件 ＋ `/audit-consistency` の観点B 指摘 0 |
| 4 | **範囲外の明示**（このゴールでは達成しないこと＋その追跡先） | （書かない） | 「`]][[#N]]` 記法の統一は範囲外 → MN-B1、D1 バッチ4 で対応」 |
| 5 | **再発防止**（Q5。このゴールを達成したあと、同じ崩れ方をどう機械的に止めるか） | 「今後気をつける」 | 「`check-docs-links.mjs` に Markdown 相対リンク検証を追加し CI へ」 |

要素 3 に**コマンドを 1 つも書けないゴールは、ゴールの切り方が悪い**。分割するか、検証可能な代理指標（対象件数・チェックリストの充足）を定義してから着手する。

## 手順

1. **ゴールを書く**：上表の 5 要素を、対象の台帳（パッケージ／サブ機能なら `.claude/docs/<パッケージ>.md`、セッションバッチなら作業開始時の宣言）に書く。
2. **着手前に検証手段を空振りさせる**：`pnpm check:docs` 等を**先に実行して現在値を記録**する（例：75 件）。着手前の値が無いと「直った」の主張が検証できない（Q1）。
3. 作業する。
4. **検証手段を再実行し、実測値を記録する**。目標値に届かない場合、届かない項目を要素 4（範囲外）へ移すのではなく、**未達として明示**する。ゴールを後から下げない（Q8）。
5. **再発防止を入れたことを確認**してから完了と呼ぶ（Q5）。入れられない場合は理由を書く。

## 未達のときの扱い

- 未達項目は G 番号を起こして [`docs/detailed_design/00_reference.md`](../../docs/detailed_design/00_reference.md) §8.1 へ載せ、**解消を担う作業単位と判定条件**を書く（Q4）。
- 同じゴールが 2 回連続で未達なら、努力不足ではなく**ゴールの切り方か実施順序の誤り**として計画を見直す。

## 禁止事項

- ゴール未設定のまま着手すること
- 達成できなかった項目を、事後にゴールの範囲外へ移して「達成」と呼ぶこと
- 検証手段が「レビューで問題なし」だけのゴール（誰がやっても同じ判定にならない）
- 完了報告に、実際には実行していないコマンドの結果を書くこと（Q1）
