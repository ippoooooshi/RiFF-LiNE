# ギャップ起票

引数: `$ARGUMENTS`

## 起票の条件

「後で」を許すなら、**番号・担当・判定条件**をその場で書く。無期限・無責任の繰り越しは禁止。3つのうち1つでも書けないなら、それは繰り越しではなく**今やるべきこと**。

**担当作業単位は実在するものを書く。** `wp.mjs check` が台帳に無い担当を検出して赤にします（実在しない担当への繰り越しは、無期限の持ち越しと同じ）。担当するパッケージがまだ無いなら、先に起こしてください。

```bash
node .claude/scripts/wp.mjs list
node .claude/scripts/wp.mjs add <ID> --name "<名前>" --done "<完了条件>"
```

## 手順

1. `docs/detailed_design/00_reference.md` §8.1 を**全体検索**し、既存の最大番号と番号衝突を確認する（記憶で断定しない）
2. 次番号を採番し、§8.1 の表に1行追記する

   | # | ギャップ | 内容 | 担当作業単位 | 判定条件 | 状態 |
   |---|---|---|---|---|---|
   | G\<番号\>（\<発見日\>、\<発見契機\>） | \<一言サマリ\> | \<どの文書のどの記述が、どの文書のどの記述と食い違うか。両方を逐語引用する\> | \<解消を担う作業パッケージ／サブ機能\> | \<何が成り立てば解消と言えるか。できればコマンド\> | 未解消 |

3. 経緯の詳細が必要なら §9 に小節を追加する
4. 関連する設計書側にも、必要なら注記を**同じターンで**入れる

## 解消するとき

状態を「**解消済み（YYYY-MM-DD、対応作業単位）**」に書き換える。**行は削除しない。** 何が問題だったかの記録が消えると、同じ失敗を繰り返したときに気づけなくなる。

書き換える前に、**判定条件が実際に満たされていることを確認する**。「解消済み」と書いてから確認するのは順序が逆で、過去に「追記済み」と書いたが実体が無かった例がある。

## 1件ずつ

見つけた不具合をまとめて起票しない。粒度が粗いと解消判定ができない。

## ここに書かないもの

- **新たな設計判断を要するもの** → `docs/basic_design/13_design_decision_points.md` に分岐点として（カテゴリB＝工学判断／C＝ヒアリング確定）
- **技術前提が未検証のもの** → 同じく分岐点カタログのカテゴリA（検証待ち）へ。「〜できる」と前提して設計しているが誰も確かめていない事項は、ギャップではなく検証待ち

## 同種が続いたら

同じ種類の繰り越しが2つの作業単位で連続したら、繰り越しではなく**計画の誤り**として実施順序を見直す。実際、実 UI の手動確認を全パッケージが最終パッケージへ繰り越した結果、統合不全が終盤まで露見しなかった。
