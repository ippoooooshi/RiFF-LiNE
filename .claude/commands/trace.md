# 網羅台帳

引数: `$ARGUMENTS`

## なぜこの形なのか

「上位を1行目から全行読め」と指示する方式は、読んだことを検証できないので機能しなかった。対応表方式も検証キー方式も試して**両方すり抜けた**——キーは書く側が選ぶため、見落としているものは原理的にキーにならない。実際、検証キー方式で「指摘 0 件」に到達した直後に全行読み合わせをやり直したら不具合 25 件が出た。

そこで役割を分ける。

```
列挙  → 機械（間引かない。間引きは「対象外」という判定であり、記録に残す）
分解  → AI（上位だけを見る。下位は見せない）
検算  → 機械（分解件数が推定下限を下回ったら拒否）
承認  → 別の AI（**分解した本人ではない。** 断片ごとに「これは要求か」だけを答える）
判定  → AI（下位を実際に開いて、意味で突き合わせる）
集計  → 機械（未判定が残っている間は完了にできない）
```

**分解のとき下位を見せないこと**が、検証キー方式との決定的な違い。下位の欠落に影響されない。

**なぜ承認だけ別の AI なのか。** 機械の検算が見ているのは**形**（出どころが逐語か・区間が重なっていないか・
取り残しが無いか）で、これは嘘の紐付けを全部捕まえる。捕まえられないのは
「紐付けは正しいが、そもそも要求ではない」もの——`（PC版）` → 「（PC版）を対象とした利用シーンである」は
形として満点で、中身だけが間違っている。意味を読まないと判定できないので、機械には原理的に見えない。

循環していないのは、**掛かっている圧力が違う**から。分解する側が水増しするのは下限があるからで、
承認する側に下限は無い。何件通そうが何件落とそうが仕事は終わる。
重ならない誤りを二重に通すことだけが根拠であり、**承認する側に件数の目標を与えた時点でこの根拠は消える。**

## `init`

```bash
node .claude/scripts/split.mjs --all      # 構造単位へ分割し、要求数の下限を推定
node .claude/scripts/ledger.mjs sync      # 台帳の骨格を作る（既存の判定は保持）
```

`split` の出力で確認すること。

- **推定要求数 ÷ 判定対象** が 1 に近ければ、切り出しが粗すぎる可能性がある
- **列挙が未閉鎖**（「等」「など」）の件数 — これは**要件が未確定である箇所の候補**。決めるべき中身が書かれていないまま設計へ降りるとギャップになる
- **撤回マーク**（打ち消し線）の件数 — 下位が旧要件のままでないかを見る材料

## `status`

```bash
node .claude/scripts/ledger.mjs stats
```

状態は 5 つ。**`✓ 完了` 以外はすべて未完。**

| 表示 | 意味 |
|---|---|
| `! 未初期化` | `split.mjs` / `ledger sync` を回していない。台帳がまだ無い |
| `! 未着手` | 骨格はあるが、一度も分解していない |
| `  進行中` | 分解または判定が残っている |
| `! 承認待ち` | 分解は済んだが、承認が未解決（`requireApproval` を立てた段だけ） |
| `✓ 完了` | 分解も承認も判定も残っていない |

`承認 12/30` のような数字が横に出る。**`requireApproval` を立てていない段でも出る**——
出さないと「機構はあるが誰も見ていない」状態が緑のまま続くため。

「未判定 0」は完了を意味しない——**一度も分解していない台帳も未判定 0 になる。** 初版はここを区別せず、7 段すべてに `✓` を出していた。

## `run <edge> [範囲]`

`edge` は `req->bd` のような形式（`project.json` の `edges` に定義がある）。**既定は全件。** 試しに少しだけ回したいときだけ絞る。

```bash
node .claude/scripts/ledger.mjs scope "bd->dd"            # まず章ごとの未処理件数を見る

node .claude/scripts/ledger.mjs next "bd->dd"             # 全件（既定）
node .claude/scripts/ledger.mjs next "bd->dd" 30          # 先頭 30 件だけ
node .claude/scripts/ledger.mjs next "bd->dd" --file 04_editing_core
node .claude/scripts/ledger.mjs next "bd->dd" --section 4.1

node .claude/scripts/ledger.mjs next "bd->dd" --ids-only  # ID だけ（自動実行用）
node .claude/scripts/ledger.mjs show "bd->dd" "<id>"      # その 1 件だけ取り出す
```

承認だけを回したいときは `approve` を使う（分解した本人ではなく、別の役が答える）。

```bash
node .claude/scripts/ledger.mjs approve-next "bd->dd"            # まだ見ていない断片
node .claude/scripts/ledger.mjs approve-next "bd->dd" --ids-only
node .claude/scripts/ledger.mjs approve-show "bd->dd" "<entryId>"
node .claude/scripts/ledger.mjs approval-report "bd->dd"         # 当たり方の集計
```

**`--file` と `--section` が当たるのは上位側（`edge` の左）の文書です。** 下位側の章名を渡すと 1 件も当たりません。
当たらなかったときは `warning` が返ります——**`0 件` は「もう無い」ではなく「数えていない」ことがあります。**

`--ids-only` と `show` は**自動実行のためにあります。** 大量の本文をエージェント間で運ぶと、量が増えたときに欠落・改変が起きて「分母を機械が固定する」前提が崩れます。運ぶのは短い ID だけにし、中身は各自が `show` で取りに行きます。

返ってきた `phase` によって、やることが変わる。

### `phase: "decompose"`

**上位の原文だけを見る。下位のファイルを開かない。**

### 「要求」とは何か

> **下位の文書に書かれていなければ、不備といえること。**

この 1 行が判断の基準。これに当てはまらない断片は、**要求ではないので `skip` にする。**

| 要求でないもの | 例（実際に要求として書かれてしまった） |
|---|---|
| ラベル・項目名 | `（PC版）` → 「（PC版）を対象とした利用シーンである」 |
| 目的・ねらい | `…効率化するため` → 「耳コピ作業の効率化を目的とする」 |
| 枠組み・位置づけ | `ことを重視する` → 「…を重視する価値として位置づける」 |
| 経緯・旧方針 | `当初はiPhoneアプリ単体として構想したが` |
| 出典・参照 | `（3章・6章参照）` |
| 根拠・前提の説明 | `PCはOS標準で複数アプリの音声が同時に鳴らせるため` |
| プロジェクトの属性 | `アプリを個人開発する` |

**下限は「要求の数」ではなく「説明すべき断片の数」。**
要求として書けない断片は、無理に要求にせず `skip` で理由をつけて外す。
`skip` も下限に数えられるので、**要求を水増しして下限に届かせる必要はない。**

その単位が要求している事項を列挙する。**要求ごとに、原文のどの部分から読み取ったかを逐語で添える**（`from`）。
要求ではない部分は、理由をつけて外す（`skip`）。

```bash
node .claude/scripts/ledger.mjs decompose "req->bd" "<unitId>" '[
  {"text":"数値を直接入力してテンポを設定できる","from":"数値入力"},
  {"text":"タップしたリズムからテンポを設定できる","from":"タップ入力"},
  {"skip":"（4.3節参照）","why":"4.3節への参照表記であり、テンポ設定の要求そのものではない"}]'
```

**原文の同じ部分を 2 つの項目が指すことはできない。** 同じ内容を言い換えて件数を埋めようとすると、区間の取り合いで拒否される。
**原文のうち、どの項目にも割り当てられなかった部分は列挙されて返る。** そこに要求が書かれていないか確かめ、書かれていないなら `skip` で理由をつけて外す。

`section`（その行が属する章）が一緒に渡る。**章を見て、そもそも要求が書かれる場所かを判断すること。**
変更履歴・リスク一覧・未決事項・作業パッケージの見積もりの章に、下位へ降ろす要求は無い。

**この行が何も要求していないときは、原文全体を 1 つの `skip` にする。** 件数の下限は免除され、
「要求ゼロ」として記録される。件数を満たすために架空の要求を書かないこと——
**要求ゼロは正当な答えで、記録が残る。水増しは記録に残らない嘘になる。**

```bash
node .claude/scripts/ledger.mjs decompose "req->bd" "<unitId>" '[
  {"skip":"- **作成日**：2026-08-27（初版）／同日 改訂","why":"要件定義書の作成日と改訂の記録であり、基本設計への要求を含まない"}]'
```

### 承認 — その断片は、そもそも要求か

分解を書き終えたら、**別の役**が断片ごとに 1 つだけ答える。

> **この断片は、下位の文書に書かれていなければ不備といえるか。**

```bash
node .claude/scripts/ledger.mjs approve-next "req->bd"            # まだ見ていない断片の一覧
node .claude/scripts/ledger.mjs approve-show "req->bd" "<entryId>"  # 1 件だけ
```

答えは 3 つしかない。

| 答え | 必須のもの | 意味 |
|---|---|---|
| `要求` | `expect` | 下位に無ければ不備。**その要求が満たされたとき下位に現れるはずの一文**を書く |
| `要求でない` | `kind` | 上の表の 7 種のどれか |
| `判断できない` | `resolvesBy` | 断片が曖昧。何を確かめれば決着するか |

```bash
node .claude/scripts/ledger.mjs approve "req->bd" "<unitId>#0" 要求 \
  '{"why":"テンポの数値入力という手段を定めており下位に無ければ不備","expect":"setTempo は数値入力欄からの指定を受け付ける"}'
```

**`expect` が書けないなら、それは要求ではない。** 感想で通さないための仕掛けがここにある。
「重要な観点である」「考慮が必要である」は `expect` ではない。設計書にそのまま載る形の一文を書く。

**下位の文書を開かないこと。** 答えるのは「下位に無ければ不備か」であって「下位に書いてあるか」ではない。
下位を開くと、下位に書いてあるものが要求に見え、**下位に無いものだけが「要求でない」に落ちる**——
つまり**漏れているものを「もともと要求ではなかった」ことにしてしまう。**

ワークフロー（`approve`）で回す場合、これは指示ではなく**構造**になっている。
`agents/approver.md` はファイルを触るツールを持たず、台帳の取得と書き戻しは親がやる。
承認する側は**開きたくても開けない**（`tools:` に `Read` などを足すと前提が消えるので、smoke がその行を見ている）。

#### 食い違ったとき

**断片は消えない。** 「指摘」として記録され、次のどちらかで決着させる。

```bash
# A) 同意する（要求 → 同じ断片の対象外へ移す。承認はそのまま引き継ぐ）
node .claude/scripts/ledger.mjs concede "req->bd" "<unitId>#1"
# B) 反論して維持する
node .claude/scripts/ledger.mjs rebut "req->bd" "<unitId>#1" \
  '{"expect":"<下位に現れるはずの一文>","why":"<なぜ要求だと言えるか>"}'
```

**同意（`concede`）が一番安い経路になるようにしてある。** 手で分解を書き直すと、
指摘を受けていない断片を 1 文字でも変えた時点でその承認まで消える。
直すのが高いと、承認を通す最短経路が「反論して押し切る」になってしまう。**そこは逆にしない。**
（`concede` は区間を動かさないので、重なり・取り残し・下限の検査結果は変わらない。
理由は承認する側が挙げた `kind` から作られるが、`--why` で自分の言葉に差し替えられる。）

対象外にしたものを「要求である」と指摘された場合（逆向き）は `concede` できない。
**要求の文は分解した側が書くもの**なので、分解し直す。

消さないのは、承認する側が誤って「要求でない」と言ったときに黙って消すと、
**網羅台帳が存在する理由そのもの——落ちが無いこと——が壊れる**から。落ちるより残るほうが安全な側に倒している。

反論にも `expect` が要る。承認する側に課したのと同じ作文を、維持する側にも課す——
**そうしないと反論が無料になり、指摘を全部撥ねて終わりにできる。** 反論で通した件数は別枠で数えられる。

**指摘に従って直した分は、承認を引き継ぐ。** 直すたびに全部承認し直すなら、
直すことが一番高くつき、**最短経路が「反論して押し切る」になってしまう。** そこは逆にしない。

#### 完了を止めるかどうか

既定では**止めない**。止めるのは `project.json` の edge に `requireApproval: true` を書いた段だけ。
承認がどのくらい当たるかを測る前に全段を止めると、当たっていない検査で作業が止まる。
まず全件に回して当たり方を測り、それから止める側に倒す。

```bash
node .claude/scripts/ledger.mjs approval-report "req->bd"
```

語尾の型（`〜すること` / `〜である`）と判定の対照表が出る。
**語尾は承認する側に見せていない**ので、ここでの差は「語尾で先に絞り込めるか」の検証になる。
差が出ないなら語尾は使えない——その場合は全件に回し続ける。

### `phase: "judge"`

**下位を実際に開いて読む。** 目次や「〜に反映済み」という記述を根拠にしない（それ自体が検証対象）。

| 判定 | 意味 |
|---|---|
| `一致` | 上位が決めていることが下位に在る。別の言葉で書かれていてもよい |
| `部分` | 一部だけ降りている。**上位の何が下位のどこにも無いか**を具体的に書く |
| `不一致` | 下位が上位と**違うこと**を決めている。両者を引用して対比する |
| `陳腐化` | 上位が後から変更されたのに下位が古いまま |
| `申し送り先が不在` | 下位 A が「これは B で扱う」と書いているのに、B にその記述が無い |
| `対応先が誤り` | 対応表等が指す節に、その内容が実際には無い |
| `対象外` | 上位側が「不要」「スコープ外」「他 Phase 送り」と決めている。**理由が必須** |

```bash
node .claude/scripts/ledger.mjs judge "req->bd" "<unitId>#0" 一致 \
  '{"file":"docs/basic_design/05_playback_audio.md","line":142,"quote":"テンポは数値入力欄から直接指定できる"}'
```

`一致` 以外は、その場で `00_reference.md` §8.1 に **G 番号で1件ずつ起票する**（`/gap`）。まとめて直そうとしない。粒度が粗いと解消判定ができなくなる。

「〜が無い」と書くときは、**無いことを確かめた方法**（grep した語と結果件数）を evidence に含める。読んだ記憶で断定しない。

## 大量にあるとき

数百件を対話で回すのは現実的でない。均質で独立した判定なので、ここは並列実行が向いている。

```
Workflow({ name: 'coverage', args: 'bd->dd' })                             全件（既定）
Workflow({ name: 'coverage', args: { edge: 'bd->dd', limit: 30 } })        先頭 30 件だけ
Workflow({ name: 'coverage', args: { edge: 'bd->dd', file: '04_editing' } })  その章だけ
Workflow({ name: 'coverage', args: { edge: 'bd->dd', section: '4.1' } })   その節だけ

Workflow({ name: 'approve',  args: 'req->bd' })                            承認だけを回す
Workflow({ name: 'approve',  args: { edge: 'req->bd', limit: 100 } })      先頭 100 断片だけ
```

`approve` は **`agents/approver.md`** を使う。分解した側とは別の役で、**ファイルを触るツールを持たない**——
断片は親が渡し、判定の書き戻しも親がやる。承認する側は下位を開けない。
`requireApproval` を立てた段では、`coverage` は分解まで進んで**判定に入る前に止まる**
（承認で落ちる断片を先に判定すると、その判定を捨てることになり、そのうえ
**水増しされた分母の上に「判定済」が積み上がる**）。

**初めて回す段は、まず 30 件だけ試すことを勧めます。** 判定の中身を見てから全件に入れば、薄かったときにプロンプトを直す余地が残ります。全部回してから薄いと分かるのが一番もったいない。

## `stale <edge>`

上位ドキュメントが変更され、過去の判定が無効になった単位を出す。上位を直したら必ず確認する。

---

## 是正の順序

**上位に近い文書から順繰りに直す。** 上流を直さずに下流を直すと、下流が「間違った上流」に合わせて固まる。

1. 上位側に誤り・内部矛盾があるなら、まずどう解釈したかを**本人に決めてもらい、記録する**。黙って一方を採らない
2. 下位に追記・確定する
3. 連動更新を同じターンで行う
4. 是正しきれず下流へ渡る分は、G 行に「上位は解消済み・下流は未」と書き分け、担当する作業単位と判定条件を残す
