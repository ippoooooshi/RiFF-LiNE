# 運用ガイド — 日々どう使うか

> 設計の理由は `rationale.md`、規約は `rules/core.md`、移行は `../MIGRATION.md`。
> ここは**何を打つか**だけ。

## いちばん短い流れ

**先に 1 つだけ。** `.claude/state/` と `.claude/coverage/` は直接編集できません。
ゲートが読む場所なので、検査される側が書けると「検査に通った」と「検査を消した」が
区別できなくなるためです。ゴール・担当段・phase・adhoc は `state.mjs` から書きます。

```bash
node .claude/scripts/state.mjs show      # いまの作業状態
node .claude/scripts/state.mjs --help    # 使い方（引数なしで show）
```

**そして「何を編集したか」は申告ではなく `git` の実差分で決まります。** Edit でも Write でも
Bash の heredoc でも `sed -i` でも同じように見えます。

```
セッションを開く          → 現在地が自動で出る（何もしなくていい）
/wp start <パッケージ名>   → ゴールと**担当する段（edge）・範囲**を決める。ここで一度止まる
/wp design                → 分母を固定 → 設計を書く → 全件判定。終わったら止まる
/wp impl                  → 分母を固定 → 未判定を1件ずつ実装。終わったら止まる
/wp review                → 差分を hunk に切って分母を固定 → 1件ずつ判定 → 批評。指摘が出たら差し戻す
/wp done                  → 完了判定。未分解・未判定が残っていれば完了にできない
```

**分母に入れる／入れないは段ごとに指定できます。** 変更履歴やリスク表を要求として数えると、
水増ししないと分解の下限を満たせなくなるので、`project.json` の段に `skipSections` を書いて外します。
テストの段がパスで分けられないときは `idPrefix` で ID から分けます。

**この仕組みの中心は網羅台帳です。** 要件→基本設計、基本設計→詳細設計、詳細設計→実装、各段→テスト——
どれも「上位が要求していることを下位へ降ろす」作業で、降ろし漏れは書いている最中には見えません。
だから**書く前に上位を分解して分母を機械に固定させ、書いたあと全件を判定する**。
未分解が残ったまま書いたターンは Stop hook が終わらせません。

```bash
node .claude/scripts/ledger.mjs pending "<edge>" --file "<範囲>"   # いまの分母と残り
node .claude/scripts/split.mjs --coverage --show-skipped          # 切り分けが全行を覆えているか
node .claude/scripts/split.mjs orphan-tests                        # どの段にも入らなかったテスト（分母の穴）
```

**同じ形をレビューとテストにも当てています。** サボりは3か所とも同じ構造——
「全部見た」「全部書いた」を確かめる手段が無いところで起きるので、分母を機械に固定させます。

| 場面 | 分母を固定するもの | 単位 | 何を要求するか |
|---|---|---|---|
| 設計・実装 | `ledger.mjs` | 上位文書の構造単位 | 全件に判定と証拠 |
| レビュー | `diff-units.mjs` | `git diff` の hunk | 全件に判定。**「問題なし」にも理由** |
| テスト | `check-coverage.mjs` | ファイル単位のカバレッジ | 基準線より下がらないこと |

**切り分けは機械、判定は AI。** 切り分けは抽出ではなく分割で、文書の全行がどれかの単位に属します。
対象外にした行も理由つきで残るので、`--show-skipped` で「要求が書かれている行が除外に混ざっていないか」を目で見られます。

**フェーズは自動で進みません。** 各境界であなたが見て、次を打ちます。橋渡しは会話ではなくファイル（設計書と `state/current.json`）なので、セッションをまたいでも続きから入れます。

## 場面別

### 何をやるか決めるとき

```bash
node .claude/scripts/wp.mjs list     # 在るもの／着手できるもの
```

**新しい仕事が出たら、まずパッケージを起こします。** 既存のどれにも属さない仕事——機能追加で要件が増えた、パッケージが大きすぎて割りたい、ギャップの繰り越し先が要る——はここから。

```bash
node .claude/scripts/wp.mjs add WP10 --name "ループ再生" \
  --done "小節範囲を指定して再生し、終了小節の後に開始小節へ戻ることを実機で確認" \
  --after "WP7" --scope "packages/core/src/playback/**"
```

完了条件が空／前提が実在しない／範囲が実ファイルに当たらない、のどれかなら機械が拒否します。**完了条件が書けないなら切り方が悪い**ので、分割するか検証可能な代理指標を決めてください。

### 作業を始めるとき

```bash
node .claude/scripts/wp.mjs start WP10    # 前提が未完なら拒否される
```
```
/wp start データモデル・永続化
```

Claude が前提パッケージの完了状況を確認し、設計書を読み合わせ、**ゴール案を出して止まります。** 承認すると `state/current.json` に書き込まれ、以降のターンで効きます。

ゴールは5つ揃って初めてゴールです。**検証手段にコマンドを1つも書けないゴールは、切り方が悪い**ので分割します。

| 要素 | 悪い例 | 良い例 |
|---|---|---|
| 達成状態 | 「リンクを直す」 | 「相互参照が実在ファイル・実在節のみを指している」 |
| 検証手段 | 「レビューで問題なければ」 | `node .claude/scripts/check-docs-links.mjs` が 0 件 |
| 範囲外 | （書かない） | 「記法の統一は範囲外 → G38、次バッチ」 |
| 再発防止 | 「今後気をつける」 | 「リンク検査に相対リンク検証を追加し CI へ」 |

着手前に検証手段を**空振りさせて現在値を記録**します。着手前の値が無いと「直った」を検証できません。

### バグを見つけたとき

```
このバグを直して。再現テストを先に書いて、水平展開までやること。
```

`impl` エージェントの手順に入っています。

1. 再現するテストを先に書く（この時点で赤）
2. 直す
3. 緑になることを確認
4. `node .claude/scripts/spread.mjs scan "<パターン>"` で同型を全リポジトリから数え、全件に判定を付ける
5. 未対応が残るなら `/gap` で起票、防止手段を1つ足す

**再現テストなしの「直しました」は受け付けません**（impl エージェントの手順で必須。Stop hook が見るのは検証が緑かどうかだけです）。

同じ箇所を繰り返し直している気がしたら：

```bash
node .claude/scripts/recurrence.mjs
```

### レビューさせるとき

```
/wp review
```

`review` には `git diff` と受け入れ基準だけが渡ります。**あなたや実装側が書いた説明は渡りません。**

**まず機械が差分を hunk に切って分母を固定します。** 「レビューしました。問題ありません」という文は、差分の一部しか見ていなくても書けるからです。`phase` が `review` の間、分母が固定されていないターンは終われません。

```bash
node .claude/scripts/diff-units.mjs split     # 何 hunk あるかを決める（未追跡の新規ファイルも含む）
node .claude/scripts/diff-units.mjs pending   # 判定済 / 未判定 / 指摘
```

判定は3つだけ。**「問題なし」にも理由が要り、しかもその hunk に実際に現れる語を 1 つ以上含んでいないと書き込めません。** 「特に問題ありません」のような、どの hunk にも貼れる一言は弾かれます（`export` `const` のような言語キーワードだけも認めません）。「指摘あり」は引用が実ファイルと照合され、一致しなければ書き込めません。Blocking 以外なら「なぜブロッキングでないか」が必須です。

語を 1 つ借りただけの雛形（「`setTempo` の変更なので問題ありません」）までは弾けません。**弾けない代わりに数えます。** `pending` は hunk 由来の語を伏せてから理由を突き合わせるので、同じ雛形が何件を覆っているかが出ます。

```
hunk 42  判定済 42  未判定 0  指摘 1（base: main）
  指摘なしの判定 41 件 → 理由は 3 種類（最多の 1 文が 28 件を覆っています）
  ⚠ 1 種類の理由が広く使われています。…
```

同じ一括リネームのように**正当に理由が同じ**場合もあるので、書き分けは強制しません（無意味な差異を強いる検査は信用されなくなるため）。数字を見て判断するのはあなたです。

差し戻して直したあと、もう一度 `split` すると**中身が変わっていない hunk の判定は引き継がれ、変わった hunk だけが未判定に戻ります。** 全件やり直しにはなりません。離れた場所に行を足して行番号がずれただけの hunk も引き継がれます（同一性は `@@` ヘッダではなく変更行そのものから取っています）。

指摘が出たら `critic` が1件ずつ `AGREE` / `DISAGREE_EVIDENCE`（矛盾するコードを引用）/ `DISAGREE_CONCERN` を返し、引用が実ファイルと一致しない指摘は無効化されます。

**hunk 0 件は「差分が無い」ではありません。** base の指定が外れている可能性があるので、0 件のまま通さないでください。

### テストが足りているか見たいとき

```bash
node .claude/scripts/check-coverage.mjs
```

テストは実行しません。**既にある coverage の結果を読むだけ**なので毎ターン走っても無料です。有効にするには `project.json` に測定結果の場所を書きます。

```json
"paths": { "coverageSummary": "coverage/coverage-summary.json" }
```

書くと「未計測」が緑ではなく**赤**になります。テストを書いたことにするサボりは、空振り検出（assertion 0・恒真・モック反響）では拾いきれません——assertion があっても通らない経路が残っていれば同じだからです。

初日に 100% は要求しません。着手前に `node .claude/scripts/baseline.mjs record` で現在値を基準線にし、以降は**下がったファイルだけ**が赤になります。上げるのは作業単位のゴールでやってください。

### ちょっとした修正を頼むとき

```
この関数の typo 直して
```

`/wp start` を打っていなくても検査は掛かります。**触ったファイルから作業の種類が決まる**ためで、`packages/**` を編集すれば実装、`docs/**` を編集すれば設計として扱われます。以前は宣言しなければ台帳もゴールも最初から効いていませんでした。

台帳まで立てたくないときは、小修正だと宣言すれば通ります。

```bash
node .claude/scripts/state.mjs adhoc "Tempo.ts の typo 修正のみで、呼び出し側は変えない"
```

- 理由は 12 文字以上で、**いま変更されているファイルに触れている**こと（どの修正にも貼れる文は弾かれます）
- `.claude/state/adhoc.json` と `journal.jsonl` に記録され、セッション冒頭に件数が出ます
- **1 ターンで失効**します。次のターンでまた小修正なら、もう一度宣言してください
- **検証（typecheck / lint / test）も同型走査（`spread.mjs`）も免除されません**
- 直近 6 時間で 3 回を超えると、先にゴールを置くよう要求されます——それはもう小修正ではなく、宣言されていない作業なので

### コードを変更するとき（修正でも追加でも）

コードを触ったターンは、**同じ型が他に無いか**を全件確認するまで終わりません。修正か追加かは区別しません——区別しようとすると、区別する側が語を選んで検査を外せてしまうからです。

```bash
node .claude/scripts/spread.mjs scan "<直した型の正規表現>"
node .claude/scripts/spread.mjs next 1
node .claude/scripts/spread.mjs verdict <id> 是正済み '{"file":"...","line":42,"quote":"<直した実コード>"}'
node .claude/scripts/spread.mjs verdict <id> 別物   '{"reason":"<なぜ同型ではないか。その箇所の語を含める>"}'
node .claude/scripts/spread.mjs verdict <id> 繰越   '{"gapId":"G71","reason":"<なぜ今やらないか>"}'
```

**`horizontal.mjs` を直接叩かないでください。** あれは `spread.mjs` が内部で呼ぶ検索本体で、
記録を残しません。直接叩いても Stop hook から見ると走査していないことになり、ターンが終われません。

**1 ファイルに絞った `--in` は拒否されます。** 自分が直したファイルだけを走査しても、
「他に同型は無い」ことの確認にはならないからです。

**1 箇所だけに当たる文字列では水平展開になりません。** 変更した型を書いてください。ヒット 0 件は「同型が無い」ではなく「パターンが当たっていない」可能性があります。

パターンが思いつかないときは、止められたメッセージに**今回の差分から拾った語の候補**が出ます。走査は毎回やり直しです（前回の緑は使えません）。走査したパターンが触ったファイルに当たっていないと、これも通りません。

繰越には G 番号が要ります（`/gap` が番号・担当・判定条件の 3 点を要求します）。番号は**ギャップ台帳に実在すること**が確認されます——実在しない番号への繰り越しは、記録ではなく消去なので。**省略する手段は用意していません**——繰越が正規の判定なので、必ず有限で終わります。

### 「この機能も欲しかった」と言うとき

```
/feature 小節単位でループ再生したい
```

機械が本文から未確定点を見つけて**質問を作ります**。「など」「適切に」「数値のない上限」「受入条件なし」の 4 種類だけを見ます。

出た質問は 1 つずつあなたに聞きます。**記録した質問の数が未確定点の数を下回っていると、要件に書き込めません**——差分は推測で埋めた分で、要件の推測は設計・実装・テストの全段へ伝播するからです。

書き込んだあとは、分母を作り直して各段へ降ろすまで終わりません。縦（設計→実装）だけでなく**横（テスト）の段も `edges` にあります**。

### 「これどこに書いてある？」

普通に聞いてください。答えは3つの形のどれかで返ります。

```
確認した     → docs/basic_design/04_editing_core.md:182 「（逐語引用）」
未確認       → 未確認（推測）。確かめるには … が要る
見つからない → 見つからなかった（"カポ" を docs/basic_design/ 全体で grep、0 件）
```

**「見つからなかった」は失敗ではなく結論**で、それ自体が不具合の発見であることが多いです。

### 網羅性を確かめたいとき

```bash
node .claude/scripts/ledger.mjs stats                     # 各段の状態
node .claude/scripts/ledger.mjs scope "bd->dd"             # 章ごとの未処理件数
node .claude/scripts/ledger.mjs stale "bd->dd"             # 上位の本文が変わって再判定が要る単位
node .claude/scripts/ledger.mjs approval-report "bd->dd"   # 承認の当たり方
```

**上位文書を編集しても、判定は文書ごと消えません。** 単位の id は行番号ではなく本文から作るので、
行がずれただけなら引き継がれ、**本文が変わった単位だけ**が `stale` に出て再分解を要求されます。
変更前の本文と以前の分解は参照用に残ります（そのまま使い回さないこと）。

回すときは、**まず 30 件だけ試して判定の中身を見てから**全件に入るのを勧めます。

シェルで edge を渡すときは **必ず引用符で囲みます**（`"req->bd"`）。裸の `>` はリダイレクトになり、`req-` という edge を探して失敗したうえ、リポジトリ直下に `bd` という空ファイルが生えます。`req-bd` の形でも同じ段として読みます（v34。`>` が無いので引用符を忘れても何も生えません）。ゲートは引用符の外の `段->` を打つ前に止めます。

ワークフローは自律的に回ります。**エージェント間で運ぶのは ID だけ**で、各エージェントが自分で `show` して読み、自分で `judge` して書き戻します。本文を復唱させないので、件数が増えても壊れません。書き込みに失敗した件は握り潰さず `failures` として報告されます。

```
Workflow({ name: 'coverage', args: { edge: 'bd->dd', limit: 30 } })   まず 30 件
Workflow({ name: 'coverage', args: 'bd->dd' })                        全件
Workflow({ name: 'coverage', args: { edge: 'bd->dd', file: '04_editing' } })  その章だけ

Workflow({ name: 'approve',  args: 'bd->dd' })                        承認だけを回す

Workflow({ name: 'coverage', args: { edge: 'bd-dd', file: '02_data_model', lines: '164-211' } })  行で区切る
Workflow({ name: 'coverage', args: { edge: 'bd-dd', units: ['<単位 ID>', …], rules: ['<分け方の決まり>', …] } })
```

**区切りに分けて進めるとき**（v34）：1 ターンで回しきれない章は、行で区切ります。ゴールも行で狭められますが、そのときは範囲の外をいつ扱うかを書きます。範囲の外の未分解は Stop で止めずに、数を毎回知らせます。

```bash
node .claude/scripts/state.mjs goal --unit "02 章の区切り 3" --goal "164 行から 211 行の単位が分解・承認済み" \
     --verify-by "ledger.mjs approval-report" --edge "bd->dd" --file "02_data_model" \
     --lines 164-211 --later "区切り 4・5（212 行から 298 行）は次の 2 ターンで分解する"
node .claude/scripts/ledger.mjs pending "bd->dd" --file 02_data_model --lines 164-211
```

**章を 3 段で回す**（v35）：毎ターン新しいセッションで `.claude/commands/chapter.md`（`/chapter`）を最初に読みます。①章の全部の分解・承認・settle と本人に聞くことの一覧 → 本人に 1 回で聞く → ②章の全部を書く・印・harvest → ③章の全部の判定と閉じる確かめ。1 ターンの上限は判定 300・承認 450（本人決定 2026-10-01）。

```
Workflow({ scriptPath: '.claude/workflows/judge.js', args: { edge: 'bd-dd', file: '03_screens_ui_pc', segment: ['<この回の範囲の文>'] } })
Workflow({ scriptPath: '.claude/workflows/judge.js', args: { edge: 'req-bd', ids: ['<要求 ID>', …], segment: ['直した行：…'] } })   判定し直し
node .claude/scripts/ledger.mjs judge-groups "bd->dd" --file 03_screens_ui_pc --max 10    受け先ごとのまとまりを見るだけ
```

判定役には、同じ受け先（印が最初に当たったファイルと見出しの最初の語。印が無ければ上位の節）を見る要求を 10 件まで渡します。承認・settle も既定で、同じ節の断片を 10 件まで 1 体に渡します（同じ単位の断片は混ぜない・長い断片が並べば文字数の予算で少なく切る。`perAgent: 1` で 1 件ずつに戻せます）。

**上位の文を直して分け直すとき**（v37）：`ledger.mjs show "bd-dd" "<単位 ID>"` の `prevEntries` に前の分け方が出ます。変わっていない断片は 1 文字も変えずに写すと、承認と本人待ちを引き継ぎます（判定は引き継ぎません）。

**詳細設計を書き換えたら、判定の引用の行番号を付け直す**（v38）：詳細設計の途中に行を足すと、その下の判定の引用が「行番号がずれた」で無効になります（照合は ±3 行まで）。ターンの始まりのコミットを控えておき、書き換えたあとに打ちます。判定は変えず、git の差分で行を送って照合が通るものだけ付け直します。書き換えた所の近くのもの・始まりの時点で既にずれていたものは「判定し直し」に並ぶので、judge.js の `ids` で判定し直します。

```bash
node .claude/scripts/ledger.mjs reanchor "bd-dd" --since <始まりのコミット> --file 03_screens_ui_pc --dry   # 数を見るだけ
node .claude/scripts/ledger.mjs reanchor "bd-dd" --since <始まりのコミット> --file 03_screens_ui_pc         # 付け直す
node .claude/scripts/ledger.mjs show "bd-dd" "<要求 ID>"     # 判定済みなら judgement に判定が出る（v38）
```

**承認の一覧と中身**（v39）：一覧は ID と住所と大きさだけを 200 件まで取り、組を決めてから中身を組ごとに取ります（`window`・`fetchMax`・`writeMax`）。残りが `fetchMax` 以下の回は一覧に中身も付けて 1 体で取り、終わりの 3 つ（最後の取り直し・報告・台帳の数）は `wf-tail` の 1 体で取ります。分解役は既定で 1 体 10 単位です。

**v42**：判定し直し（`ids`・`idsFile`）は既定で同じファイルの要求を節をまたいでまとめます（`groupBy: "section"` で戻せます）。上位の本文が変わっていない分け直しは、前と同じ要求の判定も引き継ぎます。承認役は「範囲を閉じる文・提供しないと決める文・既定に任せると決める文」を要求として答えます。

**v43**：承認・settle は、中身の取り出しで原文（`source`・`span`）が落ちた断片を承認役に渡さず、1 件ずつ取り直します。2 回とも落ちた断片は結果の `noText` に出て、未承認のまま残ります。`tag-check --json` は一覧を切らず、章ごとの印なしの数（`untaggedByFile`）を出します。

**基本設計の閉じる文**（v41）：`node .claude/scripts/bd-closures.mjs --json` で基本設計の「〜だけ」「ここに無いものは足さない」「既定に任せる」の形の文を引けます。`workflows/bd-audit.js` は、その文ごとに基本設計のほかの箇所と両立するかを確かめ、食い違いを両方の引用つきで返します（何も書きません）。基本設計に決定を足すときは、足す機能の語で閉じる文を確かめます。判定し直しを同じファイルでまとめる `groupBy: "file"` は、dryRun で比べてから使います。

**v40 の直し**：承認・settle の書き戻しは答えを `--b64 … --sum …` で渡します（写しても形が変わらない）。judge.js は渡した ID と一覧を照らし合わせ、写し落とした ID を並べ直します。ID が多いときは `idsFile`（scratchpad に並べたファイル）で渡します。根拠の照合は要求の印（`<!-- req … -->`）を除いて行います（印は行の終わりに置く）。承認の結果の `groupStats` に、組の大きさと組を切った理由が出ます。答えを取り違えた体の断片は、まず 3 件までの組で聞き直します。

**要求と一緒に対象外へ移った断片**（v39）：concede・settle で要求を対象外へ移すと、その要求の「含む」の断片も対象外へ移りますが、v39 からは未承認になり、承認役が見直します（本人が concede した後は approve.js を回す）。v38 までに承認を引き継いで移った分は、1 回だけ次で戻します。

```bash
node .claude/scripts/ledger.mjs reopen-carried "bd-dd" --dry --json   # 数を見るだけ
node .claude/scripts/ledger.mjs reopen-carried "bd-dd"                 # 未承認に戻す（前の承認と理由は priorRecords.carried に残る）
```

**承認の詰め方**（v38）：approve.js・settle.js は、同じファイルなら節をまたいで 1 体に 10 件まで詰め（同じ単位は混ぜない）、窓 60、窓の終わりでなければ 5 件未満の体を次の窓へ回します。`pack: "section"`・`window`・`defer: 0` で前の形に戻せます。リンク・参照・記号だけの対象外は decompose が承認済みにします（承認役に回りません）。

**承認の答えの取り違えを洗う**（v36）：まとめて渡した承認で、答えが隣の断片に書き込まれることがあった（v35）。v36 の approve.js・settle.js は書く前に見つけて 1 件ずつ聞き直す。v35 で書いた承認は、次で洗う。

```bash
node .claude/scripts/ledger.mjs approval-audit "bd->dd" --file 03_screens_ui_pc --json      # 疑いを出すだけ
node .claude/scripts/ledger.mjs approval-reset "bd-dd" "<entryId>" --why "<なぜ疑うか>"     # 未承認に戻す（記録は残る）
```

**図の中にだけある決まり**（v34）：図（mermaid）は台帳の分母に入りません。区切りを分解する前に `node .claude/scripts/check-figure-notes.mjs --file <章>` で、図の注記が本文にあるかを見て、無ければ本文の対応する行に写します（知らせるだけで止めません）。

### 分解が「そもそも要求か」を確かめたいとき

機械が見ているのは**形**（出どころが逐語か・区間が重なっていないか・取り残しが無いか）だけです。
「紐付けは正しいが、そもそも要求ではない」——`（PC版）` → 「（PC版）を対象とした利用シーンである」——は
形として満点なので、**機械には原理的に見えません。**

そこで分解した本人ではない役が、断片ごとに 1 つだけ答えます。
**「この断片は、下位の文書に書かれていなければ不備といえるか」。**

```bash
node .claude/scripts/ledger.mjs approve-next "bd->dd"      # まだ見ていない断片
node .claude/scripts/ledger.mjs approve-show "bd->dd" "<entryId>"
```

「要求」と答えるには、**その要求が満たされたとき下位に現れるはずの一文**を書く必要があります。
書けないものは要求ではありません——感想で通さないための仕掛けです。

ワークフロー（`approve`）で回すと、承認する側は**ファイルを触るツールを持ちません**。
断片は親が渡し、書き戻しも親がやるので、**下位を開きたくても開けません。**

食い違っても**断片は消えません。** 「指摘」として記録され、同意するか反論するかで決着します。

```bash
node .claude/scripts/ledger.mjs concede "bd->dd" "<entryId>"   # 同意（承認はそのまま引き継ぐ）
node .claude/scripts/ledger.mjs rebut   "bd->dd" "<entryId>" '{"expect":"…","why":"…"}'
```

**同意が一番安い経路になるようにしてあります。** 直すのが高いと、最短経路が「反論して押し切る」になるので。

### 「等」「など」が残っていて決まらないとき

承認が「判断できない」と答えるものの多くは、**要件定義書の列挙が閉じていない**ことが原因です。
分解のしかたの問題ではないので、**最後にまとめて本人に聞きます。**

```bash
node .claude/scripts/ledger.mjs ask "req->bd"
```

行ごとに「原文／止まっている部分／聞くこと／決め方 2 通りとその結果」が出ます。
答えが決まったら原文を直し、`split` → `sync` → `stale` の単位を分解し直してください。
消さないのは、承認する側が誤ったときに黙って消すと、**台帳が在る理由——落ちが無いこと——が壊れる**からです。

既定では完了を止めません。止めるのは `project.json` の edge に `requireApproval: true` を書いた段だけです。
**当たり方を測る前に全段を止めると、当たっていない検査で作業が止まります。**

`一致` `対象外` 以外が出たら、1件ずつ `/gap` で起票します。**まとめて直そうとしない**——粒度が粗いと解消判定ができません。

/audit impl      実装 vs 設計

### 完了させるとき

```
/wp done
```

以下が全部揃うまで完了になりません。**最後の項目は AI が埋められません。**

- 検証が緑
- 対象エッジの未判定 0
- レビューの**未判定 0**（`diff-units.mjs pending`）と Blocking 0（批評を通過し、証拠が照合済み）
- カバレッジが基準線より下がっていない（宣言している場合）
- 着手前 baseline と現在値を並べて記載
- 再発防止を1つ足した（足せないなら `rationale.md` に理由）
- 繰り越しは G 番号・担当・判定条件つきで起票
- **本人による実アプリ確認**（見た目・音・操作感）。`current.json` の `pendingHuman` は機械ゲートではなく、`/wp done` の手順が読む項目です

網羅台帳の `humanJudged: true` の段（要件 → 受入シナリオ）は、`ledger.mjs judge … --human` で人が記録するまで `人間判定待ち` のまま完了になりません。

全件を判定しても、上位を直して分解し直した単位が残っていれば `前後確認待ち` のまま完了になりません。`ledger.mjs stale-diff "<edge>"` で前後を読み、`--ack <単位> --why "…"` で確認済みにしてください（前の要求が黙って消えていないかを人が見るための状態です）。

**詳細設計を書くとき（要求 ID の印）**：要求を満たす段落・表の行の末尾に `<!-- req <印> -->` を付けます。印は `ledger.mjs tags "<edge>" --file <章>` で出ます。書き終えたら `ledger.mjs tag-check "<edge>" --file <章>` で**印の無い要求 0・行き先の無い印 0**を確かめてから判定に進みます。印は判定役が探す手がかりで、一致の根拠にはなりません（根拠は本文の逐語）。

**前の版から引き継いだ本人待ち**：上位の文が変わって単位が作り直されると、そこにあった本人待ちは今の断片に付かず、`approval-report` に「前の版から引き継いだ本人待ち」として残ります。本人が中身を見て、今の断片で決め直したら `ledger.mjs release-hold "<edge>" <holdId> --why "…"`（本人の端末から）で外します。
分解し直して断片の区切りや文が変わったときも同じです（v30）。本人待ちの断片は、分解し直しても黙って外れません。

**要求に「含む」を付ける（v30）**：前置き・理由の句（「〜と定めている以上、」）や表の左列の見出し語は、対象外に分けずに、それが支える要求に含めます。`{"text":"<要求>","from":"<逐語>","with":["<同じ単位の逐語>"]}`。含められるのは同じ単位（同じ文・表の同じ行）の逐語だけで、別の要求を入れてはいけません。確かめ役は要求と含むを一緒に見て 1 回だけ答えます。

**要件から直す（v31）**：下の段で手戻り（要件に無い、利用者に見える振る舞い）が出たら、要件定義書から直して下へ降ろします。`req-add.mjs open "<要望>"` → 未確定点を本人に聞いて `answer` → 既存の表に行を足すなら `req-add.mjs row "<項目>" "<文>" --section "<節>" [--after "<前の行の項目>"] --history "<変更内容>"`、既存の箇条に足すなら `req-add.mjs amend "<箇条の頭の逐語>" "<足す文>" --section "<節>" --history "<変更内容>" --before "<変更前>"`。今の文を書き換えるなら `req-add.mjs replace "<今の文の逐語>" "<書き換えた後の文>" --section "<節>" --history "<変更内容>"`（v33。節の中で 1 か所だけ当たるときだけ）。どれも変更履歴の表に 1 行を自動で足します。そのあと `split.mjs req` → `ledger.mjs sync "req->bd"` → 分解・承認・判定 → 基本設計。

**語の無い単位（v30）**：「**」だけ、ひらがなだけの単位は、対象外の理由の中に原文そのもの（例：「**」）を逐語で含めれば通ります。種類は「書式・記号の切れ端」が使えます。断片だけに語が無いとき（例：フォルダの図の罫線「│  ├─」）も、承認などの理由にその断片を逐語で含めれば通ります（v32）。

**古い詳細設計からの拾い上げ**：`ledger.mjs harvest scan --ref <古い詳細設計が残っている最後のコミット>` で拾う行を洗い出し、章ごとに `harvest list --file <古いファイル> --pending` → `harvest set <id> new|bd|drop --why "…" [--in <ファイル> --quote "<逐語>"]`。残りは `harvest report --strict` で数えます。

`split.mjs <段>` は分母のファイル（`.claude/coverage/units/<段>.jsonl`）を**書き換えます**。数を見るだけなら `--dry-run` を付けてください。

## 止められたとき

### ターンが終わらない

Stop hook がブロックしています。理由がそのまま出ているので、指示されたコマンドを実行してください。

ゴールや台帳を要求されたのに「そんな大袈裟な作業じゃない」と思ったら、それは `adhoc` で通す場面です（上の「ちょっとした修正を頼むとき」）。**ファイルを 1 つも編集していないターン（調べ物・質問）はそもそも止まりません。**

```bash
node .claude/scripts/verify.mjs
```

**逃げても記録は残ります。** `state/unverified.json` にマーカーが書かれ、次のセッション開始時に必ず表示されます。

同じ理由で4回以上ブロックされたら、Claude が「何が通らないか」を報告するようになっています。原因が設計側にあることもあるので、その報告を読んでください。

### 削除しようとしたら確認が出た／拒否された

ゲートは**削除先のパスを解決して**判定します。綴りは見ません。

| 行き先 | 判定 |
|---|---|
| プロジェクトの中（`rm -rf node_modules` など） | 通る |
| OS の一時ディレクトリ | 通る |
| その外 | 確認が出る |
| ルート・ドライブ直下・ホームそのもの | 拒否 |

`rm -rf /` も `rm -fr /` も `rm --recursive --force /` も同じ扱いです。
以前は綴りを列挙していたので、フラグの順を変えるだけで扱いが変わっていました。

### ファイルを編集できないと言われた

**hook が実際に止めるのは下の2つだけ**です（`project.json` の `guards`）。レビューエージェントの書き込みは hook では判定できない（どのエージェントかが入力に無い）ので、`agents/review.md` の tools に Edit/Write を与えないことで止めています。

| 拒否 | 意味 |
|---|---|
| 既存のテストファイル | テストを通すためにテストを直すのを防いでいます。このターンで作ったテストは編集できます |
| 実装フェーズ中の `docs/` | 実装が設計を書き換えて辻褄を合わせるのを防いでいます。食い違うなら実装を止めて報告させてください |
| 設計フェーズ中の `packages/` `apps/` | 設計が固まる前に実装が先行するのを防いでいます（`project.json` の `guards.designPhaseReadonly`） |

どれも**順序の問題**です。仕様が変わったなら、先に設計を更新して承認を得るのが正しい順序です。

### セッション冒頭の現在地が、実行結果と食い違う

出力 1 行目のスタンプ（`status.mjs:1a2b3c7`）を比べてください。違えば別の版の出力です。無ければ、そもそもこの `status.mjs` の出力ではありません。

```bash
node .claude/scripts/status.mjs --no-verify      # いまの実測
echo "{}" | node .claude/hooks/gate.mjs session-start   # フックが返すもの
```

**注入は必ずセッション開始時点のスナップショット**です。作業中に変わったら取り直してください。

### 既存の負債で毎ターン止まる

**最初に基準線を記録してください。**

```bash
node .claude/scripts/baseline.mjs status   # いま何件あるか
node .claude/scripts/baseline.mjs record   # それを「既知の負債」として記録
```

記録すると、ゲートは**基準線より増えていないか**だけを見るようになります。既存の負債で止まらなくなり、新しく増えたものだけが赤になります。

**負債は隠れません。** `status.mjs` がセッション冒頭に件数を出します。

```
既知の負債（基準線 2026-09-11）: 合計 9 件
   stubs         9 件  ← ゲートは「これより増えないこと」だけを見ています
```

解消したら縮めます。

```bash
node .claude/scripts/baseline.mjs shrink   # 解消済みを基準線から落とす
node .claude/scripts/baseline.mjs list stubs   # 基準線に載っている項目を全件見る
```

基準線は**減る方向にしか動かしません。** 増やすときは `record` で明示的に記録し直す必要があるので、なし崩しに増えることはありません。

### ゴールが無いと言われた

`/wp start` を打っていない状態で作業パッケージに入っています。既定では `phase` が `design` / `impl` のときだけ要求されます。調べ物や小さな修正では出ません。

厳しくしたい／緩めたいときは `project.json` の `goalRequired` を変えてください（`always` / `phase` / `off`）。
