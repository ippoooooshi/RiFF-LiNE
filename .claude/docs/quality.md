# 品質の運用（失敗カタログと防止手段の索引）

> 規約本体は [`../rules/quality.rule.md`](../rules/quality.rule.md)。本ファイルは**実際に起きた失敗と、それぞれに今どんな防止手段が効いているか**の対応表。
> 新しい失敗クラスを見つけたら、是正と同じターンで本表に 1 行足す（quality.rule.md Q5）。

## 1. なぜこの資産があるか

このプロジェクトは要件定義 → 基本設計（16 冊）→ 詳細設計（10 冊）→ 実装 を V 字で進め、自動ゲート（typecheck / lint / test / build）とパッケージ単位のセルフレビューを通してきた。それでも 2026-09-09〜10 の実 UI 検証で、**15 画面が何も動かない・設計に同型の欠落が 6 件・設計書間のリンクが 75 本切れている・テストの 3 分の 1 が ID を持たない**ことが判明した。

原因は個々の不注意ではなく、**「書いた／直した」で完了とみなし、機械的に検算する仕組みを置かなかったこと**にある。したがって防止手段は「気をつける」ではなく、スクリプト・CI ゲート・チェックリスト・レビュー観点として置く。

## 3. 品質チェックの実行

```bash
pnpm check:quality      # check:docs + check:stubs + check:test-ids
pnpm check:docs         # 設計書 Wikilink の解決チェック
pnpm check:stubs        # UI 配線のダミーハンドラ・放棄マーカー検出
pnpm check:test-ids     # テスト ID の付与と採番簿への登録
node scripts/check-docs-links.mjs --warn-shorthand   # ]][[#N]] 曖昧記法も併せて警告
```

CI（`.github/workflows/ci.yml` の `quality-gate`）に組み込み済み。赤のままではマージできない。
ダミー配線を意図的に残す場合は `// quality-allow-stub: <理由と、いつ誰が解消するか>` を書き、同時に `00_reference.md` §8.1 へ G 行を起こす。

## 4. 現況（2026-09-10、Phase 1 完成・製品化 D1 実施中）

| チェック | 着手前 | 現在 | 解消予定 |
|---|---|---|---|
| `check:docs` | 75 件のリンク切れ | **0 件**（D1-b1 で解消） | 完了 |
| `check:stubs` | 8 件のダミーハンドラ | **8 件** | I1 機能全結線 |
| `check:test-ids` | （検査自体が無かった） | **0 件**（D1-b6 で 33 ファイル・364 テストへ付与） | 完了 |

3 つすべてが緑になることが、設計ゲート（G-D）・実装ゲート（G-I）の機械的な構成要素（[`phase1-productization.md`](phase1-productization.md)）。

## 5. 新しい失敗クラスを見つけたら

1. 是正する
2. **同じターンで** §2 の表に 1 行足す（実例・何が起きたか・防止手段・規定）
3. 防止手段が機械化できるなら `scripts/` に足して `check:quality` へ繋ぐ。できないならレビュー観点／チェックリストとして [`../rules/quality.rule.md`](../rules/quality.rule.md) か該当ルールへ
4. 機械化も規約化もできない場合は、その理由を書く（「気をつける」で終わらせない）
