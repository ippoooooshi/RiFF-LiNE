# テスト規約（運用索引）

> 権威: [`docs/basic_design/11_test_strategy.md`](../../docs/basic_design/11_test_strategy.md)（特に §0 品質KPI・§2 カバレッジ・§3 対象一覧）、[`docs/basic_design/15_development_process.md`](../../docs/basic_design/15_development_process.md) §5。

## テストレベル（V字の右側、§1）

| レベル | 粒度 | タイミング |
|---|---|---|
| 単体テスト | メソッド単位 | 各作業パッケージの実装直後（L/XL はサブ機能の区切りごと） |
| 結合テスト | モジュール単位（サービス層をまたぐ） | 単体完了後、作業パッケージ完了前後 |
| システムテスト | アプリ全体の操作シナリオ | 主要パッケージが揃った時点 / Phase 節目 |
| 運用テスト | 実際の耳コピ作業 | Phase 1 完了前後 |

## カバレッジ基準（§2、品質KPI）

| 種別 | 適用範囲 | 基準 |
|---|---|---|
| C0（命令網羅） | 実装した全メソッド | **100%** |
| C1（分岐網羅） | 実装した全メソッド | **100%** |
| C2（条件網羅） | §2 の「対象ロジック一覧」に限定 | 複合条件の各要素を真偽の組み合わせで検証 |

C2 対象ロジック（抜粋・随時追記）: コマンド層 execute/undo の対称性、Undo/Redo 履歴のメモリ予算判定、バリデーションの上限・重複判定、奏法記号の自動候補判定、拍子/テンポ継承チェーン再計算、スキーママイグレーション、ファイルI/Oのアトミック書き込み・整合性検証、`NotificationCenter` のレベル別ルーティング。

## タイミング（§5、テスト後書き）

- **TDD は採らない**。主要ロジックの実装後にまとめて書く（仕様の細部が実装しながら固まる領域の二度書きを避ける）
- **L/XL サイズは例外**: `feature/<slug>-<subfeature>` の区切りごとにテストを追加し、未検証コードが積み上がる期間を短くする
- 「自動テスト基盤」という独立作業パッケージは設けず、各パッケージの DoD（基準3）に組み込む

## フレームワーク・配置

- **Vitest**。単体は対象と同じディレクトリの `*.test.ts`（`packages/core/src/**`）、結合は `apps/desktop/src/main/*.test.ts`
- テスト名: `<対象>_<条件>_<期待結果>`。各テスト先頭コメントに対応 ID（`// UT-XXX` / `// IT-XXX`）と、該当する基本/詳細設計の節番号を併記
- 外部ライブラリ（alphaTab 等）は mock。実 I/O は OS の一時ディレクトリを使い、テスト後に破棄

## 禁止事項

- 本番データファイル・実ストレージルートの参照
- ネットワーク通信
- 機微情報を assertion メッセージ・ログに含めること
- テスト実行順依存

## impl フェーズのテスト追跡レポート（必須出力）

実装完了時に5項目すべて出力（省略・N/A 代替不可）: (1) テスト件数の増減（UT/IT/合計、実装前・後・増減）(2) 結果内訳（PASS/SKIP/FAIL）(3) SKIP 理由（件ごと）(4) テスト不具合と修正内容 (5) 今回追加したテスト（名前と理由）。

## 検証ゲート（完了条件）

コード変更後、完了報告の前に `pnpm typecheck` / `pnpm lint` / `pnpm test` がすべて緑であることを確認する。未確認・一部スキップ・失敗ありを「完了」と報告しない。振る舞いを変えたのに旧仕様のままテストが通る状態（false positive）は不可。
