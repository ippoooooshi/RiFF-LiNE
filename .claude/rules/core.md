# 中核規約

> ここには**スクリプトで判定できないもの**だけを置く。判定できるものは `.claude/scripts/` にあり、hook と CI が強制する。ドキュメントに二重で書かない。

## 1. 引用の書式（3つの形しかない）

```
確認した   → `docs/basic_design/04_editing_core.md:182` 「カポ使用時も表示は運指のまま」
未確認     → 未確認（推測）。確かめるには <方法> が要る。
見つからない → 見つからなかった（"カポ" を docs/basic_design/ 全体で grep、ヒット 0 件）
```

この3つ以外の書き方をしない。「〜のはずです」「おそらく〜です」を断定形に丸めない。**「見つからなかった」は失敗ではなく結論**であり、それ自体が不具合の発見である場合が多い。

「0件だった」と書く前に必ず検索する。読んだ記憶で断定しない。

**原因を書くときも同じ。** 「A のせいで B が起きた」「A が原因でした」と書けるのは、
**A を外して B が起きなくなることを確かめたとき**だけ。確かめていないなら
「未確認（推測）。確かめるには A を戻して再現する必要がある」と書く。

これは規約にしかできない——反事実は機械には測れないので、`claims.mjs` は見ていない。
実測で 3 回続けて外した（2026-09-16）:

| 書いたこと | 実際 |
|---|---|
| 「引数が JSON 文字列で渡っている」 | 表示の形をそう読んだだけ。実行時の値は違った |
| 「再分解で対象から外れました」 | 外れたのは `ask` の引き金を絞ったパッチのため |
| 「`--file` から `docs/` を外したので噛み合った」 | その検査は `--file` を見ていない。別のパッチのため |

3 つとも**もっともらしく、確かめる手段が在り、確かめていなかった**。
原因が分からないまま先へ進むほうが、間違った原因を書くより安全。

**これは規約であると同時に、機械が強制する唯一の文書規約である。** Stop hook が `scripts/claims.mjs` を通して、そのターンで言ったことを照合する。

| 主張 | 機械が見るもの |
|---|---|
| `ファイル:行` ＋ 逐語引用 | 実ファイルと一致するか |
| 「見つからなかった」「0 件」「存在しない」（対象がパスか引用符つきの語のとき） | そのターンに検索（Grep / Glob / grep / rg / find）の記録が在るか |
| 「確認しました」「実行しました」「読みました」 | そのターンに対応するツール使用の記録が在るか |

裏が取れなければターンを終えられない。**確かめていないなら「未確認（推測）」と書くこと。** そう書けば主張として扱われない——これが2番目の形が在る理由で、逃げ道であると同時に記録でもある。

## 2. 質問の書式

判断を仰ぐときは4つを守る。

1. **ID を主語にしない。** `G46` `B24` `MJ-A3` と言われても判断材料にならない。平文で何を決めるのかを書き、ID は末尾に添える。
2. **矛盾は逐語引用する。** 「2箇所が矛盾しています」ではなく、両方の原文を行番号つきで並べる。
3. **選択肢には結果を書く。** その案を採ると何がどうなるか、何を諦めることになるかを1〜2行ずつ。
4. **なぜ今決める必要があるかを1行で。** これが書けないなら、まだ聞くタイミングではない。

```
悪い: G46（カポの表示方式）について判断が必要です。A: 運指のまま  B: 実音に反映

良い: カポを付けたとき、タブ譜の数字をどう表示するか決めてください。
      要件定義書に両方の書き方が混在しています。
        「カポ使用時も表示は運指のまま」（要件4.1、L182）
        「カポの設定は表示・再生ピッチに反映される」（要件2.3、L94）
      A. 押さえる位置の数字をそのまま表示（カポ2で3フレットを押さえたら「3」）
         → 市販タブ譜と同じ慣習。ただし再生側で +2 する処理が要る。
      B. 実音のフレット位置を表示（同じ状況で「5」）
         → 数字と実音が一致。ただし演奏者が毎回カポ分を引き算する。
      これを決めないと編集コアと再生エンジンの両方が設計できません。（G46）
```

**聞くべき場面**は4つ。上位文書が矛盾している／決めるべき中身が未定義（「等」「など」で列挙が閉じていない箇所を含む）／スコープを超える／技術前提が未検証。いずれも**推測で埋めない**。

## 3. 調査・相談に答えるとき

- 外部ライブラリ・ツールの仕様は、`node_modules/` の実物か公式ドキュメントを引いてから答える。引けないなら「未確認」と書く。**もっともらしい API 名を書かない。**
- 設計判断の相談には**2案以上とトレードオフ**を出す。1案しか成立しないなら「なぜ他が成立しないか」を書く。
- 決めるのは本人。AI は選択肢と結果を並べるところまで。

## 4. レビューの重大度

重大度は「製品として出せるか」だけで決める。完成度を理由に下げない。

以下は非ブロッキングに見えても**ブロッキングに格上げする**。

- 仕様乖離
- 潜在バグ（意図不明のアサーション、自己矛盾、条件分岐の論理欠陥）
- セキュリティリスク・機微情報の混入
- テスト空振り（常に PASS で何も検証していない）
- トレーサビリティ断絶（設計書節番号／要件・テスト ID の併記欠落）
- ダミー配線・未結線のまま「完成」と呼んでいる箇所

純粋な可読性・スタイルのみが非ブロッキング。非ブロッキングと判定した項目には「なぜブロッキングでないか」を1行つける。

## 5. 是正したら防止手段を足す

不具合を直したら、同じ種類を機械的に防ぐ手段を**同じ変更の中に**入れる。スクリプト・CIゲート・型・テストのいずれか。「気をつける」は手段ではない。

足せなかった場合は `.claude/rationale.md` の「残っている既知の弱点」に1行足し、**なぜ機械化できないか**を書く。これが「気をつける」で終わらせないための唯一の逃げ道であり、逃げた記録が残る。

## 6. 本人へ判断を回すとき（AI が本人に出すもの）

2 節は「何を聞くか」の書式。ここは**AI が本人に判断を回すときに何を書くか**で、1 行の指示だけを投げないための規約。

**実測（2026-09-21）**：割れた断片 1 件について、外部 AI が「1 周目を採る。このコマンドを打て」とだけ出した。
本人の返事は「**現状だと情報から判断できない**」だった。**判断材料を出さずに結論と手順だけ渡していた。**

回すときは**必ず 5 つ**を書く。

1. **何を決めるのかを、専門語を開いて 1 段落で。**
   節番号・ID・コマンド名を主語にしない。「この一文を要求として数えるか、後ろの文を導入するための宣言として数えないか」のように書く。
2. **なぜ決まっていないのか。** 仕組みのどこで止まっているかを説明する。
   「2 人に別々に聞いて答えが割れたので、多数決を取らずに本人へ回す仕組みになっている」まで書く。
3. **両者の言い分を逐語で。** 要約しない。**どちらが正しそうかの印を付けない。**
4. **自分の見立てと、その根拠。そして反対する理由も。**
   **根拠は手元で確かめたものだけ。** 確かめていないものは「未確認（推測）」と書く。
   **反対する理由を書けないなら、まだ材料が足りない。**
5. **決めた後に何が起きるか。** 数えられるものは前後の表にする。
   **数字は手元で確かめたものだけ書く。** 確かめていないなら**式で渡す**（`138 −（一致へ動いた件数）` のように）。
   予測を確定値として書くと、受け取った側が「合わない」と言って止まる（実測で 1 往復ぶん無駄にした）。

そのうえで、打つコマンドは**最後に 1 つだけ**置く。

**やってはいけないこと。**

- 結論とコマンドだけ渡す（＝上の 1〜5 が無い）
- 「どちらでもよい」と書いて実質的に決めさせない。**見立ては必ず書く**（決めるのは本人）
- 決めたことを取り消す道を書かずに渡す。**どの状態からでも戻せることを確かめてから回す**
  （`hold` → `concede` → `uphold` は実測で 3 回、戻す道が塞がっていた）

## 7. 一時ファイル

作業用の中間ファイルはリポジトリ内に作らない。OS の一時ディレクトリを使う。変更ログ・作業記録を目的とした新規 Markdown を作らない（既存を更新する）。
