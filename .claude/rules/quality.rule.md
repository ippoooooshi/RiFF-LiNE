# 品質規約（最上位）

> 本ファイルは他の全ルールに優先する品質の憲法。個別領域は [docs.rule.md](docs.rule.md) / [tests.rule.md](tests.rule.md) / [typescript.rule.md](typescript.rule.md) / [layer-architecture.rule.md](layer-architecture.rule.md) / [electron.rule.md](electron.rule.md) / [ui.rule.md](ui.rule.md)。
> 失敗の実例と、それぞれに対する現行の防止手段は [../docs/quality.md](../docs/quality.md)。

## 0. 品質の基準

**このアプリは製品である。**「個人開発だから」「MVP だから」「シェル段階だから」を理由に、見た目・結線・整合性の基準を下げない。基準を下げてよいのは *スコープ*（何を作るか）であって *完成度*（作ったものがどうあるか）ではない。スコープを狭めるのは正しい判断、狭めたスコープの中を中途半端に残すのは不良品。

## 1. 八つの規定

### Q1. 主張は検証を伴う（Claim ⇒ Verify）

「反映済み」「解消済み」「対応済み」「〜に定義されている」と**書く／報告するときは、その直前に参照先を実際に読んで確認する**。確認していないなら書かない。

- 過去の実例: G6（申し送り先と実装が食い違い）、G10（「追記済み」と書いたが実体なし）、G19（存在しない節への「反映先」）、監査 MJ-B2（実装済みクラスへの死んだアンカー）。いずれも「書いた本人が確認していれば防げた」もの。
- 適用: クロスリファレンスを書いた直後にその節を開く。ギャップ台帳を「解消済み」へ書き換える前に実体を確認する。完了報告に含める事実は、その場で観測した結果だけにする。

### Q2. 単一の真実源（Single Source of Truth）

**同じ事実を 2 箇所に書かない。** 書く必要があるなら一方を「正」と明記し、他方はそこへの参照に留める。

- 過去の実例: G1（詳細設計書本体が責務レベルのまま、as-built は `00_reference.md` §3 にだけ存在 → どちらが正か不明のまま実装が進んだ）、`TagStore.create` の戻り値が 2 箇所で不一致。
- 適用: 値・シグネチャ・上限値・エラーコードのレベルは定義箇所を 1 つに決める。コード側も同様（同種ロジックの二重定義禁止、[typescript.rule.md](typescript.rule.md)「単一の真実源」）。

### Q3. 「完成」は繋がっていること

シェル・スタブ・ダミーハンドラは**完成ではない**。完成とは、設計が定めた接続先（サービス／コントローラ／IPC）へ実結線され、その経路が自動テストで検証されている状態。

- 過去の実例: WP8 の 15 画面が `() => undefined` で無反応のまま「シェル段階・非ブロッキング」と分類され、実 UI で初めて破綻が露見（G23）。
- 適用: `pnpm check:stubs` が 0 件。意図的な繰り越しは `// quality-allow-stub: <理由と、いつ誰が解消するか>` を書き、同時に Q4 の台帳へ載せる。

### Q4. 繰り越しには番号・責任・期限を付ける

「後で」を許すなら、**G 番号（`00_reference.md` §8.1）＋ 解消を担う作業パッケージ ＋ 判定条件**をその場で書く。無期限・無責任の繰り越しは禁止。同種の繰り越しが 2 パッケージ以上連続したら、繰り越しではなく計画の誤りとして実施順序を見直す。

- 過去の実例: DoD 基準5（実 UI 手動シナリオ）を WP1〜7 の全パッケージが最終パッケージへ繰り越し、統合不全が終盤まで露見しなかった（G23）。
- 適用: 繰り越しを書いたら `00_reference.md` §8.1 に G 行を起こす。解消時は「解消済み（日付・対応パッケージ）」へ書き換え、**削除しない**。

### Q5. 直したら、同じクラスを機械的に防ぐ手段を 1 つ足す（Fix + Prevent）

不具合・不整合を是正したら、**同じ種類が二度と起きない仕組み**を同じ変更の中に入れる。スクリプト・CI ゲート・型・テスト・チェックリスト・規約のいずれか。「気をつける」は手段ではない。

- 過去の実例: `SetTempoCommand` 欠落（G2）を直したが仕組みを足さなかったため、同型の欠落が 2 件（拍子変更 BL-1・リピート BL-2）残っていた。
- 適用: 是正 PR には「この class を今後どう防ぐか」を必ず書く。防止手段を足せない場合は理由を書く。

### Q6. トレーサビリティは双方向で閉じる。ただし**対応表は検証ではない**

要件 → 設計 → 実装 API → テスト ID の鎖を、**両方向から**検算する。「設計にあるものが実装されたか」だけでなく「要件にあるものが設計に存在するか」を必ず見る。

- 過去の実例: BL-1／BL-2（要件4.1 の記譜要素にコマンドが存在しない）。順方向のレビューだけでは検出できなかった。
- 適用: データモデルの変更可能フィールドは、対応するコマンド（または明示的な「編集不可」の記載）とテストを持つ。対応表を維持し、追加のたびに更新する。

**そのうえで、対応表が埋まっていることを「検証した」と呼んではならない。** 対応表は**一度確かめた事実が後で壊れたことを知るための回帰ネット**であって、確かめる行為そのものではない。

| 何を作ったか | 何を検出できるか | 何を**構造的に**見落とすか |
|---|---|---|
| 章単位の対応表 | 章がどの文書に対応するか | **章の中の抜け**（BL-1〜BL-6 を 6 回続けて見逃した） |
| 項目単位の対応表＋検証キー（下位の本文に literal で在るべき語を機械照合） | 一度確かめた語が消えたこと | **キーに選ばなかった中身**。キーは書く側が選ぶため、見落としているものは原理的にキーにならない |
| 上位の**全行**を読み、意味で突き合わせる | 上記すべて | （これが検証。ただし人が読む以上、回帰は上の 2 つに委ねる） |

- 実例: 検証キー方式で「指摘 0 件」に到達した直後に要件定義書 436 行を全行読み合わせたところ、**不具合 25 件**が出た（G40〜G64）。過半はキー照合では原理的に出ないもの（上位内の矛盾を下位が黙って解決していた／申し送り先に実体が無い／要件の半分だけ降りている）。
- 適用: 段が変わるたびに、**上位ドキュメントを 1 行目から全行読む**。手順は [`../commands/trace-review.md`](../commands/trace-review.md)。「主要な項目を確認した」で終わらせない。
- 検証キー方式の実装は 2026-09-10 に破棄済み（タグ `backup/traceability-tables-20260910`）。**作り直さない。**

### Q7. 設計の完成度＝実装が迷わない粒度

詳細設計は責務の散文で止めない。**クラス／メソッドのシグネチャ（引数・返り値・例外時の挙動）・型・状態遷移**まで書く（B13）。曖昧なまま実装すると、実装が勝手に決めて設計と乖離し、乖離が検出されないまま積み上がる。

- 過去の実例: G1（WP4〜8 が責務レベル止まり）→ 「設計どおりに実装できているか」を検証する土台が無い状態で 5 パッケージが積み上がった。
- 適用: 設計フェーズの完了条件に「シグネチャレベルであること」を含める。実装で乖離したら、実装を設計に合わせるか設計を更新するかを**その場で**選ぶ（乖離放置は DoD 基準2 違反）。

### Q8. 重大度を完成度で割り引かない

レビューの重大度は「製品として出せるか」で決める。「まだシェルだから」「後でやるから」を理由に Blocking を非ブロッキングへ downgrade しない。**後でやる**なら Q4 の台帳へ載せる。載せないなら今やる。

- 過去の実例: WP8 のダミー配線・14 章ビジュアル未到達・画面導線の欠落が一貫して「非ブロッキング」と分類され、実 UI 検証で初めて製品水準に程遠いと判明した。

## 2. 機械的ゲート

| コマンド | 検査 | 対応する規定 |
|---|---|---|
| `pnpm check:docs` | 設計書の Wikilink が実在ファイル・実在節を指すか | Q1 / Q2 |
| `pnpm check:stubs` | UI 配線にダミーハンドラ・放棄マーカーが無いか | Q3 |
| `pnpm check:test-ids` | 全テストファイルが採番簿（`11_test_strategy.md` §3.1）で予約された ID を持つか | Q6 |
| `pnpm check:quality` | 上記 3 つをまとめて | — |
| `pnpm typecheck` / `lint` / `test` / `build` / `format` | 既存の自動ゲート | 全般 |
| `/audit-consistency` | 設計体系の横断整合（独立 3 観点） | Q1 / Q2 / Q6 |
| `/audit-fidelity` | 実装 vs 設計の全体照合、ダミー配線の機械チェック | Q3 / Q6 / Q7 |
| `/trace-review` | **機械ゲートではない。** 上位ドキュメントを全行読み、下位へ意味で降りているかを人が判定する手順。上の各ゲートが「一度確かめた事実の回帰」を見るのに対し、これは**確かめる行為そのもの**（Q6） | Q1 / Q4 / Q6 |

`check:docs` / `check:stubs` は CI の品質ゲートに含まれ、赤のままではマージできない。緑化後に pre-commit へも接続する。

## 3. 完了を宣言する前に

1. 自動ゲート 5 種（typecheck / lint / test / build / format）＋ `pnpm check:quality` が緑
2. 変更に対応する UT / IT があり、カバレッジ KPI（[tests.rule.md](tests.rule.md)）を満たす
3. 文書同時改訂が済んでいる（[docs.rule.md](docs.rule.md)）
4. 独立レビュー（実装との対話履歴を持たないセッション）で Blocking 0
5. Q5 の防止手段を足した、または足せない理由を書いた
6. 繰り越しがあれば Q4 の台帳に載せた
7. 報告に書いた事実はすべて Q1 のとおり自分で観測した

## 4. 禁止事項

- 検証していない状態を「済」と書く／報告する（Q1）
- ダミー配線のまま「完成」と呼ぶ（Q3）
- 台帳に載せない繰り越し（Q4）
- 是正だけして防止手段を足さない（Q5）
- 完成度を理由にした重大度の引き下げ（Q8）
- 「一人開発だから」「隙間時間だから」を理由にした自動化工程の緩和（[`docs/basic_design/15_development_process.md`](../../docs/basic_design/15_development_process.md) §0.1）
