## 1. パンの向き（-50 と 50 のどちらが左か）

1. **何を決めるか**：各パートの音を左右のどちらから鳴らすかを決める「パン」は、-50 から 50 の整数で持つと基本設計に書いてある。この -50 の側が左なのか右なのかを決める。ミキサー画面のつまみを左に回したときに音が左へ寄るかどうかとして、利用者に見える
2. **なぜ決まっていないか**：基本設計は値の範囲だけを書き、向きをどこにも書いていない。作り直している詳細設計は、利用者に見えるのに基本設計に無いものを決めずに注にする書き方にしている（part-tuning-management.md 2.1 節「次の 2 つは利用者に見えるが、基本設計に書かれていないので本書では決めない。」）ので、注にして先へ進めた。止めなかったのは、向きが決まらなくても 02 章の残りの区切りを書けるため（向きを使うのは 05 章の再生の回）
3. **原文**：
   - 要件4.2「パートごとの音量・パン（左右定位）調整が必要（ソロ／ミュートとは別に細かいバランス調整）」
   - 要件4.3「**専用ミキサー画面**：全パートの音量／パン／ソロ／ミュートを一覧で操作できる画面を用意」
   - 基本設計 02:135「| volume, pan, solo, mute | number/bool | 4.3「専用ミキサー画面」。パンの実行時制御可否は[[13_design_decision_points.md#2]]A13で検証待ち。音量は0から100の整数、パンは-50から50の整数とする |」
   - 基本設計 03:278「| ミキサーパネル | 全パートを横並びのチャンネルストリップで表示。音量／パン／ソロ／ミュートのみ（EQ等なし、要件4.5）。各チャンネルの見出しにパート識別色を表示 |」
   - 基本設計 05:25「ミキサーパネル（[[03_screens_ui_pc.md#10]]）の音量・パンは各パートのMIDIチャンネルのControl Change（Volume/Pan）へ即時反映する。」
   - 詳細設計 part-tuning-management.md 2.1 節の注「パンの向き（-50 と 50 のどちらが左か）」
   - alphaTab 1.8.4 の型定義 `alphaTab.d.ts` 13483 行「Gets or sets the balance (0-16; 8=center)」（alphaTab の側の値は 0 から 16 で 8 が真ん中。どちらが左かはこの行に書いていない）
   - 今のコード（読んだだけ）：`packages/core/src/parts/commands/partAttributeCommands.ts` の `SetPartPanCommand` は、受け取った値をそのまま `balance` に入れている（「super(score, trackIndex, 'balance', pan);」）。-50 から 50 を 0 から 16 へ読み替える所は見つからなかった（"balance" を `packages/` と `apps/` の `src` で grep、読み替えの式は 0 件）
4. **選べる案**：

| | 案 A：-50 が左、50 が右 | 案 B：-50 が右、50 が左 |
|---|---|---|
| ミキサーのつまみ | 左に回す（値を小さくする）と音が左へ寄る。数直線と画面の左右が同じ向き | 左に回すと音が右へ寄る。つまみの向きと音の向きが逆になる |
| MIDI の Pan（Control Change 10） | MIDI の Pan が 0 を左の端、64 を真ん中、127 を右の端とするなら（規格の中身は手元で確かめていない。未確認〈推測〉）、小さい値が左で同じ向き。読み替えは足して寄せるだけ | 読み替えで向きを反転させる式が要る |
| 書き出す MIDI（要件4.4 の「ミキサーの音量・パンを入れる」） | 同じ読み替えで書ける | 反転を書き出しの側にも入れる |

5. **見立て**：**案 A**
   - 根拠：一般の DAW やミキサーの表示も、左を負の側に置くものが多い（未確認〈推測〉。確かめるには主な DAW の表示を実際に見る必要がある）。MIDI の Pan は小さい値が左の端（MIDI の規格の中身は手元で確かめていない。未確認〈推測〉）で、向きがそろうと再生と書き出しの読み替えが 1 つの式で済む
   - 反対する理由：alphaTab の `balance`（0 から 16）で、0 が左か右かを型定義からは確かめられていない。もし alphaTab の側が逆向きなら、案 A でも読み替えの式で反転が要る（どちらの案でも、式の向きは 05 章の回に実機で確かめる必要がある。基本設計 13 章の A13 はパンの実行時の制御そのものがまだ検証待ち）
6. **決めた後**：
   - 基本設計 02:135 の備考に向きを足す（例：「パンは-50から50の整数とし、-50を左の端、0を中央、50を右の端とする」。行数は変わらない）。要件は直さない（要件は向きを求めていない）
   - 直した行を分解し直し、承認に回す（02 章の区切り 2 の 1 単位）。詳細設計 part-tuning-management.md 2.1 節の注から 1 行外し、本文に書く
   - -50 から 50 を alphaTab の `balance` と MIDI の Pan へ読み替える式は、05 章の回に playback-integration.md に書く
   - 取り消すとき：基本設計の備考を前の文に戻し、分解し直す（1 単位）

## 2. パート識別色の既定パレット（何色で、どの色か）

1. **何を決めるか**：パートを足したとき、ほかのパートと重ならない色を自動で付ける。その「最初から用意しておく色の組」を何色にし、どの色にするかを決める。スコア表示で譜面をパートごとに色分けするときと、パートの一覧やミキサーの見出しで、利用者に見える
2. **なぜ決まっていないか**：基本設計は「8色程度」とだけ書き、色の数を閉じていない（「程度」）。色の値も書いていない。前の詳細設計（作り直す前、`2759936` の時点）と今のコードには 8 色が決めてある。作り直している詳細設計は、利用者に見えるのに基本設計に無いものを決めずに注にする書き方にしている（part-tuning-management.md 2.1 節「次の 2 つは利用者に見えるが、基本設計に書かれていないので本書では決めない。」）ので、前の 8 色を引き継がずに注にして先へ進めた。止めなかったのは、色が決まらなくても 02 章の残りの区切りを書けるため（色を使うのは 03 章の画面の回）
3. **原文**：
   - 要件4.5「譜面のパート別色分け表示 | **【2026-08-30 基本設計フェーズで決定】** 必要。スコア表示モードで各パートを識別色で着色する」
   - 基本設計 02:140「新規パート追加時は既存パートと重複しない色を8色程度の既定パレットから自動割当し、パート管理パネル（[[03_screens_ui_pc.md#10]]）から手動変更も可能にする。」
   - 基本設計 14:49「Part.colorの既定パレットは、本書のアクセントカラーと隣接しすぎない（パートの色をアクセント＝操作可能要素と誤認しない）よう、ヒュー（色相）を意図的にずらして選定する。」
   - 基本設計 14:45（アクセントカラー）「| accent | `#5850ec` | `#8b84f5` | プライマリボタン、アクティブなナビ/タブ、フォーカスリング |」
   - 前の詳細設計 `2759936` の part-tuning-management.md 157 行から 167 行「/** パート識別色の既定パレット（8色。02_data_model.md §3.2「8色程度の既定パレット」の確定値）。 */ export const PART_COLOR_PALETTE: readonly string[] = [ '#4f46e5', // indigo '#059669', // emerald '#dc2626', // red '#d97706', // amber '#0891b2', // cyan '#7c3aed', // violet '#db2777', // pink '#65a30d', // lime ];」
   - 今のコード（読んだだけ）：`packages/core/src/parts/PartColorAllocator.ts` 13 行から 21 行に、前の詳細設計と同じ 8 色。色の選び方は同じファイルの `allocate` の説明「未使用の先頭パレット色を返す。」「全色が埋まっている場合（通常はパート数上限で到達しない）はパレット先頭を返す。」
   - 台帳（turn 102 の判定）：02:140 の「パートごとの色分け表示」と「8色程度の既定パレットから自動的に割り当てる」の 2 要求が、パレットの色の数と値が無いことを理由に「部分」。この 2 件は、ここが決まるまで分類を付けていない
   - 詳細設計 part-tuning-management.md 2.1 節の注「パート識別色の既定パレットの色の数と値（基本設計は「8色程度の既定パレット」と書く）」
4. **選べる案**：

| | 案 A：前の 8 色をそのまま引き継ぐ | 案 B：8 色にするが、アクセントカラーに近い色を入れ替える | 案 C：色の数から決め直す |
|---|---|---|---|
| 色の数 | 8（パートの上限 8 と同じなので、上限まで重ならない） | 8 | 本人が決める数。8 より少ないと、上限の 8 パートで色が重なる |
| 14 章のアクセントカラーとの関係 | 1 色目の `#4f46e5`（インディゴ）は、アクセントの `#5850ec`（インディゴ）と色相がほぼ同じ。6 色目の `#7c3aed`（バイオレット）も近い。14:49 の「ヒューを意図的にずらして選定する」と合わない見込み（色相の差を数で確かめてはいない。未確認〈推測〉） | 近い色を、ほかの 6 色と重ならない色相の色に替える（どの色にするかも決める） | B と同じ確かめが要る |
| 今のコード | そのまま使える | `PART_COLOR_PALETTE` の 2 色を替える（実装の回） | 数と値を替える |
| 基本設計の直し | 02:140 の「8色程度」を「8色」にし、値の置き場所を書く | A と同じ | 02:140 の数を直す |

5. **見立て**：**案 B**
   - 根拠：色の数は、パートの上限 8（基本設計 02 章 4.3 節と 3.2 節）と同じ 8 にすると、上限まで色が重ならない。前の 8 色は、1 色目がアクセントカラーと同じインディゴで、基本設計 14:49 が求める「アクセントと隣接しすぎない」に合わない見込み
   - 反対する理由：どれくらい離れていれば「隣接しすぎない」かの基準が基本設計に無いので、案 B でも替える色を選ぶ基準がまた要る。案 A なら今のコードをそのまま使え、前の詳細設計で一度決めた値を変えずに済む
6. **決めた後**：
   - 基本設計 02:140 の「8色程度」を閉じた数に直す（行数は変わらない）。直した行を分解し直し、承認に回す（02 章の区切り 2 の 1 単位）
   - 色の値は、詳細設計 part-tuning-management.md 2.1 節の注から外して本文に書く（案 B・C なら、替えた色と選んだ理由も）。拾い上げの行 `part-tuning-management.md:288aed45`（前の詳細設計の 8 色）を、書いた場所へ set する
   - 台帳の「部分」の 2 件を判定し直す。色分け表示のほうは、色を重ねる画面（03 章の回）が書かれるまで一致にならない見込み（未確認〈推測〉）
   - 取り消すとき：基本設計の数を「8色程度」に戻して分解し直す。詳細設計は注に戻す

## 3. 小節の拍子の「直前を継ぐ」を、どこに残すか

1. **何を決めるか**：小節の拍子は、値を持たない小節では「直前の小節の拍子を継ぐ」と基本設計が決めている。たとえば 1 小節目を 4/4、2 小節目から 5 小節目を「継ぐ」にしておくと、あとで 1 小節目を 3/4 に変えたとき、2 小節目から 5 小節目も 3/4 になる。一方、2 小節目に「4/4」とはっきり入れた小節は、1 小節目を変えても 4/4 のまま。この「継ぐ」と「同じ値をはっきり入れた」の違いを、曲のファイルのどこに残すかを決める
2. **なぜ決まっていないか**：曲の実体は alphaTab のデータ（`Score`）で、拍子は曲共通の小節（`MasterBar`）が持つ。ところが `MasterBar` は拍子の値を小節ごとに必ず持ち、「継ぐ」の印を持つ所が無い（alphaTab 1.8.4 の型定義で確かめた。変わり目かを表す `hasChanges` は読み取り専用で、説明に「テンポが本当に前の小節から変わるかは見ない」とある）。前の詳細設計は、アプリの側のデータ（`AppMetadata`）に「継ぐ」の印を持つとしていた。しかし本人が 2026-09-27 に、曲のファイルの `appMeta` に入れるものを 5 つに限ると決めていて、その 5 つに入っていない。テンポは、変わる小節にだけテンポの印（`tempoAutomations`）を置けるので、印が無い小節を「継ぐ」と読める（詳細設計 editing-core.md 3.2 節にそう書いた）。拍子だけが残った。止めなかったのは、区切り 3 のほかの要求は、これが決まらなくても書けるため（使うのは基本設計 04 章の回に書く拍子を変えるコマンド）
3. **原文**：
   - 基本設計 02:170「| Bar.timeSignature / tempoBpm（nullable＝直前値継承） | 4.1「拍子・テンポの曲途中変更」。小節の挿入・削除時の継承チェーンの扱いは[[04_editing_core.md#10]]（[[13_design_decision_points.md#3]]B5）で規定。拍子とテンポは曲共通で、実体はalphaTabの`MasterBar`が持つ（本表の`Bar.timeSignature`・`tempoBpm`は論理名。3.2節） |」
   - 基本設計 13:52（B5）「**(b)に確定**：挿入した新規小節のtimeSignature/tempoBpmは常にnull（継承）で初期化し、直前の実値をコピーしない。削除時は前後の継承チェーンが変化しないため追加処理は不要（null継承は「値」ではなく「参照方向」なので削除の影響を受けない）。」
   - 基本設計 04:171「挿入：新規小節の`timeSignature`/`tempoBpm`は常に`null`（＝直前の値を継承）で初期化する。直前の実値をコピーして固定値化しない。こうすることで、後から挿入位置より前の拍子・テンポを変更した場合にも新規小節へ自動的に反映される。」
   - 基本設計 02:270「`appMeta`（曲のファイルのうちScoreの外に置く情報）に入れるのは、`tags`（曲に付けたタグ）・`memos`（小節メモ）・`sectionMarkers`（セクションマーカー）・`settings`（曲ごとの表示の設定、…）・`thumbnail`（曲一覧のサムネイル）の5つに限る。」
   - 前の詳細設計 `2759936` の editing-core.md 212 行「| 対象フィールド | alphaTab `MasterBar.timeSignatureNumerator` / `timeSignatureDenominator` / `timeSignatureCommon`（4/4 のとき `true`）。継承は本アプリ側の概念のため、`null` 指定時は直前の実値を解決して書き込み、`AppMetadata` 側に「この小節は継承」であることを保持する |」（行番号は `git show` の出力で数えた）
   - 今のコード（読んだだけ）：`packages/core/src/editing/commands/barCommands.ts` の小節を足すコマンドは、拍子を直前の小節の値で埋め（「masterBar.timeSignatureNumerator = prev.timeSignatureNumerator;」）、テンポは印を空にしている（「masterBar.tempoAutomations = []; // 継承（B5）」）。拍子の「継ぐ」の印はどこにも持っていない
   - 詳細設計 editing-core.md 3.2 節の注「拍子の「直前を継ぐ」を、alphaTab と曲のファイルのどこに持つかは、基本設計に書かれていないので本書では決めない。」
4. **選べる案**：

| | 案 A：直前と同じ値の小節を「継ぐ」と読む（印を持たない） | 案 B：`appMeta.settings` の中に「拍子をはっきり入れた小節」の一覧を持つ | 案 C：`appMeta` に 6 つ目の項目を足す |
|---|---|---|---|
| 1 小節目を変えたとき | 直前と同じ値が続く小節は、全部いっしょに変わる。前にはっきり同じ値を入れた小節も変わってしまう | 基本設計どおり。はっきり入れた小節は変わらない | B と同じ |
| 小節を消したとき（B5 の「削除の影響を受けない」） | 消した小節の次の小節は、消す前の値を持ったままになる。消した小節がはっきり違う拍子だったとき、次の小節は B5 の読み（前の小節を継ぐ）と違う値になる | 基本設計どおり | B と同じ |
| 譜面の見た目 | 同じ拍子が続く所に記号は出ないので、A でも B でも見た目は同じ（alphaTab が同じ拍子のときに記号を描かないことは確かめていない。未確認〈推測〉） | 同じ | 同じ |
| 基本設計の直し | 02:170 の「nullable＝直前値継承」を、「直前と同じ値＝継承」と読む書き方に直す。B5 の削除の文も直す | 02:270 の `settings` の説明に、拍子の一覧を持つことを足す | 02:270 の「5つに限る」を 6 つにする（本人の 2026-09-27 の決定を変える） |
| 今のコード | 小節を足すコマンドは今のまま。拍子を変えるコマンド（今は無い、G26）で、続く小節を一緒に変える | 拍子を変えるコマンドと小節を足す・消すコマンドが、一覧を読み書きする | B と同じ |

5. **見立て**：**案 B**
   - 根拠：B5 と 04 章 10 節が決めた振る舞い（足した小節は後から前の拍子に付いていく、消しても継ぐ向きは変わらない）をそのまま守れる。`settings` は「曲ごとの設定」として 5 つの中にあるので、本人が決めた 5 つの数を変えずに済む
   - 反対する理由：`settings` は「曲ごとの表示の設定」と書かれていて（02:270）、拍子の一覧は表示の設定ではない。入れると `settings` の意味が広がる。案 A なら何も足さずに済み、今のコードの小節を足すコマンドもそのまま使える。はっきり同じ値を入れる使い方がどれくらいあるかは分からない（未確認〈推測〉）
6. **決めた後**：
   - 選んだ案に合わせて基本設計 02:170（A）か 02:270（B・C）を直し、直した行を分解し直して承認に回す（02 章の区切り 3 か区切り 5 の 1 単位）
   - 詳細設計 editing-core.md 3.2 節の注を外して本文に書く。B・C なら data-model-persistence.md の `appMeta` の節（区切り 4 の回に作る）にも書く
   - 拾い上げの行 `editing-core.md:7ae8cd91`（前の詳細設計の「`null` の意味」の行）を、書いた場所へ set する
   - 取り消すとき：直した基本設計の行を前の文に戻して分解し直し、詳細設計は注に戻す
